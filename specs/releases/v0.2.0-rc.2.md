## Changes since 0.2.0-rc.1

- Docusaurus autogenerated sidebar blocks expand nested folders with document
  and category positions, numeric prefixes and JSON/YAML category labels. Index
  documents remain accessible, and repeated navigation references write one
  page file. Partial/hidden documents are excluded. Generated category indexes
  become editable MDX pages with child links, titles and descriptions, with
  collision-safe filenames. Manual category links import their target documents.
  Explicit document and generated-category slugs become route overrides under
  `/guide`, preserving case and Unicode while keeping source file/asset locations.
  Navigation, search and converted file links use those routes; collisions and
  unsafe slugs fail before writes. Generated default routes yield to explicit
  slugs. Styling, generated-index images/keywords, source deployment prefixes,
  root-relative source URLs, plugins and custom generators require review.
- Imports preserve authored page titles/descriptions independently of sidebar
  labels. Docusaurus custom document IDs, default number-prefix rules and
  `sidebar_label` resolve against real source files; draft/unlisted pages are
  excluded and reported. Empty declarative sidebars no longer import omitted
  files. Invalid metadata, ambiguous IDs and missing sidebar targets fail
  before writes.
- Imports preserve explicit Markdown heading IDs, including Docusaurus comment
  forms and IDs on leading page titles. TOC and search recognize the emitted
  literal MDX headings. Duplicate or unsupported explicit IDs fail before writes.
  Fenced examples containing shorter fences retain their literal source.
- An explicitly selected container runtime can use the full twelve-second
  discovery budget, accommodating slower `info` responses without switching to
  another runtime. Automatic discovery still limits each probe to three seconds.
- Hosted builds and image commands accept invocation-only `--base-path`,
  `--site-url` and `--no-check`. URL settings reach rendering, SEO metadata and
  image runtime/health checks without editing authored files. `/` clears a
  saved prefix; `--no-check` skips only the separate validation preflight.
  Portable HTML output rejects these hosted-only options. Delivery and `ship`
  carry them through one build to publication; `zel ci` can freeze them in
  generated workflows. Dry-run plans show the selected settings, and
  `--no-check` retains credential checks and rendering validation.
- `zel dev --host` selects an IPv4/IPv6 binding for either renderer. `--open`
  or `--browser <executable>` opens the ready site once, including a hosted
  site's configured prefix. Ctrl-C cleans up the owned hosted container.
- Hosted `zel check --json` emits a versioned report from the real engine,
  including deep findings and strict warnings. Content failures use exit 3;
  unavailable runtimes use exit 4, and incompatible engine reports use exit 1.
- Hosted development reloads open browser tabs after successful content and
  asset preparation, including image-only changes. Invalid edits retain the
  displayed page until corrected. Production pages do not poll for updates.
- Generated GitHub workflows use a separate concurrency group for each workflow
  filename and Git ref. Independent sites in one repository no longer replace
  each other's pending runs. Regenerate with `zel ci --force` after reviewing
  customizations; publishing a new CLI does not modify existing workflow files.
- Published-release acceptance retries transient download failures with bounded
  fresh attempts and can verify an immutable release tag using an updated test
  driver. Invalid files, checksums and version mismatches still fail.
- Documentation retains 46 original routes, 282 legacy heading targets and 29
  authored images while adding nine CLI pages and correcting repository links.
- Documentation acceptance now waits for hydration and rejects console errors
  as well as uncaught exceptions. Negative controls verify that a head newline
  causing React #418, an uncaught exception, and a console-only error all fail
  the checker.

This is a separate candidate; the rc.1 tag and assets remain unchanged. The
complete documentation on Netlify staging still encounters a hosting-injected
newline that causes a hydration failure. That issue is reported to Netlify and
is not claimed fixed in this candidate. Production documentation/domain cutover
and stable promotion remain separate decisions.

## Candidate highlights

This candidate brings the native CLI and installers up to the current Zellij
documentation workflow. It is intended for acceptance testing before 0.2.0 stable.

- **Portable documentation:** `zel init`, `build`/`b`, `serve`/`s`, `view`/`v`
  and `dev` support Markdown sites without Docker. Generated sites support direct
  `file://` navigation, search, links and bundled assets. Math, mindmaps and
  optional Mermaid rendering have offline support.
- **Short commands and conventional folders:** a documentation folder contains
  `zel.yaml`, `content/` and generated `site/`. Omitted paths discover the current
  documentation folder or `docs/zellij`. Global `--cwd`, `--site-root` and
  `--config` controls support other layouts and named configurations.
- **Hosted sites and images:** generate editable Next.js wrappers, build static
  or Next.js images with `zel si` and `zel ni`, and run/push images with `ir` and
  `ip`. Runtime discovery supports Docker, Podman and nerdctl, with useful
  diagnostics when no runtime is available. Commands do not install or start one.
- **Delivery:** `zel netlify`, `publish`/`pub` and `ship` build and deliver using
  saved settings. `zel ci` generates GitHub workflows pinned to a compatible
  release, including this candidate by default; it can also dispatch workflows.
- **Authoring and maintenance:** validation and formatting, validation watch,
  schema explanations and AI context, import/migration, shell completions,
  `doctor`, `version`, `pull`, `upgrade`, wrapper extraction and rendering-feature
  selection are available. Invocation-only feature overrides cover build,
  preview, development, images, delivery and CI generation.
- **Native packages:** x64 and ARM64 archives for GNU/Linux, macOS and Windows.
  Unix and PowerShell installers verify checksums and executable versions,
  preserve existing installations on failure and leave PATH changes to the user.

## Compatibility and current limits

The stable 0.1.3 executable predates these commands and configuration contracts.
Use the pinned candidate installation instructions below and select its matching
engine image for hosted/container commands. Candidate publication does not deploy
the production documentation website or promote stable installation channels.

The Next.js wrapper is served over HTTP; portable static output supports direct
file opening. Local image builds select one target platform; `pub` and `ship`
accept `--platform all` to publish both Linux AMD64 and ARM64 under one tag.
Generated image CI builds on native runners and combines immutable digests after
both builds succeed. The published engine images also provide both platforms. Netlify is
the implemented cloud deployment provider; other providers, broader conversion
fidelity and additional advanced build options remain future work. Unsupported
source constructs during migration still require review of the converted site.

## Acceptance

The release workflow builds and tests all six native archives before upload.
After publication, it downloads archives, checksums and installers from the
development release and, when enabled, the shared releases repository. Native
runner checks cover installation, reported version/architecture, replacement and
failure preservation, upgrade, portable build, serve/view and Ctrl-C shutdown.
The four published engine variants are pulled and executed on both native Linux
architectures. Check the **Release** workflow result before relying on a candidate;
a release page can exist while image publication or acceptance is still failing.

Image commands and image delivery now support repeatable explicit `--build-arg NAME=VALUE`, including aliases, printed recipes and generated GitHub workflows. Duplicate names use their last value. Values remain argv/workflow data; printed recipes contain names only. Static-folder and Netlify operations reject them before work. See the image and CI documentation for reserved settings and non-secret usage. This remains unpublished source functionality.

Site images use smaller runtimes: static images use NGINX Alpine slim, and Next.js
images exclude npm, Yarn and Node headers from their shipped layers. Node,
required libraries and traced application dependencies remain. CI measures image
size against the previous runtime bases with identical site content and exercises
both architectures. Combined local publication requires a suitably configured
builder; Zel does not install emulation or start services.
