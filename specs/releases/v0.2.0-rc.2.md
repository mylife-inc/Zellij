## Changes since 0.2.0-rc.1

This candidate includes the CLI, engine and documentation changes through the
public asset URL linking milestone (PR #103). It is a separate candidate; the
rc.1 tag and assets remain unchanged.

### Import and migrate existing documentation

- Six importers now serve `detect`, `list formats`, `convert` / `cv`,
  `migrate` / `mig` and `ship`: MkDocs, Docusaurus, VitePress, Jekyll, Hugo and
  Sphinx. They read supported declarative source files without executing source
  JavaScript, Python, Ruby, templates or extensions.
- Docusaurus imports support authored titles/descriptions, document IDs,
  autogenerated sidebars, category metadata, generated index pages, manual
  category links and explicit slugs. Draft/unlisted/partial documents are
  excluded and reported. Navigation, search and file links use emitted routes;
  ambiguous IDs, collisions and unsafe routes fail before writes.
- VitePress imports support literal configuration, standard `defineConfig`,
  `srcDir`, nested/multiple sidebars, metadata and referenced source/public
  assets. Only pages selected by declared sidebars are imported.
- Jekyll imports support YAML configuration, front-matter Markdown pages,
  output documentation collections, literal scoped defaults, navigation arrays,
  source permalinks and eligible static assets.
- Hugo imports support one TOML/YAML/JSON configuration, Markdown sections and
  leaf bundles, all three front matter formats, publication rules and supported
  links/resources. `_index.md` becomes a visible Zellij index page.
- Sphinx imports support literal `conf.py`, explicit toctrees, headings/labels,
  nested bullet and decimal/alphabetic/Roman lists, code, admonitions, images,
  rectangular grid/simple tables, list tables, inline/local-file CSV tables,
  document-local text/image substitutions and local UTF-8 `literalinclude`
  excerpts. Document, section and download references map to hosted output.
  Source files, nesting and expansion have bounded resource limits.
- Imported Markdown links preserve supported source deployment prefixes,
  website routes, queries, fragments and explicit heading IDs. Relative website
  document links use the original page URL. Ambiguous slash policies or omitted
  targets are reported instead of guessed. Fenced examples retain literal
  content, including nested fences. MkDocs nested paths are portable on Windows.
- `--assets copy|link|skip` applies to all six importers. Copy remains the default.
  Link requires `--asset-base-url https://.../` and emits public URLs for eligible
  local files without reading/copying asset bytes or fetching remote URLs.
  Source asset roots determine the URL paths; conflicting public paths fail
  before writes. CSV/include content inputs remain readable. Skip retains asset
  references and reports omissions. All modes retain containment, exclusion and
  symlink checks; none uploads assets to a CDN.
- `convert --validate` runs the same hosted validation used by migrate after
  writing. Failure retains converted files for repair and returns failure.
  Dry runs neither write nor validate through a runtime.

### Delivery and CI generation

- Native static delivery now includes Netlify, Cloudflare Pages (`cf`), Vercel
  (`vc`), GitHub Pages (`ghp`) and AWS S3 (`s3`). These adapters also work through
  saved `publish` / `pub`, import-and-`ship` and generated CI. They target existing
  configured resources; commands do not provision cloud projects or domains.
- Cloudflare Pages and Vercel create previews by default, with explicit
  production intent. Custom Cloudflare Functions/Workers and provider rule files
  remain unsupported. Vercel uploads prebuilt static output without a remote
  source build or the Vercel CLI.
- GitHub Pages requires an existing `gh-pages` root source and explicit
  production intent. Non-forced commits preserve history and custom domains;
  success requires the matching commit's Pages build.
- S3 requires an existing website bucket, region, expected owner and explicit
  production intent. Conditional writes detect concurrent changes. Uploads
  retain stale keys and are not atomic; bucket/CDN setup and pruning are excluded.
- Fly (`fly`) deploys static/Next AMD64 images to existing configured web
  Machines, with organization identity, leases, version guards and fresh health
  checks. Partial rollouts are reported; app creation, scaling and automatic
  rollback remain outside this command.
- Railway (`rw`) deploys registry images to an existing image service in an
  explicit project/environment. The image is built and pushed once; publication
  retains its registry digest. Success reports Railway's startup deployment
  status, not end-to-end website acceptance or continuing health. Railway needs
  its own registry pull access.
- `zel ci --system gitlab` and `--system circle` join the GitHub generator.
  All three use saved settings and an exact CLI/engine version pin. GitHub
  remains the default and the only system with native dispatch/provisioning.
  Generated GitHub workflows now have separate concurrency groups per workflow
  filename and Git ref, so independent sites do not replace each other's runs.
  Regenerate with `--force` after reviewing local customizations; installing a
  new CLI does not update existing workflow files.

### Authoring, builds and runtime behavior

- Opt-in native wizards guide site creation (`init -i`, `nd -i`), page creation
  (`np -i`) and editable app creation (`na -i`). They retain noninteractive
  command forms. Page registration remains a printed `pages.yaml` entry; app
  creation does not install dependencies.
- `new section` supports its wizard, scalar `--set`, complete JSON values through
  `--set-json`, optional-field `--unset`, list counts, pricing tiers/highlighting
  and positional output. These commands author new sections.
- `new docs --full` includes all 23 section examples and local media. `doctor [site]` resolves site/configuration settings, avoids unnecessary runtime probes
  for portable sites and offers structured JSON diagnostics.
- Hosted builds, images, delivery, ship and CI generation accept invocation-only
  `--base-path`, `--site-url` and `--no-check`. `/` clears a saved prefix.
  URL settings reach rendering, SEO and runtime/health checks without changing
  authored files. `--no-check` skips the separate content preflight, retaining
  credential checks and rendering validation. Portable HTML rejects these
  hosted-only options.
- Image commands and image delivery accept repeatable `--build-arg NAME=VALUE`,
  including aliases and generated workflows. Duplicate names use their last
  value; printed recipes show names only. Static-folder and Netlify delivery
  reject image build arguments. Build arguments are not a secret transport.
- `pub --platform all` and `ship --platform all` publish Linux AMD64 and ARM64 under one image
  tag. Generated image CI builds on native runners and combines immutable
  digests after both builds succeed. Local combined publication needs a
  configured builder; Zel does not install emulation or start services.
- Static site images use NGINX Alpine slim. Next.js site images omit npm, Yarn
  and Node headers from runtime layers while retaining Node, required libraries
  and traced application dependencies. CI compares compressed sizes using the
  same site content and exercises both architectures.
- `zel dev --host` selects IPv4/IPv6 bindings; `--open` or `--browser` opens the
  ready site, including its configured prefix. Ctrl-C cleans up the owned hosted
  container. Hosted development reloads after successful content or asset edits;
  invalid edits retain the displayed page until corrected. Production pages
  do not poll for edits.
- Hosted `check --json` reports versioned engine findings, including strict/deep
  results. Content failures use exit 3, unavailable runtimes exit 4, and
  incompatible reports exit 1. An explicitly selected runtime can use the full
  twelve-second discovery budget; automatic probes remain limited to three
  seconds per runtime.
- Windows upgrades recover from transient executable sharing locks while
  preserving the installed binary on failure. CLI dispatch is exhaustive at
  compile time. Imported download navigation, MDX code leaking into search,
  duplicated guide titles and shifted anchors with CRLF line endings are fixed.

### Documentation and acceptance

- Documentation preserves all 46 original routes, 282 original heading targets,
  82 compatibility mappings and 29 authored images, and adds nine CLI pages.
  Browser acceptance waits for hydration and rejects both console errors and
  uncaught exceptions, with independent negative controls.
- Published-release downloads retry transient failures with bounded fresh
  attempts. Acceptance can use an updated test driver against a separately
  checked-out immutable release tag. Checksums, invalid files and version
  mismatches still fail.

## Candidate highlights

- **Portable documentation:** `init`, `build` / `b`, `serve` / `s`, `view` / `v`
  and `dev` support Markdown without Docker. Generated portable sites support
  direct `file://` navigation, search, links and bundled assets. Math, mindmaps
  and optional Mermaid rendering have offline support. Publicly linked assets
  still require their external server.
- **Conventional folders and short commands:** a documentation folder contains
  `zel.yaml`, `content/` and generated `site/`. Omitted paths discover the current
  documentation folder or `docs/zellij`; explicitly selected folders may have
  any name. Global `--cwd`, `--site-root` and `--config` support other layouts.
- **Hosted sites and images:** editable Next.js wrappers, static/Next images
  through `si` / `ni`, and image run/push through `ir` / `ip`. Runtime discovery
  supports Docker, Podman and nerdctl with diagnostics when none is available.
  Commands do not install or start a runtime.
- **Maintenance:** validation/formatting, watch, schema explanations, AI context,
  completions, doctor, version, pull, upgrade, wrapper extraction and optional
  rendering-feature selection are available.
- **Native packages:** x64 and ARM64 archives for GNU/Linux, macOS and Windows.
  Unix and PowerShell installers verify checksums and executable versions,
  preserve existing installations on failure and leave PATH changes to the user.

## Compatibility and current limits

The stable 0.1.3 executable predates these contracts. Use the pinned candidate
installation instructions below and select its matching engine image for
hosted/container commands. The generator defaults to its own CLI version; that
version's native assets and matching images must exist before generated CI runs.
The Next.js wrapper requires HTTP; portable output supports direct file opening.

All registered command families have handlers. This does not mean the full
CLI design is complete or free of undiscovered bugs. In particular:

- Live-account acceptance remains pending for Cloudflare Pages, Vercel, GitHub
  Pages, AWS S3, Fly and Railway. Protocol fixtures and hosted-output tests cover
  these adapters; they do not replace testing against each live service.
- Actual GitLab and CircleCI runner acceptance remains pending. Generated YAML
  and build/publication recipes are tested separately in repository CI.
- Existing arbitrary YAML editing is not part of the new-section authoring
  commands. Importers retain documented limits: dynamic VitePress/Docusaurus
  configuration and custom routing; Jekyll Liquid/themes/blog semantics;
  complex Hugo menus/modules/cascades/localization; Sphinx/MyST/domains,
  extensions, parsed includes, spanning table cells and remote CSV sources.
  Unsupported constructs require manual migration and review of generated sites.
- Full documentation on Netlify staging encounters a hosting-injected newline
  that causes a hydration failure. It has been reported to Netlify and is
  not claimed fixed in this candidate. Production documentation/domain cutover
  remains a separate decision.

Candidate publication does not promote stable installation channels, move
`latest` image tags or deploy the production documentation site.

## Acceptance

The release workflow builds and tests all six native archives before upload.
After publication it downloads archives, checksums and installers from the
development release and, when enabled, the shared releases repository. Native
runner checks cover installation, version/architecture, replacement and failure
preservation, upgrade, portable build, serve/view and Ctrl-C shutdown. All four
published engine variants are pulled and executed on native Linux AMD64 and
ARM64 runners.

Check the **Release** workflow result before relying on this candidate: a
release page can exist while image publication or acceptance is still failing.
Pre-publication CI artifacts and their checksums provide preparation evidence;
they are not evidence that the public release downloads have passed acceptance.
