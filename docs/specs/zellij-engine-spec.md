## 1. What Zellij Is

Zellij is a shared Next.js engine that turns a folder of structured content (YAML + MDX + assets) into a complete, beautiful product website containing both **marketing pages** (Apple/Stripe-quality landing and feature pages) and **user guide documentation** (clean docs layout with sidebar navigation) — as a single site with a single deployment.

The name comes from Moroccan zellij mosaic art: intricate walls composed from a fixed vocabulary of geometric tiles. Zellij the engine works the same way — polished sites composed from a fixed vocabulary of **sections** ("tiles"), styled by **themes** ("glazes").

### 1.1 Comparison to mkdocs (mental model)

| | mkdocs | Zellij |
|---|---|---|
| Input | `mkdocs.yml` + markdown folder | `zellij.config.yaml` + content folder (YAML pages + MDX + assets) |
| Config expresses | File tree / nav | Page compositions from section building blocks + theme |
| Content format | Markdown | YAML (marketing pages), MDX (guides) |
| Output look | Traditional docs (sidebar tree + prose) | Marketing-grade visual design + docs layout for guides |
| Output nature | Static HTML | A Next.js app (statically generated by default, extensible with dynamic features later) |
| Distribution | CLI tool | Versioned npm package consumed by a thin per-product wrapper app |

### 1.2 Critical architectural rule

**Zellij is not a code generator.** It does not scaffold or emit Next.js projects. It is a versioned package (`@shebka/zellij`) that a thin per-product Next.js wrapper imports. All rendering logic, components, layouts, and future features live in the package. Products upgrade by bumping a dependency version — never by regenerating code.

The wrapper's `zellij.config.yaml` points at `../../docs/external`. Zellij reads that folder **at build time** and statically generates the site.

## 3. Technology Constraints

- **Next.js 16.2.x (latest stable line as of July 2026) using the App Router**, **React 19.2.x**, TypeScript 5.x in strict mode. Pin exact versions in the package's `peerDependencies` and the demo app's lockfile; do not scaffold on Next.js 15 (its support window ends October 2026).
  - Turbopack is the default bundler in Next.js 16 — do not introduce custom webpack configuration or webpack-only plugins.
  - Do not adopt TypeScript 7 yet; support for it only landed via recent 16.2 backports. Stay on TS 5.x unless the implementer verifies a clean build.
  - Always install current patch releases (Next.js and React shipped coordinated security patches in 2026 — being on the latest patch of the 16.2 line is a requirement, not a nicety).
- **Static generation by default**: every page produced via SSG. No runtime data fetching in v1. The architecture must not preclude adding server features later (see §10).
- **Tailwind CSS** for styling, driven entirely by CSS custom properties emitted from the active theme (see §6). No hardcoded colors/fonts in components.
- **MDX** via `next-mdx-remote` or `@next/mdx` (implementer's choice, justify in README) for guide content.
- **YAML parsing** via `yaml` package; **schema validation via `zod`** — every config and page file is validated at build time with human-readable errors (file, path, expected type). A malformed content file must fail the build loudly, never render a broken page.
- **`basePath` support is mandatory and must be tested.** All internal links, assets, and images must respect Next.js `basePath` so wrapper apps can be reverse-proxied under `shebka.net/products/<name>/docs`.
- No custom markdown dialect. No parser inventions. YAML + MDX + plain markdown only.

## 4. Content Model

Zellij consumes a content directory with this contract:

```
content/                          # (or docs/external in product repos)
├── marketing/
│   ├── landing.yaml              # required — the "/" page
│   ├── features.yaml             # optional additional marketing pages
│   └── <any>.yaml                # each YAML file = one marketing page
├── guide/
│   ├── _sidebar.yaml             # ordered nav structure for guide section
│   ├── index.mdx                 # guide home ("/guide")
│   ├── quickstart.mdx
│   └── <nested folders allowed>/
└── assets/                       # referenced by relative path from content files
```

Routing rules:

- `marketing/landing.yaml` → `/`
- `marketing/<name>.yaml` → `/<name>` (unless overridden by a `route:` field in the file)
- `guide/**/<name>.mdx` → `/guide/**/<name>`
- `assets/**` → served under the site's asset route, basePath-aware

## 5. Pages, Sections (Tiles) & Navigation

A marketing page YAML file declares an ordered list of sections. The engine maps each to a polished React component.

### 5.1 Page file shape

```yaml
# marketing/landing.yaml
title: "PayOS — Payments infrastructure that just works"
description: "SEO meta description here."
route: /                # optional override
sections:
  - type: hero
    headline: "Payments infrastructure that just works"
    subhead: "Run it as SaaS or deploy the full stack on your own cloud."
    cta:
      - { label: "Get started", href: /guide/quickstart, style: primary }
      - { label: "See features", href: /features, style: ghost }
    visual: assets/hero-dashboard.png
    visualStyle: floating        # floating | framed | full-bleed
  - type: logo-strip
    heading: "Trusted by teams at"
    logos: [assets/logos/a.svg, assets/logos/b.svg]
  - type: feature-grid
    heading: "Everything you need"
    columns: 3
    items:
      - { icon: refresh, title: "One-click reconciliation", body: "Match transactions across providers automatically." }
      - { icon: shield,  title: "Built-in compliance",     body: "PCI scope reduction out of the box." }
  - type: zigzag
    rows:
      - { title: "...", body: "...", image: assets/shot1.png, align: image-right }
      - { title: "...", body: "...", image: assets/shot2.png, align: image-left }
  - type: cta-banner
    headline: "Ready to ship payments?"
    cta: { label: "Read the guide", href: /guide }
```

### 5.2 Section inventory (v1 — all 12 required)

Each section gets: a zod schema, a React component, responsive behavior (mobile-first), and a demo instance in `apps/demo`.

1. **hero** — headline, subhead, up to 2 CTAs, optional visual with 3 display styles, optional announcement badge.
2. **logo-strip** — heading + row of logos, grayscale-until-hover treatment.
3. **feature-grid** — heading, optional subhead, 2/3/4 columns of icon+title+body cards. Icons from `lucide-react` referenced by name; unknown icon names fail the build.
4. **zigzag** — alternating text/image rows; each row: title, body (markdown-inline allowed), image, align.
5. **showcase** — one large full-width panel: eyebrow, headline, body, large visual; supports `background: default | tinted | inverted`. (The Apple "learn more" building block.)
6. **stats-band** — 3–5 big numbers with labels.
7. **testimonial** — single quote (author, role, avatar) or carousel of up to 5.
8. **pricing-table** — 1–4 tiers: name, price, period, feature list, CTA, `highlighted: true` on one tier. Must gracefully render a single "Contact us" tier.
9. **faq** — accordion of question/answer pairs (answers support markdown-inline).
10. **cta-banner** — closing full-width call to action.
11. **markdown-prose** — escape hatch: renders an MDX/markdown block inside marketing styling, for pages needing free-form prose (e.g. an "About" page).
12. **video-embed** — self-hosted mp4 or YouTube/Vimeo URL, with poster image; lazy-loaded.

Design bar for every section: generous whitespace, a deliberate type scale, subtle borders/shadows per theme, and motion behavior per the motion system in §6.5. The demo app should look like a real, expensive product site, not a component gallery.

### 5.3 Extensibility

Section `type` dispatch must be a registry so v2 can add sections (or allow wrapper-registered custom sections) without touching core dispatch logic. Unknown `type` in content = build error listing valid types.

### 5.4 The Page Model

A **page** is the unit of navigation: one YAML file declaring an ordered list of sections rendered top-to-bottom, plus a page-level layout choice. Each file in `marketing/` is one page; there is no limit on how many pages a product defines.

Page-level fields:

```yaml
title: "Features — PayOS"       # required; used for <title> and OG
description: "..."               # required; meta description
route: /features                 # optional; defaults to filename
layout: stack                    # optional; defaults to stack (see below)
theme: midnight                  # optional per-page theme override
motion: expressive               # optional per-page motion override
navHighlight: features           # optional; which nav item shows as active
sections: [...]                  # ordered list of tiles
```

**Page layouts** (the frame around the section stack — not the sections themselves):

- `stack` (default) — full-width vertical stack of sections; the standard marketing page.
- `stack-narrow` — same, but the content column is capped (~900px) and centered; for text-led pages such as About, Security, or Changelog.
- `stack-sidebar` — vertical stack with a persistent right-hand rail (e.g. a sticky "Request a demo" card or in-page section links); for long feature pages.
- `landing` — `stack` plus landing-specific treatment: nav starts transparent over a full-bleed hero and solidifies on scroll (see §5.5).

Layouts are a small closed set for the same reason themes are: arbitrary per-product layouts would reintroduce visual drift. Adding a layout is an engine change, not a content change.

**Section anchors.** Any section may declare `id: pricing`, which renders an anchor target and makes `/features#pricing` valid as a nav or CTA destination. Anchor scrolling must respect the sticky bar height (CSS `scroll-margin-top` derived from the nav token) so targets are never hidden behind the bar.

### 5.5 Sticky Top Navigation Bar

The nav bar is declared once in `zellij.config.yaml` and is shared by every marketing page and the guide docs layout, so branding and navigation stay identical sitewide. Content authors never touch nav code.

**Behavior requirements:**

- **Sticky by default**, pinned to the viewport top across the whole site, above all page content, with a theme-defined height, background treatment (solid, tinted, or translucent-blurred), and bottom hairline.
- **Scroll transition:** on `layout: landing` pages the bar begins transparent with no border over the hero and animates to its solid/blurred state past a scroll threshold (default 80px, configurable). On all other layouts it renders solid from the start. Behavior obeys the motion preset — under `motion: none` the bar simply renders solid always.
- **Auto-hide (optional):** `nav.hideOnScrollDown: true` hides the bar when scrolling down and reveals it on scroll up; default `false`.
- **Logo on the left**, linking to `/` (the landing page). Uses `logoDark` automatically in dark mode.
- **Links centered or left-aligned** per `nav.align`; **CTA button(s) on the right**.
- **Active-state highlighting:** the nav item matching the current route (or the page's `navHighlight`) is visually marked. On landing pages with in-page anchor links, the active item updates as the user scrolls between sections (IntersectionObserver-driven scroll spy).
- **Dropdowns and mega-menus:** a nav item may declare children — either a simple dropdown list or a `mega` panel with grouped, described links (title + one-line description + optional icon). Keyboard accessible (arrow keys, Escape to close), focus-trapped while open, and hover-or-click on desktop, tap-to-expand on mobile.
- **Mobile:** below the theme's `md` breakpoint the links collapse into a hamburger that opens a full-height drawer with the same items (nested items as accordions) and the CTA pinned at the bottom. Body scroll locks while open; Escape and backdrop tap close it.
- **Extras:** optional theme toggle (`nav.themeToggle: true`), optional search trigger (`nav.search: true` — opens the ⌘K modal from §7.3), optional GitHub/social icons, optional announcement bar rendered directly above the nav (dismissible, dismissal remembered in `localStorage`).
- **Accessibility:** `<header>` + `<nav>` landmarks, `aria-current` on the active link, `aria-expanded` on toggles, visible focus rings, and a "Skip to content" link as the first focusable element.

**Config shape:**

```yaml
nav:
  sticky: true                  # default true
  align: left                   # left | center
  hideOnScrollDown: false
  transparentOverHero: true     # applies to layout: landing pages
  scrollThreshold: 80
  themeToggle: true
  search: true
  links:
    - { label: Features, href: /features }          # → marketing/features.yaml
    - { label: Pricing,  href: /pricing }
    - label: Solutions                               # dropdown
      children:
        - { label: For startups,   href: /solutions/startups }
        - { label: For enterprise, href: /solutions/enterprise }
    - label: Resources                               # mega panel
      mega:
        groups:
          - heading: Learn
            items:
              - { label: Guide,     href: /guide,        description: "Install, configure, operate.", icon: book }
              - { label: Changelog, href: /changelog,    description: "What shipped recently.",      icon: clock }
    - { label: Security, href: /features#security }  # anchor into a section
  cta:
    - { label: "Get started", href: /guide/quickstart, style: primary }
  social:
    github: "https://github.com/shebka/payos"
  announcement:                 # optional bar above the nav
    text: "PayOS 2.0 is live —"
    link: { label: "read the notes", href: /changelog }
    dismissible: true
```

**Validation (build-time, fail loudly):** every `href` must resolve to an existing page route, an existing guide path, a declared section `id` anchor, or an absolute external URL. A nav link pointing at a nonexistent page is a build error naming the offending label and href — this is the single most valuable guardrail in the whole nav system, since broken nav is the most visible possible defect on a marketing site.

**Footer** follows the same declarative model (already in §8) and reuses the link-validation logic.

## 6. Themes ("Glazes")

A theme is a named token set: color palette (light + dark), font pairing (heading/body, loaded via `next/font`), radius scale, spacing scale, shadow style, and per-section accent behavior.

- Ship **10 built-in themes** with genuinely distinct personalities (different font pairings, palettes, radius/shadow character — not palette swaps):
  1. `midnight` — dark, electric accent, tight geometry (Linear-like)
  2. `paper` — light, warm, editorial serif headings (Stripe-docs-like)
  3. `terracotta` — warm Moroccan palette, generous curves (Shebka house style)
  4. `mono` — austere black/white with a single accent, brutalist edges
  5. `aurora` — dark with soft gradient glows and glassy surfaces
  6. `slate` — cool corporate blue-gray, enterprise-safe
  7. `forest` — deep greens, natural, calm SaaS
  8. `sunburst` — light, high-energy warm accent, playful radius
  9. `carbon` — near-black developer-tool aesthetic, monospace-flavored headings
  10. `porcelain` — ultra-minimal light, hairline borders, luxury feel
- Selected in `zellij.config.yaml` via `theme: terracotta`.
- **Token override block** in config lets a product tweak (e.g. `accent: "#0EA5E9"`, `radius: lg`) without forking a theme.
- Implementation: themes emit CSS custom properties on `:root`; Tailwind config maps utilities to those variables. Components never reference raw values.
- Dark mode: each theme defines both modes; config chooses `mode: light | dark | system`.

### 6.5 Motion System — scroll-driven animation & motion polish

Motion is a first-class part of Zellij: it is what separates an "expensive-feeling" product site from a static template. It must also be entirely declarative — content authors never write animation code.

**Motion presets.** The engine ships three global presets, selected in config via `motion: none | subtle | expressive` (default `subtle`):

- `none` — zero animation; also the forced behavior when the visitor has `prefers-reduced-motion` set, regardless of config. This accessibility override is mandatory and must be tested.
- `subtle` — entrance reveals only: sections and their child items (cards, zigzag rows, stats) fade/translate in on scroll, with small stagger between siblings. Implemented with IntersectionObserver + CSS transitions.
- `expressive` — everything in `subtle`, plus scroll-driven effects on selected sections:
  - **hero**: gentle parallax on the visual; headline entrance on load.
  - **showcase**: sticky-scroll treatment — visual pins while accompanying text scrolls/steps past (the signature Apple "learn more" effect), with a scroll-linked scale/opacity ramp on the visual.
  - **zigzag**: per-row reveals with directional translate matching each row's alignment.
  - **stats-band**: count-up animation on numbers when entering the viewport.
  - **feature-grid**: staggered card reveals; subtle hover lift.

**Per-section override.** Any section instance may set `motion: none | subtle | expressive` in its YAML to deviate from the global preset (e.g., an expressive hero on an otherwise subtle page).

**Theme motion personality.** Each theme's token set includes motion tokens — duration scale, easing curves, translate distance — so `mono` moves crisply and minimally while `aurora` moves slowly and softly. Components read motion values only from tokens, never hardcoded.

**Implementation constraints.** Prefer native primitives: IntersectionObserver, CSS transitions/animations, and CSS scroll-driven animations (`animation-timeline: view()`/`scroll()`) with an IntersectionObserver fallback where unsupported. A small dependency (e.g. `motion`) is permitted **only** for the sticky-showcase and parallax behaviors if native CSS proves insufficient — justify in the README, keep it tree-shaken out of guide pages. Guide docs pages use no scroll animation beyond trivial hover/focus transitions; motion is a marketing-layout concern. All motion must be transform/opacity-only (no layout-shifting animations) to protect Lighthouse CLS.

## 7. Guide Docs

Rendered under `/guide/**` with a docs layout: left sidebar (from `_sidebar.yaml`), prose column (~70ch), right-hand "On this page" table of contents from headings, previous/next links, and breadcrumbs. Fully themed by the active theme.

### 7.1 `_sidebar.yaml`

```yaml
- label: Getting Started
  items:
    - quickstart            # refers to guide/quickstart.mdx
    - installation
- label: Configuration
  items:
    - config/overview
    - config/database
```

Files present on disk but absent from the sidebar: build warning, page still generated. Sidebar entries with no matching file: build error.

### 7.2 MDX component set (available in guide files without imports)

`<Callout type="info|warning|danger|tip">`, `<Steps>` / `<Step title="">`, `<Tabs>` / `<Tab label="">`, `<CodeGroup>` (multi-language code tabs), `<Card>` / `<CardGrid>`, `<Screenshot src caption>`, and syntax-highlighted code blocks (Shiki) with copy button, line highlighting via meta (```ts {2,4-6}```), and filename labels (```ts title="next.config.js"```).

### 7.3 Search

v1: client-side search over guide content using a build-time index (Pagefind or FlexSearch), ⌘K modal. Marketing pages excluded from the index.

## 10. Future-Proofing (design for, don't build)

The engine will later gain dynamic features (auth-gated pages, feedback widgets, DB-backed changelogs, in-app search service). v1 must therefore:

- Keep all content loading behind a single `ContentSource` interface (v1: filesystem) so remote/DB sources can be added.
- Keep rendering server-component-first so switching selected routes from SSG to dynamic rendering is a per-route change, not a rewrite.
- Version the config schema (`schemaVersion: 1` implicit) and validate forward-compatibly (unknown top-level keys = warning, not error).

Explicit non-goals for v1: versioned docs, i18n/locales, remote content, CMS integration, comments, A/B testing. Do not build these.

## 13. Resolved Implementation Decisions (v1.1)

This section settles the choices the spec explicitly delegated to the implementer and closes gaps in the original draft. Where §13 is more specific than an earlier section, §13 wins. Each milestone is delivered and reviewed before the next begins (incremental cadence, per owner direction).

### 13.1 Toolchain baseline

- **Node.js ≥ 20.11 (LTS "Iron") or ≥ 22.x.** Enforced via `engines` in every `package.json` and a root `.nvmrc`. Next.js 16 requires Node 20.9+; we floor slightly higher for stable `node:` test runners and `structuredClone`.
- **Package manager: npm** (workspaces), matching §2.1 — no pnpm/yarn. A root `package-lock.json` is committed. Turborepo is optional and deferred; plain npm workspace scripts (`--workspaces`, `-w`) are sufficient for v1.
- **TypeScript 5.x strict** across the monorepo, shared `tsconfig.base.json`. No TS 7 (per §3).

### 13.2 Package build & consumption — `transpilePackages` now, `tsup` for publish later

- **In-monorepo (dev + demo build):** `@shebka/zellij`'s `package.json` `exports` map points at **TypeScript source** (`./src/index.ts` and subpath entries). The demo app consumes it via Next's **`transpilePackages: ['@shebka/zellij']`**. No build step gates local development; Turbopack compiles package source directly (fast inner loop, honors §3's "Turbopack is default, no webpack config").
- **For npm publishing (M6):** add a **`tsup`** dual-format build (ESM + CJS + `.d.ts`) emitting to `dist/`, and a `publishConfig`/`exports` overlay that points published consumers at `dist/`. `"use client"` directives must be preserved (tsup `banner`/esbuild handling verified) so client components survive the build. This is a packaging concern only — it does not change any component code.
- **Client/server boundary discipline (enables §10 future-proofing):** section and layout components are **server components by default**; only interactive leaves (nav drawer, accordion, tabs, carousel, scroll-spy, motion wrappers, ⌘K search) carry `"use client"`. This keeps the SSG-first posture and lets selected routes go dynamic later without a rewrite.

### 13.3 Content pipeline & the `ContentSource` interface

All content access goes through one interface (per §10) so the filesystem source can later be joined by remote/DB sources. v1 ships **only** `FileSystemContentSource`.

```ts
// packages/zellij/src/content/source.ts
export interface ContentSource {
  /** Resolved site config (validated). */
  loadConfig(): Promise<ZellijConfig>;
  /** All marketing pages (parsed + validated), keyed by resolved route. */
  listMarketingPages(): Promise<MarketingPage[]>;
  /** Ordered guide sidebar tree from _sidebar.yaml. */
  loadGuideSidebar(): Promise<SidebarNode[]>;
  /** All guide docs (raw MDX source + frontmatter + resolved route). */
  listGuidePages(): Promise<GuidePage[]>;
  /** Resolve a content-relative asset path to something renderable (see 13.4). */
  resolveAsset(relPath: string): Promise<ResolvedAsset>;
}
```

- The catch-all route (`app/[[...slug]]/page.tsx`, §9) resolves a slug against the union of marketing routes and guide routes; `generateStaticParams` enumerates both. Route collisions between a marketing page and a guide path are a **build error**.
- Parsing: `yaml` → `zod` for config + marketing pages; `gray-matter` for MDX frontmatter, then `zod` on the frontmatter. **Every** validation failure throws a build error naming `file · path · expected` (per §3). A shared `formatZodError(file, error)` helper produces these messages so errors read identically everywhere.
- Link/anchor validation (§5.5, §8 footer) runs as a **whole-site pass** after all pages load — it needs the full route + anchor-`id` inventory — and is the single guardrail called out in §5.5. It emits one aggregated, sorted error list rather than failing on the first bad link.

### 13.4 Asset serving under `basePath` (gap closed)

The original draft said assets are "served under the site's asset route" without defining it. Resolution:

- Content lives **outside** the Next app (`docs/external/assets`, or `apps/demo/content/assets`), so it cannot sit in `public/` directly. At build, Zellij exposes assets in **two** ways depending on use:
  1. **`next/image`-optimized images** (heroes, screenshots, feature/zigzag/showcase visuals — everything that must hit Lighthouse ≥95 per §11.6): the content loader copies referenced images into the app's `public/_zellij/assets/**` during a **prebuild content-sync step** (`zellij sync-assets`, wired into the demo's `predev`/`prebuild`), and components render them via `next/image` with a `src` of `/_zellij/assets/...`. `next/image` automatically prepends `basePath`, so reverse-proxied wrappers work with no extra logic.
  2. **Raw/static assets** (logos as inline SVG where possible, video posters, downloadable files): same `public/_zellij/assets/**` location, referenced through a `withBasePath(path)` helper that reads the configured `basePath` so non-`next/image` URLs are also prefix-correct.
- A single **`asset()` resolver** maps a content-relative path (`assets/hero.png`) to its public URL (`/_zellij/assets/hero.png`) and is the only place paths are rewritten. SVG logos are inlined at build (enabling `currentColor`/dark-mode swap per §5.5) rather than copied when small.
- **`basePath` is threaded from one source:** `zellij.config.yaml` (or `next.config.js`) → a build-time constant → `asset()`, `next/image`, the FlexSearch index base, and internal `<Link>`s. §11.5's `basePath: '/products/acme/docs'` test asserts links, images, fonts, and search index fetch all resolve correctly.

### 13.5 MDX pipeline — `next-mdx-remote/rsc`

- Guide `.mdx` is compiled with **`next-mdx-remote/rsc`** (RSC-native `compileMDX`), loaded by path in the catch-all route. This suits file-driven routing where content lives outside `app/`.
- The §7.2 component set (`Callout`, `Steps`/`Step`, `Tabs`/`Tab`, `CodeGroup`, `Card`/`CardGrid`, `Screenshot`) is supplied via the `components` map so guide authors use them **without imports**.
- Plugins: `remark-gfm`; `rehype-slug` + a TOC extractor for the "On this page" rail; **`@shikijs/rehype`** (Shiki) for highlighting with copy button, line-highlight meta (```` ```ts {2,4-6} ````), and `title="..."` filename labels (§7.2). Shiki themes are chosen per active Zellij theme's light/dark mode.
- Marketing's `markdown-prose` section (§5.2 #11) reuses the same MDX compile + component map inside marketing styling, so there is one MDX path, not two.

### 13.6 Guide search — FlexSearch + build-time index

- A **build-time indexer** walks guide MDX, strips to searchable text (headings weighted), and emits a static JSON index to `public/_zellij/search-index.json`. Marketing pages are **excluded** (§7.3).
- The **⌘K modal** (client component, also opened by `nav.search`, §5.5) lazy-loads **FlexSearch** + the index on first open (kept out of the initial bundle and out of guide-page critical path). Index fetch URL is `basePath`-aware via `asset()`/`withBasePath`.
- Chosen over Pagefind for full control of `basePath` correctness and exactly what gets indexed under a reverse proxy.

### 13.7 Test tooling — Vitest + Playwright

- **Vitest (unit/integration):** zod schemas (valid + invalid fixtures), config/content loaders, route resolution & collision detection, link/anchor validation (asserts the nonexistent-nav-link fixture fails with the right message, §11.2a), `asset()`/`withBasePath` under a set `basePath`, and the search indexer output shape.
- **Playwright (e2e):** runs against the built demo. Covers the browser-dependent acceptance criteria — nav sticky/transparent-to-solid transition, dropdown + mega panel, anchor scroll offset, active-state scroll spy, mobile drawer, theme toggle, dismissible announcement (§11.2a); `prefers-reduced-motion` disables animation (§11.3, via emulated media); `basePath` links/images/fonts/search (§11.5); keyboard nav of accordion/tabs/search (§11.7).
- **Build-failure fixtures** (§11.4): a `__fixtures__/broken/` set (bad YAML, unknown section `type`, unknown lucide icon, sidebar entry with no file, nav link to nonexistent page) asserted to fail `next build` / the loader with clear messages. These live outside the demo's real content so they never ship.
- **Lighthouse (§11.6):** an assertion via `@lhci/cli` (or a documented manual run) against the built landing page targeting perf ≥95, a11y ≥95, SEO 100. Documented as the M6 gate.

### 13.8 Milestone Definition-of-Done (checkpoint contract)

Each milestone is "done" only when: it builds clean (`tsc` strict + `next build` where applicable), its slice of the demo renders, its automated tests pass, and the relevant §11 acceptance criteria for that slice are demonstrably met. Milestone boundaries follow §12 exactly (M1, **M1b**, M2–M6). At each checkpoint I stop and surface the result before starting the next milestone.
