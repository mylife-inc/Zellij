<Callout type="tip" title="Available">
Works today. Reads a schema compiled into the binary, so it needs no container,
no network and no content folder.
</Callout>

```bash title="terminal"
zel list sections
zel list themes
zel list formats
zel list targets
```

Four inventories. Each answers a question you would otherwise answer by reading
documentation that might describe a different version of the tool than the one
you have.

## Why it exists

Zellij has 23 section types and fourteen themes. Nobody holds that in
their head, and the failure it prevents is specific: writing a plausible
section type that the build rejects, or picking a theme name that does not
exist and finding out four minutes into a build.

More importantly, **this prints what *your* binary knows**, not what the website
says. Converters are compiled in; a build without the Docusaurus converter will
not list it. The reference on this site describes the current release, and the
binary in your hand may not be it.

## `zel list sections`

```
bento-grid       3 fields, 1 required
card-carousel    5 fields, 1 required
cta-banner       3 fields, 1 required
faq              2 fields, 1 required
feature-grid     4 fields, 1 required
gallery          5 fields, 1 required
hero             6 fields, 1 required
logo-strip       2 fields, 1 required
…
```

The field counts are the useful part. A type with one required field is
something you can write in thirty seconds; a type with six is worth reading
[`zel explain`](/cli/explain) for first.

Every one of them is a file you write in `sections/`, and a name you put in
`pages.yaml`. See [Pages and sections](/guide/pages-and-sections) for how they
assemble, and [the section reference](/sections) for what each one looks like
rendered.

## `zel list themes`

All fourteen, with what distinguishes them. A theme is one line in `site.yaml`:

```yaml title="site.yaml"
theme: cupertino
```

Changing it changes every colour, every font stack and every radius on the site,
and changes nothing about your content. See [Themes](/guide/themes) for what
each one is for.

## `zel list formats`

```
docusaurus     Docusaurus — sidebars.js and a docs folder
mkdocs         MkDocs — mkdocs.yml with a nav tree
```

What [`zel convert`](/cli/convert) can read. **Run this before planning a
migration.** Converters are plugins compiled into the binary, so this is the
authoritative answer for the binary you have — and a format that is not listed
is one you will need the [AI route](/cli/context) for.

## `zel list targets`

```
static   A folder of HTML, CSS and JS. Any CDN, free. The default.
image    A container running the site on port 3000. Any registry. ~150 MB.
```

What [`zel build`](/cli/build) can produce. Two, not four — earlier drafts
listed `node` and `image:static`, and neither was a product anyone chooses
between. [`zel build`](/cli/build#what-happened-to-node-and-imagestatic)
explains why they went.

## Machine-readable

```bash title="terminal"
zel list sections --json
```

All four lists support `--json`. Stdout contains one object with the matching
array; errors go to stderr and return a nonzero exit code.

| Command | Array | Fields on each entry |
| --- | --- | --- |
| `list sections` | `sections` | `type`, `fields`, `required` |
| `list themes` | `themes` | `name`, `label`, `description` |
| `list formats` | `formats` | `id`, `label` |
| `list targets` | `targets` | `id`, `description` |

Section field counts exclude the shared presentation fields, just like the
human listing. Sections and themes use engine registration order; formats are
sorted by ID; targets list `static` then `image`. Consumers should select by
identifier rather than array position. The theme names and descriptions come
from the same generated catalog as the renderer.

JSON is also available for [`context`](/cli/context), [`explain`](/cli/explain)
and [`detect`](/cli/detect). Other Rust commands reject `--json` with exit code
2 before running. `--verbose` / `-v` is not implemented and is rejected as an
unknown option.
