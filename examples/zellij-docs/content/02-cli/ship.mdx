<Callout type="tip" title="Available in candidate 0.2.0-rc.1">
Current source imports MkDocs, Docusaurus, VitePress, Jekyll, Hugo or Sphinx into a
new configured hosted site, then uses shared delivery to build once and publish.
The original MkDocs/Docusaurus and Netlify/image paths are available in candidate
`0.2.0-rc.1`; the additional import formats and Cloudflare/Vercel/GitHub Pages/S3/Fly/Railway providers are
newer source functionality. Stable `0.1.3` predates these commands.
</Callout>

```bash title="terminal"
zel ship ./old-docs --out ./manual --provider netlify --site-id existing-site-id
```

Set `NETLIFY_AUTH_TOKEN` in your environment first. The site must already exist.
Netlify creates a **draft preview** unless you pass `--prod`. `--site-id` (also
`--site`) overrides `NETLIFY_SITE_ID`. No login or account/site creation runs.

`--out` is required and names the converted site root:

```text
manual/
  zel.yaml
  content/
    site.yaml
    01-guide/
    assets/
```

The original source remains untouched. The destination must be new or empty,
outside the source tree, with neither directory containing the other.

## Publish an image

Choose the contents explicitly and provide the exact registry reference:

```bash title="terminal"
zel ship ./old-docs --out ./manual --image static --tag ghcr.io/acme/manual:v1
zel ship ./other-docs --out ./other-manual --image next --tag ghcr.io/acme/other:v1
```

`static` packages generated HTML with an HTTP server; `next` packages the
standalone Next.js wrapper. Authenticate your container client with the registry
first. Image publication does not also deploy to a cloud provider.

All current import converters emit hosted content. Validation/build therefore
requires a running Docker, Podman or nerdctl runtime and a compatible Zellij
engine image, including for Netlify. Missing or stopped runtimes produce an
error with setup guidance; Zellij does not install or start them. The generated
hosted HTML needs HTTP serving. For Markdown sites that support double-clicking
`index.html`, use the [portable renderer](/cli/build).

## Inspect the conversion first

```bash title="terminal"
zel ship ./old-docs --out ./manual --provider netlify --site-id existing-site-id --dry-run
```

This reads and converts the source in memory, lists proposed files and conversion
warnings, and prints the delivery destination. It writes nothing and performs no
validation, runtime/credential checks, builds or network requests. Ambiguous
format detection requires `--from mkdocs` or `--from docusaurus`.

Warnings about skipped documents, external navigation and unsupported source
features stay visible. Building successfully establishes that the generated
content compiles; review navigation and content to assess migration fidelity.

## After success or failure

The new `zel.yaml` saves the image kind/tag or Netlify site ID, never credentials.
Production intent is not saved: a later Netlify publication defaults to a draft.

```bash title="terminal"
zel check ./manual
zel publish ./manual
# Request live Netlify publication explicitly:
zel publish ./manual --prod
```

Conversion/plan errors stop before writing. Once import completes, any later
runtime, credential, validation, build or delivery failure leaves the converted
site available for review. Fix the failing stage and use the saved site; rerunning
`ship` against the now-populated destination is refused. A failed image push can
be retried with `zel image push <exact-tag>` without rebuilding. If Netlify reports
an uncertain upload result, inspect its dashboard before retrying.

The composed command validates and builds once, then hands that result to the
publication step. No push/upload follows a failed build. It does not create a
persistent local `site/` export; use `zel build ./manual` when you want one.

## Temporary feature selection

```bash title="terminal"
zel ship ./old-docs --out ./manual --image static --tag ghcr.io/acme/manual:v1 --features all
```

`--features maths|diagrams|maths,diagrams|all|none` applies a complete rendering
selection to this command's build, for image or Netlify delivery. The plan
shows the selection, and no push/upload occurs after a build failure.

Unlike the destination and image platform, this override is not saved in the
imported `zel.yaml`. After success or a failed build, pass the same flag to
`zel publish ./manual --features all` to repeat that selection. Omitting it
uses the engine image's default. A failed image push can still be retried
without rebuilding using `zel image push <tag>`; that command needs no feature
flag because the image is already built.

## Build overrides for the imported site

The current source accepts `--base-path`, `--site-url` and `--no-check` for both
image kinds and Netlify delivery, since imported content uses hosted rendering:

```bash
zel ship ./old-docs --out ./manual --image next --tag ghcr.io/acme/manual:v1 --base-path /manual --site-url https://docs.example.com
```

The flags appear in dry-run plans and apply to the single build, using the same
[URL and validation rules as build](/cli/build#hosted-url-and-validation-overrides).
They are not saved in the converted site's configuration. Repeat them with a
later `zel pub ./manual` invocation to reuse them. Failure guidance names this
requirement while retaining converted files and leaving the source unchanged.
`--no-check` still requires valid preparation/rendering and does not bypass
credentials, runtime or conversion checks. These flags require a current CLI
and compatible engine; candidate `0.2.0-rc.1` does not include them.

## Options

| Option | Behavior |
| --- | --- |
| `<source>` | Required external documentation root |
| `--out <path>` | Required new or empty configured site root |
| `--from <format>` | Force the converter instead of detecting |
| `--assets copy\|skip` | Copy referenced assets by default; skip retains original URLs and reports omissions |
| `--kind <kind>` | Fly/Railway image kind: `static` (default) or `next`; distinct from registry-only `--image` |
| `--provider <provider>` | Deploy using `netlify`, `cloudflare`, `vercel`, `github-pages`, `s3`, `fly` or `railway` |
| `--image static\|next` | Publish this image kind; conflicts with `--provider` |
| `--tag <reference>` | Required with `--image` or Railway; exact registry destination |
| `--site-id <destination>` / `--site <destination>` | Provider-specific project, repository, bucket/prefix, Fly app or Railway service UUID; overrides provider environment |
| `--prod` | Request production; required for GitHub Pages, S3, Fly and Railway, conflicts with `--image` |
| `--features <selection>` | Complete rendering selection for this build only; saved settings stay unchanged |
| `--base-path <path>` | Hosted deployment prefix; `/` clears it only when compatible with the provider mount |
| `--site-url <origin>` | Hosted public HTTP(S) origin for canonical URLs and SEO metadata |
| `--no-check` | Skip content preflight; retain preparation, rendering and credential checks |
| `--dry-run` | In-memory conversion and plan only |

The current source accepts `--assets skip` when you intend to manage assets
separately. It omits referenced asset files without changing their URLs; links
between imported documents still convert. Those asset references may need repair
before the site can build or work correctly. Inspect the dry-run report or use
`convert` first if repairs are needed before delivery. This import-only policy
is not saved in `zel.yaml`; later `zel publish` uses the files already imported.
See [asset policy](/cli/convert#document-links-and-assets). The flag is newer than
the published rc.1 CLI.

## Image build arguments

Current source accepts repeatable `--build-arg NAME=VALUE` with `--image static`
or `--image next`. The arguments reach the imported site's image build before
push. They are not saved in the converted site's configuration; repeat them when
rebuilding. Failure retains the converted content and gives that reminder.
Netlify `ship` rejects the option before conversion writes or remote requests.
See [image build arguments](/cli/image#image-build-arguments) for value semantics.

Image delivery also accepts `--platform linux/amd64`, `--platform linux/arm64`,
or `--platform all` to publish both architectures under the supplied tag.
The choice is shown in the plan, saved as `image.platform` in the imported site's
`zel.yaml`, and used by the build and later `zel pub` commands. This flag
requires `--image`, except Fly/Railway also accept `--platform linux/amd64`; static upload providers reject it.
Combined publication requires a builder supporting both architectures. If it
fails, the converted site remains available for `zel pub`; inspect the registry
before retrying since uploaded layers may exist. See
[image publication prerequisites](/cli/image#select-the-image-platform).

## Ship to Cloudflare Pages

Current source accepts `zel ship source --out converted --provider cloudflare
--site manual`. It converts into a configured hosted site, then builds once and
uploads a Pages preview. `--prod` requests production for this invocation only.
The generated configuration saves `provider: cloudflare` and the project name;
future updates use `zel pub converted`. A failed credential check or deployment
retains the imported site for correction. See [credentials and limits](/cli/deploy#cloudflare-pages).
Published rc.1 does not include this provider.

## Ship to Vercel

Current source accepts `zel ship source --out converted --provider vercel
--site prj_YOUR_PROJECT_ID`. It imports the supported source, builds once and
creates a preview. `--prod` explicitly requests production. The imported
configuration saves the provider and project, never the token or production
choice. If credentials, access, rendering or upload fails, the converted site
remains for correction. See [Vercel setup and limits](/cli/deploy#vercel).

## Ship to GitHub Pages

```bash
zel ship source --out converted --provider github-pages --site acme/manual --prod --dry-run
zel ship source --out converted --provider github-pages --site acme/manual --prod
```

Current source supports importing and publishing to an existing GitHub Pages
`gh-pages` branch. Production intent is required before conversion; no preview
exists. The converted site's `zel.yaml` saves the provider and repository, but
never credentials or the production choice. A later publication therefore uses
`zel pub converted --prod`. A dry run performs no conversion or credential/API
work. If delivery fails after conversion, the converted site remains for review
and retry. See [GitHub Pages setup and limits](/cli/deploy#github-pages).

## Ship to S3

```bash
zel ship source --out converted --provider s3 --site acme-docs/manual --prod --dry-run
zel ship source --out converted --provider s3 --site acme-docs/manual --prod
```

Current source can import and upload to an existing S3 website bucket. Production
intent is required before conversion begins, including dry runs. Ship saves the
provider and destination, never credentials or `--prod`. If deployment fails,
the converted site remains; inspect any partial remote upload, then use
`zel pub converted --prod` when ready to retry. See [S3 setup and limits](/cli/deploy#aws-s3).


## Ship to Fly

```bash
zel ship source --out converted --provider fly --site manual --kind next --prod --dry-run
zel ship source --out converted --provider fly --site manual --kind next --prod
```

The conversion writes a configured site with `publish.image: next`, then builds
and deploys using the shared [Fly adapter](/cli/deploy#fly). Missing production
intent or an invalid kind/platform fails before conversion writes. After a
successful import, a build, authentication or rollout failure retains the converted
files; review them and retry with `zel pub converted --prod`. Source content is
unchanged. Use `--kind` for Fly; `--image` selects registry publication and cannot
be combined with a provider. Only amd64 is supported by Fly.


## Ship to Railway

```bash title="terminal"
zel ship source --out converted --provider railway --site 33333333-3333-4333-8333-333333333333 --kind next --tag ghcr.io/acme/manual:v1 --prod --dry-run
```

Remove `--dry-run` after reviewing the plan. Replace the example service UUID
and registry tag, then supply the Railway scope variables, project token and
registry login described in [Railway setup](/cli/deploy#railway). `--kind` defaults
to `static`; `--tag` is required. This deployment mode is distinct from
`--image`, which publishes an image without deploying a provider service.

The import saves `image.name` and Railway `publish` settings, but never
credentials or an implicit production flag. If delivery fails after conversion,
the converted site remains available for review and a later `zel pub converted
--prod`. The original documentation remains unchanged.
