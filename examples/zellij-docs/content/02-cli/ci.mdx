<Callout type="tip" title="Available in source">
`zel ci init github` generates a workflow. `zel ci run` dispatches an
existing workflow. GitLab and CircleCI generators remain planned. This page
describes the current command syntax; installed releases can lag current source.
</Callout>

## Generate a workflow

Run from the software repository root. `--content` is the source folder as the
workflow will see it, relative to that repository. Choose one of these modes:

```bash title="Validate only"
zel ci init github --content content
```

```bash title="Validate and publish a Next.js image to GHCR"
zel ci init github --content content --target image
```

```bash title="Validate, build HTML, and deploy to Netlify"
zel ci init github --content content --deploy netlify --no-provision
```

Each writes `.github/workflows/docs.yml`. An existing workflow is refused
unless `--force` is supplied; that option replaces the file. The current
command does not offer a custom workflow output path or print YAML to stdout.

For the image mode, use hosted Zellij content supported by `image build`.
Netlify mode runs `zel build` and uploads its HTML output using Netlify's CLI;
**it does not call the still-planned `zel deploy` command**. A plain Markdown
input therefore needs a released `zel` containing the native portable builder.
The current generated installer selects the available release rather than
pinning the source checkout used to generate the workflow.

## What the generated workflow does

All modes include validation. The publication mode determines the later work:

| Mode | After validation |
| --- | --- |
| No deployment/image option | Nothing else; no build or publication job |
| `--target image` | Build the Next.js image, authenticate to GHCR, and push it |
| `--deploy netlify` | Build HTML, then upload with Netlify's CLI |

The generated triggers are:

- Pushes to `main` that affect the selected content folder or the workflow file.
- Pull requests that affect those paths.
- Manual dispatch through GitHub Actions or `zel ci run`.

Image and Netlify publication jobs depend on validation and use
`github.event_name != 'pull_request'`. Thus they run on matching pushes and
manual dispatches, while pull requests validate without publication. The
validation-only variant has no publication job.

The image variant targets `ghcr.io/<owner>/<repository>/docs:<commit-sha>` and
requests package-write permission for its job. The current CLI cannot select a
different registry or image architecture during workflow generation.

## Netlify configuration

A Netlify workflow needs a site ID and an authentication token at execution.
`--site` selects the site ID, falling back to `NETLIFY_SITE_ID` in the local
environment. A supplied ID is written into the workflow as a value. If no ID is
supplied with `--no-provision`, the workflow reads the `NETLIFY_SITE_ID` GitHub
secret instead.

Without `--no-provision`, generation requires the site ID, a local
`NETLIFY_AUTH_TOKEN`, and an authenticated `gh` executable. It uploads that token
to the repository's `NETLIFY_AUTH_TOKEN` secret before writing the workflow.

With `--no-provision`, generation writes the workflow without uploading a token.
Arrange the required GitHub secrets separately before running it. This is useful
when generating a workflow for review or when the secrets already exist.

## Generation options

| Option | Current behavior |
| --- | --- |
| `<system>` | Required; only `github` is implemented |
| `--content <path>` | Repository-relative raw hosted content folder; otherwise configured site’s `content/`, then legacy hosted discovery |
| `--target <static\|image>` | Defaults to `static`; `image` adds image publication when no deployment provider is selected |
| `--deploy netlify` | Select Netlify publication; other providers are not implemented |
| `--site <id>` | Netlify site ID; otherwise local `NETLIFY_SITE_ID` |
| `--no-provision` | Generate without uploading the Netlify token |
| `--force` | Replace an existing `.github/workflows/docs.yml` |

Choose either the image publication option or Netlify deployment. The current
parser accepts a target string, but only `image` selects the image workflow;
other strings fall through to validation-only when no deployment is selected.
Use the documented values. `--registry`, `--on`, and `--out` are not supported.

## Run an existing workflow

`zel ci publish` remains an exact compatible spelling of `zel ci run`.

Commit and push the generated workflow before dispatching it. The workflow
must be available on the repository's default branch for manual dispatch.

```bash title="terminal"
zel ci run
zel ci run --workflow docs.yml --ref main
```

| Option | Default |
| --- | --- |
| `--workflow <file>` | `docs.yml` |
| `--ref <branch-or-tag>` | `main` |

This invokes `gh workflow run`; it does not upload the local working directory
or run a local build. The selected remote ref supplies the documentation.
A successful dispatch reports that the workflow was queued, not that its build
or deployment has finished. The workflow's selected mode determines whether it
only validates or also publishes.

If `gh` is unavailable, the current CLI prints an equivalent API request and
returns without dispatching anything. Its successful exit in that case is not
evidence that GitHub started a run.
