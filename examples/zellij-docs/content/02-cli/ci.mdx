## Generate locally

```bash
zel ci
zel ci docs/manual
zel ci --system gitlab
zel ci --system circle
zel ci init github --site-root docs/manual --zel-version 0.2.0-rc.2
```

The first form selects `./zel.yaml`, then `docs/zellij/zel.yaml`, using the usual
site convention. Any custom site-folder name is allowed. The full and short
forms use the same generator. `init`, `run`, and `publish` are reserved actions;
select a folder with one of those names using `./run` or `--site-root run`.
`--cwd` sets the base directory before site and Git discovery. CI retains
`--content` as a legacy selector; it conflicts with `--site-root`, `--config` or a positional
site. For `ci run`, use `--cwd` to select the repository; `--site-root` does not
apply to workflow dispatch.

Use `zel ci --config docs/manual/preview.yaml` to select a named configuration.
The generated workflow passes that same file to check, build and delivery using
a quoted environment value. GitHub change filters cover its folder. The file
must be inside the selected site's Git working tree. `--config` also conflicts
with a positional site and does not apply to `ci run`.

Git locates the repository containing the selected site. The workflow is written
to that repository's CI configuration, including when you run from inside the
site. GitHub is the default and writes `.github/workflows/docs.yml`; GitLab
writes `.gitlab-ci.yml`, and CircleCI writes `.circleci/config.yml`. Paths in the workflow are relative to the Git root. Existing
files require `--force`; symlinks and junctions in the destination are rejected.
Generation requires Git, but no Docker, Node, cloud login or credentials.

## Saved settings

Add CI settings to a versioned `zel.yaml`:

```yaml
version: 1
renderer: portable
name: Product documentation
publish:
  action: deploy
  provider: netlify
  site: your-existing-site-id
ci:
  system: github
  branch: main
  workflow: docs.yml
  zel-version: 0.2.0-rc.2
  triggers: [pull_request, push, manual]
  production: false
```

Then `zel ci` is enough to generate the workflow; use `--force` to replace it.
Regenerate after changing CI or publication settings so the workflow reflects
the selected artifacts, triggers and destinations. `--zel-version` overrides
the saved pin. Candidate 0.2.0-rc.2 supplies its own published version as the
fallback pin. Versions are exact, optionally prefixed with `v`, and may include
release-candidate suffixes. `latest` and versions before 0.2.0 are rejected.
The installer is downloaded from that exact release; it verifies the binary's
checksum and reported version. Engine-backed builds use the matching versioned
`ghcr.io/mylife-inc/zellij-base` image.

`system` accepts `github`, `gitlab` or `circle` (`circleci` is also accepted).
`--system` or `ci init <system>` overrides the saved choice; conflicting explicit
choices are rejected. `branch` is one literal branch name;
`workflow` is a `.yml` or `.yaml` filename, without directories. Unknown settings,
unsupported events and credentials in the CI block are errors.

For multiple GitHub workflows in one repository, choose a different `ci.workflow` filename
for each site. Current source shows that filename in the display name and derives
the concurrency group from it, so separate sites have independent queues. The
earlier `0.2.0-rc.1` generator used one shared display name/group;
candidate `0.2.0-rc.2` includes this fix. Regenerate existing workflows with the corrected CLI
and `--force` after reviewing local customizations.

Optional tag patterns and UTC schedules are independent additional triggers:

```yaml
ci:
  zel-version: 0.2.0-rc.2
  branch: main
  triggers: [pull_request, push, manual]
  tags: ['docs-v*']
  schedules: ['17 3 * * 1']
```

Tags use positive patterns with letters, digits, `/`, `_`, `-`, `.`, `*` or `?`.
Schedules use five numeric cron fields with wildcards, lists, ranges and steps.
GitHub runs schedules from its default branch, so `ci.branch` must match that
branch for scheduled publication. GitHub can delay scheduled runs and does not
evaluate path filters for tag pushes. See the
[GitHub workflow syntax reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
for platform trigger behavior.

## What each run does

The default events are pull requests, pushes to `ci.branch`, and manual dispatch.
Path filters cover the entire selected site, including `zel.yaml` and `content/`,
and the generated workflow itself. A site at the Git root watches all files.

Each run validates with `zel check --strict --deep`, then performs one build:

- Without `publish`, every event builds static HTML without delivering it.
- With saved image publication, pull requests build the selected static or Next
  image. Allowed publication events run `zel publish`, building and pushing once.
- With Netlify delivery, pull requests build static HTML. Allowed publication
  events use the native `zel deploy netlify`, building and uploading once.

Publication is allowed on configured branch pushes, manual runs on that branch,
configured tag pushes, and configured schedules on that branch. Pull requests
never publish; a manual run on another branch validates/builds only. Deployment
credentials are bound only to the publication steps. Runs do not cancel an
in-progress publication when a newer commit arrives.

For image publication, set `publish.action: push`, `publish.image: static` or
`next`, and an explicit remote registry reference in `image.name`. GHCR uses the
job's `GITHUB_TOKEN` with `packages: write`; the account/repository must be allowed
to write that package. Other registries require repository secrets
`REGISTRY_USERNAME` and `REGISTRY_PASSWORD`. The configured tag is used exactly.

For Netlify, set repository secret `NETLIFY_AUTH_TOKEN`. Site ID precedence at
generation is `--site-id` / `--site`, then local `NETLIFY_SITE_ID`, then
`publish.site`. The resolved non-secret ID is written to the workflow. When no
ID is available, execution reads repository variable `NETLIFY_SITE_ID`, falling
back to the same-named secret. Default delivery is a draft preview; set
`ci.production: true` or pass `--prod` to generate production deployments.

## Cloudflare Pages workflows

Current source accepts saved `publish.provider: cloudflare` or
`zel ci --deploy cloudflare --site manual`. The generated workflow requires
`0.2.0-rc.2` or later; generation does not verify release availability, and rc.2
has not yet been published. Set repository secret `CLOUDFLARE_API_TOKEN` and
repository variable `CLOUDFLARE_ACCOUNT_ID` (a same-named secret also works).

Project precedence is `--site`, local `CLOUDFLARE_PAGES_PROJECT_NAME`, then
`publish.site` for the selected provider. The resolved project name is written
to the workflow; otherwise it reads repository variable
`CLOUDFLARE_PAGES_PROJECT_NAME`, falling back to that secret. A provider override
does not inherit a saved Netlify destination. Account IDs are resolved only
when the workflow executes, never copied from the generator's local environment.

The publish step uses `zel deploy cloudflare`. Previews on `zel-preview` are
the default; `--prod` or `ci.production: true` explicitly requests the project's
production branch. Pull requests validate/build without provider credentials.
See [Cloudflare setup and limits](/cli/deploy#cloudflare-pages).

## Provisioning is explicit

Generation writes a local workflow only, even if credentials exist in your shell.
To also upload your environment's provider credentials to the site's GitHub repository:

```bash
zel ci --force --provision
```

This requires a deployment delivery plan and its environment credentials.
Netlify, Cloudflare, Vercel and GitHub Pages use an environment token (`NETLIFY_AUTH_TOKEN`, `CLOUDFLARE_API_TOKEN`, `VERCEL_TOKEN` or
`GITHUB_PAGES_TOKEN`). S3 uses the credential variables described below.
Provisioning requires an authenticated GitHub CLI with permission to set repository secrets. The token is sent to `gh`
over stdin; it is never written into the workflow or passed as an argument.
The workflow is written before the remote operation. If provisioning fails,
the command reports that the file remains and asks you to inspect repository
secrets before retrying an uncertain result. No workflow is dispatched.

`--no-provision` remains accepted and now expresses the default. This changes the
old generator's automatic-provisioning behavior at the new CLI version boundary.

## Compatibility options

`--content` remains an alias for `--site-root`; it accepts a configured site or
an explicit legacy raw-content folder. These overrides remain available:

```bash
zel ci init github --content content --target static --zel-version 0.2.0-rc.2
zel ci init github --content content --target image --zel-version 0.2.0-rc.2
zel ci init github --content content --deploy netlify --zel-version 0.2.0-rc.2
```

`--target static` generates validation and HTML builds with no publication.
On GitHub, legacy `--target image` builds a Next image and pushes
`ghcr.io/<lowercase-owner>/<lowercase-repo>/docs:<commit-sha>`. It uses one image
build followed by pushing that exact tag. Saved settings provide the explicit
static/Next choice for new workflows. `--deploy netlify` chooses native static
site delivery. `--target` and `--deploy` conflict. Provider destination/provision/production
options are rejected for image or build-only workflows.

## Dispatch an existing workflow

```bash
zel ci run
zel ci run --workflow manual.yml --ref main
zel ci publish --workflow manual.yml --ref main
```

Dispatch retains explicit `--workflow` and `--ref` defaults (`docs.yml`, `main`);
it does not read site configuration or regenerate files. If `gh` is unavailable,
the current command prints a manual request example and exits successfully
without dispatching anything. That exit is not evidence of a GitHub run.

`--json` is unsupported for generation and dispatch and fails before work.
Dispatch and credential provisioning remain GitHub-only. Automatic release
publication is separate from CI generation. GitLab/CircleCI generation is available in candidate `0.2.0-rc.2`;
actual GitLab/CircleCI runner acceptance remains pending.


## Image architecture

For image delivery, `zel ci --platform linux/arm64` overrides `image.platform`.
The generated workflow records the resolved selection explicitly in both
verification and publication commands, including the legacy `--target image`
form. `linux/amd64` is also supported; omitting both settings preserves the
runtime default. Static HTML and Netlify CI reject an explicit `--platform` and
ignore saved image architecture settings.

ARM64 image workflows use GitHub's native `ubuntu-24.04-arm` runner for both
jobs; AMD64/default workflows use `ubuntu-latest`. Native ARM64 avoids the
intermittent Node failures observed with QEMU in hosted/Next builds. Generation
does not change the local machine. Hosted/Next builds require an ARM64 variant
of the pinned engine image. To publish both architectures under one tag, use
`--platform all` as described below.


## Freeze rendering features

```bash title="terminal"
zel ci --features all --zel-version 0.2.0-rc.2
zel ci --features none --zel-version 0.2.0-rc.2 --force
```

Generation accepts the same complete selection as build/delivery: `maths`,
`diagrams`, `maths,diagrams`, `all`, or `none`. The selected features are written
explicitly into both verification builds and publication commands, including
Netlify, static/Next images and the legacy `--target image` form. Validation
still runs first. Prebuilt image pushes receive no rendering flag.

This changes the generated workflow, not `zel.yaml`. Once committed, the workflow
keeps that choice until regenerated. Omitting the flag when regenerating removes
the override and resumes saved portable settings or the pinned engine image's
defaults at execution time. `ci run` only dispatches an existing workflow and
does not accept this flag. Compatible native and engine releases must be
published before running the generated workflow; generation does not publish or
verify those releases.

## Publish both image architectures

```bash
zel ci --platform all
```

For saved static/Next image publication or legacy `--target image`, this generates
native AMD64 and ARM64 build jobs. Pull requests verify both architectures without
registry credentials. Authorized publication events build and push each architecture
to a unique staging tag, then a dependent job publishes the final tag from the two
immutable registry digests. A failed build prevents that final publication. No
Node/Next build runs under emulation.

The staging tags use the workflow run ID, attempt and architecture. They remain
in the registry; configure retention for the `zel-` tags if desired. Retries do
not overwrite another run's staging images. Existing event restrictions,
permissions and registry credentials still apply. Build arguments and other
invocation settings reach both native builds, not the final manifest command.

Save `image.platform: all` to use this default, or override it with a single
architecture. Regeneration with the saved/default selection removes temporary
overrides. This mode requires 0.2.0-rc.2 or later; generation does not confirm that
the pinned release exists. Current rc.2 source has not yet been published.

## Freeze hosted URL and preflight overrides

```bash
zel ci docs/hosted --base-path /manual --site-url https://docs.example.com --zel-version 0.2.0-rc.2
zel ci docs/hosted --base-path / --no-check --force
```

The current source writes these invocation settings into every verification
build and publication command, including Netlify and static/Next images. The
workflow retains them until regenerated; `zel.yaml` remains unchanged. Omission
when regenerating restores authored/default settings. Pure portable HTML/static
image workflows reject these flags; portable-to-Next workflows accept them.

`--no-check` removes the workflow's separate deep/strict validation step and
passes the flag to the build or delivery command, skipping its own preflight.
Preparation, schema/rendering checks, runtime detection, credential checks and
publication event gates remain active. Without the flag, the separate check
continues validating authored content before the overridden build.

URL values are serialized as environment data and expanded as quoted arguments.
GitHub expression syntax in these values is rejected rather than evaluated.
The flags require a pinned CLI version of `0.2.0-rc.2` or later and its matching
engine; generation rejects older pins before writing a workflow. Generation
does not verify release availability or publish a release. `ci run` dispatches
an existing workflow and does not accept these generation flags.

## Freeze image build arguments

```bash
zel ci --build-arg NODE_OPTIONS=--max-old-space-size=4096 --zel-version 0.2.0-rc.2
```

For image workflows, current source accepts the same repeatable explicit
`NAME=VALUE` syntax as [image builds](/cli/image#image-build-arguments). The last
value for a repeated name wins. Arguments reach verification builds and
publication builds, including legacy `--target image`; they never reach
`zel check` or a prebuilt image push.

The generator writes the assignments as workflow environment data and references
them using quoted shell arguments. GitHub expressions in values are rejected.
Values are visible in the generated workflow, so do not use secrets. These are
workflow settings, not saved `zel.yaml` fields; regenerate without the flags to
remove them. Static HTML/Netlify workflows reject them before writing, and
`ci run` does not accept generation options. Pins older than `0.2.0-rc.2` are
rejected; the chosen release still needs to be published before execution.

## Vercel workflows

Use saved `publish.provider: vercel` or `zel ci --deploy vercel
--site prj_YOUR_PROJECT_ID`. Generated workflows require a compatible rc.2 or
later release; generation does not check whether that release exists.

Set repository secret `VERCEL_TOKEN`. Set repository variable `VERCEL_TEAM_ID`
for a team project. If the project is not resolved from explicit, environment or
saved settings during generation, set repository variable `VERCEL_PROJECT_ID`.
Same-named secrets are accepted for the two IDs. The publish step runs
`zel deploy vercel`; previews are the default, with `--prod` / saved
`ci.production: true` explicitly selecting production. Pull-request verification
never receives deployment credentials. Explicit `--provision` can copy the local
`VERCEL_TOKEN` into GitHub's secret store after writing the workflow; it does not
create a Vercel project or provision either ID. See [setup and limits](/cli/deploy#vercel).

## GitHub Pages workflows

Use saved `publish.provider: github-pages` or:

```bash
zel ci --deploy github-pages --site acme/manual --prod --zel-version 0.2.0-rc.2
```

Pages branch publishing has no preview mode, so generation requires `--prod` or
saved `ci.production: true`. The source branch must differ from `gh-pages`.
Prepare the existing Pages site and dedicated publishing branch as described in
[GitHub Pages setup](/cli/deploy#github-pages). The generated workflow requires
a compatible rc.2 or later release; it does not verify availability.
Candidate `0.2.0-rc.2` and its matching engine images are published.

Set repository secret `GITHUB_PAGES_TOKEN` to a dedicated token with Contents
and Pages write permission on the destination. The built-in `GITHUB_TOKEN` is
not selected. An explicit, local environment or same-provider saved repository
is written to the workflow; otherwise set repository variable
`GITHUB_PAGES_REPOSITORY` (a same-named secret is also accepted).

Allowed publication events run `zel deploy github-pages --prod`; pull-request
verification builds without receiving deployment credentials. Explicit
`--provision` can save the local `GITHUB_PAGES_TOKEN` as a repository secret
through `gh` after writing the workflow. It does not create/configure the Pages
site or branch. The publication build derives hosted URL defaults from Pages;
ordinary verification builds still use authored or explicit build settings.

## S3 workflows

Use saved `publish.provider: s3` or:

```bash
zel ci --deploy s3 --site acme-docs/manual --prod --zel-version 0.2.0-rc.2
```

Generation requires `--prod` or `ci.production: true` before writing the workflow.
Candidate `0.2.0-rc.2` includes S3 support.
Prepare the [S3 website bucket](/cli/deploy#aws-s3) first.
Set repository secrets `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and, for
temporary credentials, `AWS_SESSION_TOKEN`. Set repository variables `AWS_REGION`
and `S3_EXPECTED_BUCKET_OWNER`; same-named secrets also work.

Destination precedence is `--site`, local `S3_DESTINATION`, then same-provider
`publish.site`. A resolved destination is written literally; otherwise the
workflow reads repository variable `S3_DESTINATION`, falling back to that secret.
Region and owner are resolved only when the workflow runs. Allowed publication
events run `zel deploy s3 --prod`. Pull requests validate/build without AWS
credentials. No IAM role, OIDC federation or bucket configuration is created.
Temporary credentials must still be valid when the workflow executes.

`--provision` explicitly sends both required AWS credential variables and a
nonempty optional session token to GitHub secrets, one at a time over stdin.
All credentials are validated before the workflow is written. Missing session
tokens for temporary access keys fail at that point. A later provisioning failure
leaves the workflow and may have set some secrets; inspect before retrying.
An absent/empty optional session token does not delete an existing repository
secret. When switching to long-lived credentials, clear any stale
`AWS_SESSION_TOKEN` secret yourself. Region, owner and destination are not
provisioned by this option.


## Fly workflows

```bash
zel ci --deploy fly --site manual --kind next --prod --zel-version 0.2.0-rc.2
```

Saved `publish.provider: fly` and `publish.image` also work. `--kind` overrides
that image kind; `static` is the default. Configure repository secret
`FLY_API_TOKEN`, variable `FLY_ORG` (the expected organization slug), and `FLY_APP`
when no app is saved in the workflow. Same-named secrets can supply these variables.
Destination precedence is `--site`, local `FLY_APP`, then same-provider saved site.
`--provision` explicitly uploads the local token through `gh` on stdin after
writing the workflow; it accepts the optional Fly token scheme and never stores
the token in YAML. Without that flag, generation writes only local files.

Pull-request jobs validate and build the selected image without Fly credentials.
Eligible publication events authenticate Docker to Fly's registry using stdin,
run one `zel deploy fly --kind … --prod`, and log out when the step exits. They
use an amd64 runner; an explicit arm64/combined platform is rejected. Normal
feature/build overrides are retained. Production intent is required, either as
`--prod` or `ci.production: true`. See [existing-app requirements](/cli/deploy#fly).

Generation requires a pinned CLI version of rc.2 or later but does not publish
or verify it. Candidate `0.2.0-rc.2` includes Fly deployment; live Fly account
acceptance remains pending.


## Railway workflows

Save Railway delivery settings and `image.name`, then run:

```bash title="terminal"
zel ci --deploy railway --kind next --prod --zel-version 0.2.0-rc.2
```

The workflow uses the saved service UUID, or `RAILWAY_SERVICE_ID` from repository
variables/secrets. Set `RAILWAY_PROJECT_ID`, `RAILWAY_ENVIRONMENT_ID`, and the
`RAILWAY_TOKEN` project-token secret for that environment. `ci --provision` can
store this token through authenticated `gh` explicitly; it does not create the
Railway service or registry credentials.

Pull requests build the selected amd64 image without provider or registry
credentials. Publication events log in to the registry and run one Railway
deployment. GHCR uses `GITHUB_TOKEN` with `packages: write`; other registries use
`REGISTRY_USERNAME` and `REGISTRY_PASSWORD` secrets. Registry login is cleaned up
by the login action. Railway still needs independent pull access: make the image
public or configure supported private registry credentials on the service.

`--kind` overrides saved `publish.image`; `image.name` supplies the exact push
tag. The generated workflow serializes GitHub runs on the same ref, but cannot
lock other workflows, branches, dashboard edits or external deployers. Use one
publisher per service and avoid concurrent changes. Generation is local and
checks neither credentials nor release availability. Candidate `0.2.0-rc.2`
includes this adapter; live Railway account acceptance remains pending.

## GitLab and CircleCI

Candidate `0.2.0-rc.2` includes both generators. Generation remains local: no runner,
project, credential, schedule or registry is created.

```bash
zel ci --system gitlab
zel ci --system circle
zel ci init gitlab --site-root docs/manual
zel ci init circle --site-root docs/manual
```

Save `ci.system: gitlab` or `ci.system: circle` to shorten these to `zel ci`.
The same site selection, explicit `--config`, build overrides, renderer,
static/Next image choice and seven deployment providers apply. Both support
`--target static`. Outside GitHub, legacy `--target image` selects a Next image
and requires an explicit saved `image.name`; it never guesses a GitHub owner.
`--provision` fails before writing a file for these systems. `ci run` always
means GitHub dispatch, regardless of saved `ci.system`.

| System | Default file (`ci.workflow: docs.yml`) | Custom `ci.workflow: manual.yml` |
| --- | --- | --- |
| GitHub | `.github/workflows/docs.yml` | `.github/workflows/manual.yml` |
| GitLab | `.gitlab-ci.yml` | `.gitlab/ci/manual.yml` |
| CircleCI | `.circleci/config.yml` | `.circleci/manual.yml` |

Each file is a **standalone pipeline**. Existing files require `--force`; they
are replaced, not merged. For a custom path, select that configuration path in
your CI project settings. Zellij does not combine several site pipelines into
a shared root configuration. Review any existing CI before replacing it.

These two generators run on all matching events, without path filters.
Pull/merge requests validate and build. Enabled pushes and manual runs publish
only from `ci.branch`; matching tag pushes are also eligible. Positive tag globs
use `*` for any characters except `/`, `?` for one character except `/`, and
`**` across `/`. Tags match the whole name. On GitLab, unprotected eligible refs
only verify; publication additionally requires a protected branch or tag.
CircleCI publication needs the restricted context described below.

When `ci.schedules` is set, generated jobs accept schedule events on `ci.branch`.
**Create the schedule triggers separately in the provider UI/API.** The file
and generation output list the requested UTC cron expressions. GitLab accepts
cron schedules; configure equivalent CircleCI schedule triggers using its
schedule controls. Generation does not translate or provision those remote
schedules. GitLab manual events include web/API/trigger pipelines; CircleCI
manual events mean API-triggered pipelines. Arbitrary webhook, parent/child and
multi-project pipeline events are not enabled.

### GitLab setup

The generated jobs target GitLab.com's native Linux AMD64/ARM64 runners and use
an Ubuntu 24.04 job image. Portable HTML builds need no Docker. Hosted builds,
images and manifest jobs install the Docker client and use a pinned Docker
29.9.3-in-Docker service with TLS. Temporary build folders live under the shared
build directory so container bind mounts see the same files.

For self-managed runners, adjust the runner tags and configure a privileged
Docker executor with shared `/builds` and `/certs/client` volumes. A remote
daemon without those shared paths cannot run Zellij's hosted builds. See
[GitLab's Docker-in-Docker setup](https://docs.gitlab.com/ci/docker/docker_in_docker/)
and [hosted Linux runner requirements](https://docs.gitlab.com/ci/runners/hosted_runners/linux/).

Before enabling publication:

1. Protect the intended publication branch and any allowed release tags.
2. Add provider/registry credentials as masked, **protected** GitLab CI variables.
   Scope them to the exact `zellij/<hash>` environment printed in the generated
   file. Verification jobs have no publication environment.
3. Keep protected-variable access for merge request pipelines disabled. Review
   GitLab's [variable protection settings](https://docs.gitlab.com/ci/variables/).
4. Set the destination and other provider variables in that same environment.

GitLab's built-in job token still exists in verification jobs. The generator
keeps publication logins and deployments out of those jobs; project-level
settings determine which credentials GitLab exposes.

### CircleCI setup

The generated configuration targets **CircleCI Cloud with a GitHub App or GitHub
OAuth integration**. It uses current pipeline event values and native Ubuntu
24.04 machine executors (`medium` / `arm.medium`), where Docker and source files
share the same VM. CircleCI Server and other VCS integrations are outside this
contract. Configure the project's trigger to send pull request events when
`pull_request` verification is wanted. See the
[pipeline event reference](https://circleci.com/docs/guides/orchestrate/pipeline-variables/)
and [ARM executor setup](https://circleci.com/docs/guides/execute/using-arm/).

Create a context named `zellij-publish`, or save another name:

```yaml
ci:
  system: circle
  publish-context: product-docs-publish
  branch: main
```

Put publication credentials and provider scope variables in that context,
**not in project-wide environment variables**. Restrict the context to the
intended project, trusted users and publication refs using CircleCI's context
access controls. Verification jobs never attach it. Workflow filters alone are
not an access policy: someone editing a pipeline could change those filters.
See [CircleCI contexts](https://circleci.com/docs/guides/security/contexts/).

### Publication credentials and combined images

Use the following variable names in the protected GitLab environment or
restricted CircleCI context. Saved destination values take precedence over the
same-named runtime variables. Tokens are never written into the generated file.

| Delivery | Credentials | Destination/scope when not saved |
| --- | --- | --- |
| Registry image | `REGISTRY_USERNAME`, `REGISTRY_PASSWORD` | Explicit `image.name` in `zel.yaml` |
| Netlify | `NETLIFY_AUTH_TOKEN` | `NETLIFY_SITE_ID` |
| Cloudflare Pages | `CLOUDFLARE_API_TOKEN` | `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_PAGES_PROJECT_NAME` |
| Vercel | `VERCEL_TOKEN` | `VERCEL_PROJECT_ID`, optional `VERCEL_TEAM_ID` |
| GitHub Pages | `GITHUB_PAGES_TOKEN` | `GITHUB_PAGES_REPOSITORY` |
| S3 | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional `AWS_SESSION_TOKEN` | `S3_DESTINATION`, `AWS_REGION`, `S3_EXPECTED_BUCKET_OWNER` |
| Fly | `FLY_API_TOKEN` | `FLY_APP`, `FLY_ORG` |
| Railway | `RAILWAY_TOKEN` plus registry credentials | `RAILWAY_PROJECT_ID`, `RAILWAY_ENVIRONMENT_ID`, `RAILWAY_SERVICE_ID`; saved `image.name` |

GHCR also requires registry credentials on these systems. GitLab can use its
built-in registry user/password only when `image.name` targets that project's
`CI_REGISTRY` host and neither custom registry credential is set. A partial
custom credential pair fails instead of silently falling back.

Fly logs in to `registry.fly.io` using its API token. Railway needs independent
permission to pull the pushed image, as described in [deployment setup](/cli/deploy#railway).
GitHub Pages, S3, Fly and Railway still require `--prod` or `ci.production: true`.
Other providers retain draft-by-default behavior.

For registry publication with `image.platform: all`, both generators build
AMD64 and ARM64 images on native runners. Each job pushes a unique staging tag
and records a validated immutable digest. The final job requires both successful
builds, validates their receipts, and publishes the combined tag. It does not
rebuild either image. Single-target publication and manifest updates use a queue
identified by the configuration filename. Different files have independent queues.
GitLab receipts use job artifacts; CircleCI uses workflow workspaces. If a
CircleCI rerun conflicts with an existing workspace receipt, start a new
pipeline. Staging registry tags are retained for your registry retention policy.

Local tests execute generated scripts with fake tools. GitHub-hosted acceptance
replays their image publication and manifest commands against a disposable
registry on native Linux architectures. Live runs on actual GitLab and CircleCI
projects remain a separate acceptance step; account access is needed for those.
