## One manuscript, one reading order

Put a `book` block in a portable site's `zel.yaml`. Keep Markdown and assets in
`content/`; build output stays in its sibling `site/` folder. The site folder
can have any name. Existing commands remain short:

```sh
zel check my-book --strict
zel check my-book --json
zel build my-book
zel view my-book
```

From inside `my-book`, omit the path. From a product repository, bare commands
also recognize `docs/zellij/zel.yaml`. `view` builds, starts the local server,
and opens the browser with its existing options. You can also double-click
`site/index.html`; no server is required to read the complete portable book.

```yaml title="my-book/zel.yaml"
version: 1
renderer: portable
book:
  version: 1
  title: The art of noticing
  subtitle: A field guide to attention
  authors: [Mira Vale]
  language: en
  direction: ltr
  cover:
    image: assets/cover.svg
    alt: Concentric circles on an ivory book cover
  front-matter:
    - {id: preface, source: preface.md}
  chapters:
    - id: attention
      title: Part I · Attention
      chapters:
        - {id: noticing, source: chapters/noticing.md}
        - {id: questions, source: chapters/questions.md, title: Better questions}
    - {id: practice, source: practice.md}
  appendices:
    - {id: field-notes, source: notes.md}
```

The `book` version is the integer `1`, independent of the outer site version.
Title and one to sixteen author names are required. Subtitle, cover, front
matter and appendices are optional. A part contains a nonempty list of chapters;
parts cannot nest. There must be at least one chapter. The limit is 1,024 listed
reading entries, plus the automatic title page.

Every part and reading entry has a unique ID, starting with a lowercase ASCII
letter and containing at most 64 lowercase letters, digits, hyphens or
underscores. `title-page` is reserved. IDs identify entries in the publication
record; web URLs continue to follow source filenames. Renaming an ID does not
rename its URL, and renaming a file changes its URL.

## Title page, chapters and appendices

The root home document (`index.md`, or `README.md` when no index exists) becomes
the title page automatically. Do not list it in the manifest. If you omit it,
Zellij creates a title page with the book title, subtitle, authors, cover and
contents. If you author a home document, its body remains yours: include your
own cover and credits there. The manifest's metadata and cover are still
validated and exported.

Front matter is unnumbered. Chapters are numbered continuously across parts;
appendices use A, B, … Z, AA, and so on. Sidebar, contents and previous/next links
follow the manifest, independent of alphabetical filenames or Markdown `order`.
An entry's optional `title` changes its navigation/publication label; it does
not rewrite the Markdown heading or body.

All discovered Markdown must be listed, apart from the automatic title page.
Unlisted chapters fail validation; keep drafts outside `content/`. Sources are
literal paths relative to `content/`, including their `.md` or `.markdown`
extension. They must exist and cannot escape that directory. Repeated IDs or
sources, missing chapters, `nav` together with `book`, unknown book fields,
unsafe assets and output collisions fail before replacing the last export.
There is no separate book-specific overwrite mode.

The paper theme is the book default. Set ordinary `theme` or use `--theme` to
choose another theme. A separate site `name` controls the header; without one,
the book title is used. Existing company/product branding, Markdown features,
local fonts, search and offline navigation continue to work.

## Numbered equations and cross-references (current source)

<Callout type="info" title="After rc.6">
Shared equation numbering is implemented in current source and awaits the next
CLI candidate. Use a matching engine build for Next images. Published rc.6
continues to support its earlier unnumbered print-math subset.
</Callout>

Enable `markdown: {math: true}` beside the `book` block in `zel.yaml`. Label a
display expression with one top-level LaTeX-style `\label`:

```md
$$E=mc^2\label{eq:energy}$$

See Equation $\eqref{eq:energy}$.
```

The first labelled equation in chapter 2 is `(2.1)`. Unlabelled math remains
unnumbered and does not consume a number. Chapters use their manifest order,
appendices use `A.1`, `B.1`, etc.; front-matter entries use `F1.1`, `F2.1`, etc.
An authored title page uses `T.1`. Each entry restarts its equation counter.
For a multi-line equation with one number, use `aligned` or `gathered` inside
one display expression, then put its label outside that environment.

`$\eqref{eq:energy}$` becomes a link displaying `(2.1)`; `$\ref{eq:energy}$`
displays `2.1`. References can point forward, backward or to another chapter,
including from a footnote. Put each reference in its own inline expression in
prose, not inside a heading, another link or a larger mathematical expression.
The same resolved numbers and targets serve native HTML, adapted Next images
and the optional LuaLaTeX PDF. Website reference links also work after moving
an export and opening it with `file://`, with JavaScript disabled.

Labels are unique across the book, case-sensitive, start with an ASCII letter,
and contain at most 128 ASCII letters, digits, `:`, `.`, `_` or `-`. The anchor
`_zel-eq-eq:energy` follows the label rather than its number. Inserting an earlier
equation renumbers it without changing its anchor. A Markdown link can use
custom text, for example `[Energy relation](chapter.md#_zel-eq-eq:energy)`.
Renaming the label or source file changes its target.

Duplicate/missing labels, empty labelled math and unsupported placements fail
`zel check` and publication before replacing existing output. Book authors use
labels instead of manual `\tag`, `\notag`, `\nonumber` or `equation`/`align`
numbering environments. This first shared syntax assigns one number per labelled
display expression; per-row numbering, references within larger math, custom
tags remain future increments. Non-book expression-local
math behavior is unchanged.

When equations exist, the publication record adds `equations` to schema version
1. Each item supplies `id`, `number`, reading-entry ID in `entry`, `source`,
`anchor` and encoded root-relative `href`. This field is omitted for books with
no labelled equations. The Next sidecar keeps those portable hrefs; its `routes`
map supplies hosted entry paths, and deployment base paths apply as usual.

## Theorems, lemmas and proofs (current source)

<Callout type="info" title="After rc.6">
Shared statement numbering and references are implemented in current source and
await the next candidate. Use a matching engine build for Next images.
</Callout>

Write a top-level Markdown blockquote with a marker, stable label, optional
plain text title, then a blank quoted line before its body:

```md
> [!LEMMA] {#lem:square} A square is nonnegative
>
> For real $x$, we have $x^2\geq 0$.

> [!THEOREM] {#thm:energy} Energy and equality
>
> The energy is nonnegative when the mass is positive.

> [!PROOF] {#proof:energy}
>
> Apply $\autoref{lem:square}$ and multiply by the positive mass.
> This proves $\autoref{thm:energy}$.
```

Supported markers are `THEOREM`, `LEMMA`, `PROPOSITION`, `COROLLARY`, `DEFINITION`,
`EXAMPLE`, `REMARK` and `PROOF`. Every block needs a `{#id}`, including proofs.
Titles are plain text on one line. Bodies accept normal Markdown formatting,
lists, code, ordinary nested quotes, math and footnote references. Put footnote
definitions outside the block. Semantic blocks must be top-level; nesting them
inside other quotes, lists or footnotes is unsupported, as are headings inside
their bodies. Leave a blank quoted line between the metadata and body.

Numbered kinds share one counter per reading entry. In the first chapter the
example above becomes **Lemma 1.1**, **Theorem 1.2**, then **Proof** with an end
mark. Proofs remain unnumbered and do not consume a number. Equations have their
own counter. Appendices use `A.1`, front matter uses `F1.1`, and an authored title
page uses `T.1`, following the same reading order as equations.

Enable `markdown: {math: true}` for math and LaTeX-style references:

- `$\ref{thm:energy}$` displays a linked `1.2`.
- `$\autoref{thm:energy}$` displays a linked `Theorem 1.2`.
- `$\autoref{proof:energy}$` displays a linked `Proof`.
- `$\autoref{eq:energy}$` displays a linked `Equation 1.1`.

`\eqref` accepts only equations; `\ref` cannot number a proof. Put references
in their own inline expression in prose, outside headings and other links.
Labels must be unique across both equations and statements. Forward and
cross-chapter references resolve before output is written. Native HTML, Next
and PDF use the same numbers, headings and link targets.

Statement blocks without math need no math feature. Custom Markdown links such
as `[Read the argument](chapter.md#_zel-stmt-thm:energy)` also work without it.
Stable anchors follow labels, not numbers, and continue to work after adding
an earlier block. Renaming a label or file changes its target.

The publication record adds an optional `statements` array to schema version 1.
Each item contains `id`, lowercase `kind`, optional `number` and `title`, reading
entry ID in `entry`, `source`, `anchor` and encoded root-relative `href`. Proofs
omit `number`; books without blocks omit `statements`. Invalid metadata, duplicate
or missing labels and unsupported placements fail checks/builds before replacing
existing output. Ordinary non-book blockquotes and authored MDX `<Theorem>`
components retain their existing behavior.

## Bibliography and citations

<Callout type="info" title="Current source after rc.6">
The numeric bibliography described here is implemented in current source and
will ship in the next candidate. It is not included in the rc.6 binary.
</Callout>

Save a local CSL-JSON reference catalog under `content/` and configure it in
`zel.yaml`:

```yaml
book:
  # Keep the book's existing title, authors and chapters here.
  bibliography:
    source: references.json
    title: Bibliography
    include-uncited: false
```

`source` is relative to `content/`, stays within that directory, and must be a
regular `.json` file. `title` is optional; its default is `Bibliography`.
`include-uncited` defaults to `false`. Set it to `true` to append unused catalog
entries in catalog order after the cited entries.

A minimal `content/references.json` contains an array of reference objects:

```json
[
  {
    "id": "vale2024",
    "type": "book",
    "title": "An atlas of quiet ideas",
    "author": [{"given": "Mira", "family": "Vale"}],
    "issued": {"date-parts": [[2024]]},
    "publisher": "Example Press",
    "URL": "https://example.com/atlas"
  }
]
```

This is an illustrative reference. Cite a real catalog entry in ordinary prose,
lists, tables, statement bodies or footnotes:

```md
Read the introduction [@vale2024].
Compare the sources [@vale2024, pp. 12–14; @other-key, chapter 2].
```

Each reference gets a number at its first citation in the book's reading order.
Footnotes are visited where first referenced. Repeated citations reuse that
number. A cluster preserves its authored order, for example `[1, pp. 12–14; 2,
chapter 2]`; each number links to the corresponding bibliography entry. No math
feature, JavaScript, container or citation service is required for HTML builds.

Markers must fit on one line, with at most 32 references and a 256-byte plain
text locator per reference. IDs are case-sensitive: 1–128 ASCII letters, digits,
colons, dots, underscores or hyphens, starting with a letter, digit or underscore.
CSL integer IDs also work (`[@123]`). If an exported record has an inconvenient
ID, add a `citation-key` field and cite that alias; the original ID remains in
`source_id` in the publication record. Aliases must be unique.

Inline/fenced code and escaped brackets (`\[@literal]`) remain literal. Markers
inside existing Markdown link labels and image alt text also remain literal.
Citation markers cannot supply heading text or act as Markdown reference-link
or image definitions. Bare `@id`, author-in-text citations, automatic locator
translation, BibTeX input and user-selected CSL styles are not implemented.
Ordinary non-book Markdown is unchanged.

The generated `bibliography.html` follows the appendices in navigation and PDF
reading order. Reserve that route; do not author a `bibliography.md` page.
References also appear in search. Stable `_zel-bib-ID` anchors survive renumbering;
custom links such as `[Reference](bibliography.html#_zel-bib-vale2024)` work too.
The generated page participates in prefixed Next images and the PDF table of
contents. HTML, Next and PDF share the same reference text, numbers and targets.

The built-in numeric presentation uses `id`, `type` and `title` (required), plus
optional `author`, `issued`, `container-title`, `publisher`, `publisher-place`,
`volume`, `issue`, `page`, `DOI` and `URL`. Author names support `literal`, or
`family` with optional `given`, particles and `suffix`. Dates show the year or
year range from `date-parts`, or an explicit `literal`/`raw` date; absent dates
show `n.d.`. Volume, issue and page fields accept strings or numbers. Metadata
is plain text, including any HTML or TeX-looking content. Other CSL fields are
not displayed by this presentation. This is a bounded reader of
[CSL-JSON data](https://github.com/citation-style-language/schema/blob/master/schemas/input/csl-data.json),
not a complete CSL style processor or a claim of APA/Chicago compliance.

DOIs must be identifiers such as `10.1234/example`; their links take precedence
over `URL`. URLs must be absolute HTTP(S) addresses without credentials. Neither
is fetched during a build. Catalogs support up to 10,000 entries and 8 MiB.
The raw catalog is not copied into the website unless explicitly linked as an
asset. Catalog bytes contribute to the book's content revision, including
uncited metadata, so an edited source cannot leave a stale downloadable PDF.

Missing references, duplicate IDs, malformed metadata, unsafe paths and route
collisions fail before publishing output. A failed build retains the previous
complete website/PDF. Bibliography details are exposed in the optional
`bibliography` field of publication schema version 1; books without this setting
omit that field and keep their existing revision behavior.

## Glossary and index

<Callout type="info">
These features are implemented in current source and await the next CLI
candidate. Public rc.6 does not yet include them.
</Callout>

Enable either catalog, or both, inside the existing book manifest:

```yaml
book:
  # Keep the existing title, authors and chapters.
  glossary: {source: glossary.json, title: Glossary}
  index: {source: index.json, title: Index}
```

Both sources are local JSON files relative to `content/`. The optional titles
default to `Glossary` and `Index`. A glossary catalog contains definitions:

```json
[
  {
    "id": "energy",
    "term": "Energy",
    "definition": "The capacity to do work.",
    "see-also": ["sum"]
  },
  {"id": "sum", "term": "Finite sum", "definition": "A finite addition.", "sort": "sum"}
]
```

An index catalog describes subjects and optional subentries:

```json
[
  {"id": "mechanics", "term": "Mechanics", "see-also": ["sum"]},
  {"id": "energy", "term": "Energy", "parent": "mechanics"},
  {"id": "sum", "term": "Finite sums", "sort": "sums"}
]
```

Mark occurrences with ordinary Markdown link syntax:

```md
Read the [energy](glossary:energy) definition.
This passage discusses [energy](index:energy).
A note can also refer to a [finite sum](glossary:sum).
```

The link's label stays as written; its destination becomes a real relative HTML
link or PDF link. Code examples stay literal. Use plain text or inline code in
term labels; rich formatting, images, headings and empty labels are rejected.
The `glossary:` and `index:` forms require a book and their corresponding catalog.
They accept exactly an ID, without a URL query or fragment.

`id` is case-sensitive: 1–128 ASCII letters, digits, colons, dots, underscores or
hyphens, starting with a letter, digit or underscore. Each catalog has its own
ID namespace. `term` is the displayed name (at most 512 bytes). Glossary entries
require `definition` (at most 16,384 bytes); index entries do not take it.
Definitions and other catalog text are plain data, with no Markdown, HTML or TeX
execution. All text must be nonempty and contain no control characters.

`sort` optionally supplies a 512-byte sorting key. Entries sort by the lowercase
key, then exact ID; the default key is `term`. This is deterministic Unicode
ordering, not locale-aware dictionary collation. Index `parent` identifies a
different top-level entry in the same catalog; one subentry level is supported.
Children follow their parent in sorted order. Glossary entries do not take a
parent. `see-also` lists up to 32 distinct other IDs in the same catalog; it
creates links and does not register a manuscript occurrence.

The glossary and index follow the appendices and any bibliography in navigation,
search and PDF contents. Their routes are `glossary.html` and `book-index.html`;
`index.html` remains the book's home page. These routes and the reading IDs
`glossary`/`index` are reserved while enabled. Every catalog entry is included,
even when unused; an unused entry says “No occurrences.”

Web entries link back to each marked occurrence, with its chapter title and
occurrence number. PDF entries show linked page references, combining repeated
mentions on the same page into one page reference. Footnotes are visited at their
first call site, independently of where their definitions appear in Markdown.
The existing PDF rule rejecting unreferenced footnotes still applies.

Term anchors are `_zel-glossary-ID` and `_zel-index-ID`. Occurrence anchors use
`_zel-use-KIND-ID-N` within their source page, where `N` counts that term's markers
in source order on that page. Adding a different term does not renumber these
anchors; inserting another occurrence of the same term can. Normal custom links
can use these anchors too. Markdown reference-link IDs beginning `_zel-use-`
are reserved for generated occurrence identity.

Catalogs are limited to 8 MiB and 10,000 entries each, and a book supports up to
100,000 marked occurrences. Files must remain inside `content/` and outside
hidden/generated paths; symlinks and junctions are rejected. Catalogs are not
published as assets unless explicitly linked. Their bytes contribute to the
publication revision, so editing a definition or sorting key invalidates an old
PDF. `zel check --json` and `_zellij/book.json` expose resolved collections in
optional `terms`, including stable links and occurrence records. Books without
these settings omit the new fields and retain their previous revision behavior.

No new CLI command, browser script, MakeIndex, glossary tool or PDF container
package is required. Unknown fields, undefined IDs, duplicate IDs, subentry
cycles and route collisions fail validation before replacing output. Deeper
index hierarchies, automatic indexing, page-range compression, localized
collation and rich glossary definitions remain separate extensions.

## Language and direction

`language` defaults to `en`; `direction` defaults to `ltr` and can be `rtl`.
These set the HTML content language and writing direction, including in adapted
Next images. Portable layout uses logical inline edges. They do not translate
interface labels such as “Chapter” and “Search”, select additional font packs,
or promise complete typesetting support for every language. Verify the glyphs
needed by your manuscript; the bundled fonts do not cover every script.

The supported language syntax is 2–8 ASCII letters, optionally followed by
hyphen-separated 1–8 character alphanumeric subtags, with at most 63 characters
in total (for example `en`, `fr-CA`, `zh-Hans`). Validation checks this syntax,
not the IANA language registry. Hosted `content/site.yaml` also accepts these
`language` and `direction` fields independently of a book manifest.

## Inspect the publication

On successful compilation, `zel check --json` includes a `book` object. Builds
write the same object to `site/_zellij/book.json`. Non-book and failed compilation
reports omit this optional field. Existing report fields and exit codes remain
unchanged; strict warning failures may still contain a compiled book.

The record contains `schema_version: 1`, the normalized manifest, a `revision`,
and ordered `entries`. Each entry records its `id`, `kind`, optional `number`
and part ID, title, source and encoded root-relative HTML `href`. The automatic
title page has a null source when synthesized. The complete manifest retains
part titles and the cover description.

The `sha256:` revision identifies the canonical manifest, ordered original
Markdown bytes and referenced local assets, including branding. Moving the
source/output, reformatting equivalent YAML, or changing a theme/name override
does not change it. Editing metadata, Markdown or an included asset does. It is
a content identity, not a signature or a guarantee of identical layout across
engine versions and feature settings.

`zel ni my-book` adapts the book to the Next image renderer, preserving metadata,
reading order, chapter markers and title-page content. Its public
`/_zellij/assets/book.json` contains `publication` (the same portable record) and
`routes` (entry IDs mapped to hosted routes). Apply the deployment's configured
`basePath` to both this URL and the mapped routes: the map contains unprefixed
content routes, not complete deployment URLs. Its portable `href` fields are not
hosted route declarations. Use the matching rc.6 engine image or later. Native
portable web builds require no external renderer.

## Start from the existing book template

With rc.6 or later:

```sh
zel create my-book -t book-classic --name "A question worth following" --set author="A. Writer"
zel build my-book
zel pdf my-book --check
zel build my-book --pdf
```

Book-classic 0.2.0 creates a ready-to-edit manifest, preface, part, two chapters,
appendix and original PNG cover. The title page and table of contents are
generated from the manifest. PDF is off by default; the last command explicitly
uses the optional LuaLaTeX toolchain in a supported container runtime. Edit `book` and `pdf` settings in
`zel.yaml`, then replace the sample prose and cover under `content/`.

The earlier 0.1.0 starter shipped with rc.5 remains immutable. To migrate an
existing copy, use a compatible CLI and replace its `nav` block with a `book`
manifest listing its preface and chapter files; leave its authored `index.md`
unlisted. Creating a new template never overwrites an existing manuscript.

## Optional PDF export

The first print adapter produces an English/LTR book through LuaLaTeX, with A5 as the default paper size:

```sh
zel pdf my-book --check          # Native compatibility check; no files or runtime
zel build my-book --pdf          # Website and PDF, published together
zel pdf my-book                  # PDF only, in my-book/pdf/
zel export pdf my-book --out printed-book
```

The same conventional site discovery and global `--cwd`, `--site-root` and
`--config` selectors apply. `--out` names an output **directory**, protected by
Zellij's existing output ownership rules. Standalone export leaves the website
alone. PDF generation is off by default. Set `pdf.enabled: true` to include it
in ordinary portable builds, or select it for one invocation with `--pdf`.
`--no-pdf` overrides the saved choice and removes a previous PDF and its download
links together. The two flags cannot be combined.

`build --pdf` places the verified PDF at `site/_zellij/pdf/book.pdf` and adds a
relative download link to every reading page. The link also works with a relocated
`file://` website. Its directory includes generated `book.tex`, copied print
images, `build.log`, `publication.json` and `pdf.json`. These are public export
artifacts. The receipt identifies the manuscript revision, PDF SHA-256, template
print settings and exact toolchain image. The website's publication record and PDF receipt use
the same source snapshot. The hash does not promise byte-identical PDFs between
builds: PDF timestamps and toolchain details can differ.

### Saved print settings and previews

The following top-level block belongs in a versioned portable book's `zel.yaml`:

```yaml
pdf:
  enabled: true
  paper: a5
  font-size: 11
```

`enabled` defaults to `false`, `paper` to `a5`, and `font-size` to `11`.
Paper may be `a5`, `a4` or `letter`; font size is the integer `10`, `11` or `12`
(points). Settings are validated even when PDF is disabled. Unknown keys,
unsupported values, null settings, hosted sites and missing book manifests fail
validation. The classic template still controls margins, fonts and chapter styling;
custom templates and RTL print remain future work. Standalone `zel pdf` explicitly
requests export regardless of `enabled`, using the same paper and font settings.

```sh
zel build my-book                 # Uses pdf.enabled
zel build my-book --no-pdf        # Web only for this invocation
zel view my-book --watch          # Rebuilds configured web and PDF together
zel view my-book --watch --no-pdf  # Faster web-only authoring session
zel dev my-book --pdf             # Watches with PDF enabled for this session
```

Preview overrides last for the whole session. Without an override, changing
`pdf.enabled` takes effect on the next rebuild. A failed PDF build preserves the
last complete website and PDF. Changes made during typesetting discard that
outdated build; watch mode retries the new content. Ctrl-C cancels the typesetter
and cleans up its container. `serve` only serves the existing export and never
runs a PDF toolchain.

### Static publication and CI

Static deployment commands and `zel si` / `zel image static` honor `pdf.enabled`.
They generate the matching PDF before upload or image packaging; typesetting
failure prevents delivery. The generated static image contains the export and
HTTP server, without the LaTeX toolchain. PDF-enabled Next image delivery is not
implemented: select a static image, or explicitly disable PDF in the configuration
for a web-only Next image. Deployment dry runs report the PDF requirement without
checking credentials or starting a runtime.

Generated GitHub, GitLab and CircleCI jobs inherit the saved PDF settings.
GitHub and CircleCI use their existing Linux machine runners; GitLab enables its
Docker service and shared build directory even for a portable PDF build. Runner
setup must allow the CLI and runtime to bind the same temporary paths.
Any explicit `pdf` settings require a CLI pin of **0.2.0-rc.6 or later**.
Generate the workflow with `--zel-version 0.2.0-rc.6` to select this published
candidate. Earlier binaries do not support these settings.

### Toolchain and failure behavior

A running Docker, Podman or nerdctl **Linux** runtime is required only when
actually generating a PDF. Missing or conflicting runtimes produce an actionable
error; Zellij does not install or start one. The separate official
[Pandoc LaTeX Ubuntu image](https://github.com/pandoc/dockerfiles) is pinned by
multi-platform digest and supplies LuaLaTeX and Latin Modern fonts.
The adapter emits TeX directly; it does not ask Pandoc to reinterpret Markdown.
This optional image adds no TeX dependencies to the CLI or normal website images.
First use may download it; subsequent builds can use the cached image offline.

Rootless runtimes must also support the CPU, memory and process limits used by
the PDF container. A successful `podman info` alone does not establish this:
missing delegated cgroup controllers can still prevent typesetting. See
[Podman's resource-limit requirements](https://docs.podman.io/en/stable/markdown/podman-run.1.html#cpus-number).
If several runtimes are installed, select the configured endpoint explicitly
(for example, `DOCKER_CONTEXT=default zel build my-book --pdf` for the default
Docker context). Zellij preserves the previous output if the runtime rejects
the PDF container; it does not silently remove its resource limits.

Typesetting runs with network disabled, a read-only container root, dropped
capabilities, no privilege escalation, resource limits and shell escape disabled.
Only staged print inputs and a disposable output directory are mounted. The
source project, credentials and container socket are not mounted. A bounded runtime
query selects the correct user identity for rootful or rootless containers;
unknown mappings fail before typesetting. The per-container user namespace is
explicit so custom runtime defaults cannot silently remap the staged files. Runtime calls
are bounded; cancellation and timeout remove the named container. Remote runtimes
must support the same shared local bind paths as other Zellij container commands.

Three LuaLaTeX passes resolve contents and references. Missing glyphs, unresolved
references, significant layout overflow, nonzero exits and invalid/missing PDFs
fail publication. The last complete output is retained. `pdf --check` checks the
adapter's content contract; only actual typesetting can establish layout, fonts
and successful PDF generation.

### First print template and current boundaries

The classic print template provides a title page, optional cover, paginated
contents, parts, chapters, appendices, running headings, page numbers and PDF
bookmarks. The adapter supports ordinary paragraphs, emphasis, lists, code,
quotes, footnotes, tables of up to six columns, the existing validated math
subset, local PNG/JPEG images and links between book pages/headings. Code and
ordinary text are escaped; authored HTML remains literal. Repeated footnote
references share their number; unreferenced definitions are rejected. The printed cover is followed by contents and
any authored home document; its body remains part of the publication. Current
source starts that authored home content on a separate page after the contents.

This first template supports English/LTR and Latin Modern fonts. SVG, WebP,
GIF, remote images, diagram fences, attachment links and internal-link URL queries
are rejected for print with an explanation; ordinary web builds retain their existing support.
Use local PNG/JPEG artwork and static diagram equivalents when requesting PDF.
Complex/nested tables, custom TeX templates, arbitrary raw TeX, user-selected
trim sizes and multilingual/RTL print remain future increments.
Current source adds glossary/index backmatter, shared equations, statement blocks, numeric bibliography
and citations as described above; rc.6 does not include them.
Mathematical expressions otherwise use the web renderer's supported subset.
