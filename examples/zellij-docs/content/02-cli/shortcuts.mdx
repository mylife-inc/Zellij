These shortcuts are available in candidate `0.2.0-rc.1`;
stable `0.1.3` predates them. Run `zel --help` to see what
your installed binary supports.

```bash title="From your software repository"
zel init                  # new portable: docs/zellij/zel.yaml and content/
zel c --strict            # check
zel b                     # build into docs/zellij/site/
zel v --watch             # build, serve, open, and rebuild after edits
```

To serve an existing export without building, use `zel s`. To select a custom
site, use `zel b docs/manual` or the same path with `c`, `s`, or `v`.
The global selectors work with full names and shortcuts alike:

```bash
zel --cwd ../my-product b --site-root docs/manual
zel --site-root docs/manual c --cwd ../my-product --strict
zel b --config docs/manual/preview.yaml
```

See [working-directory and site selection](/cli/config#working-directory-and-site-selection)
for precedence and conflicts.

Current source also supports `zel nd --full` for a complete section example site,
`zel ns -i` for guided section authoring, and
`zel ns hero --set 'headline=Hello'` for scripts. See [section authoring](/cli/new#interactive-authoring).
These additions require a newer native release than rc.1.

## Finding options

```bash
zel init --help
zel new portable --help
zel b --help
zel --json themes
zel c --json --strict
```

Help connects the full form and shortcut. [Shell completions](/cli/completions)
include both. Shortcuts are built into the binary and work on Linux, macOS,
and Windows without shell aliases. Arbitrary prefixes such as `zel bu` are not
commands; use `zel build` or `zel b`.

Names used as arguments keep their meaning. For example, `zel b init` builds a
folder named `init`; it does not create a new site. Use `--` before positional
paths that begin with a hyphen, such as `zel b -- -manual`.

## Scope

Shortcuts do not add capabilities to their underlying commands. `cv` still
uses raw hosted-content output by default, with `--layout site` available; `v`
previews portable or hosted static output. `si` builds a static-site image and `ni` builds a Next.js
image from either renderer;
`idf --kind static` prints its recipe, and the default `idf` retains the Next.js
recipe. `si`, `ni`, `ir`, and `ip` require a usable container runtime.

`pub` executes a saved image push or static deployment; `pub --dry-run` only
resolves the plan. `netlify` builds and uploads static HTML, with a draft preview
by default and `--prod` for live publication.

`zel ci [site]` uses saved `ci.system` (GitHub by default). For GitHub it is
equivalent to `zel ci init github --site-root <site>`, using saved settings. It writes local files by default; `--provision`
explicitly uploads the selected provider's token. See [CI](/cli/ci) for the compatible release
pin required while the current public binary is older than this contract.
`na` creates editable hosted wrappers with a built local engine package; see
[`zel new app`](/cli/new#zel-new-app-dir) for content selection and prerequisites.

Conversion shortcuts preserve the legacy raw-content default. Add `--layout site`
to `zel cv` or `zel mig` for `zel.yaml` plus `content/`. `zel ship` always uses
that configured layout and requires `--out` plus an explicit delivery destination.

## Cloudflare Pages shortcut

Current source adds `zel cf [site] --site manual` as the short form of
`zel deploy cloudflare [site] --site manual`. `zel cloudflare` is also accepted.
With a saved Cloudflare destination, `zel pub` needs no provider or project
argument. Preview is the default; production requires `--prod`. See
[setup and limits](/cli/deploy#cloudflare-pages). These forms are newer than rc.1.

## Vercel shortcut

`zel vc [site] --site prj_YOUR_PROJECT_ID` is equivalent to
`zel deploy vercel [site] --site prj_YOUR_PROJECT_ID`. `zel vercel` also works.
With a saved Vercel destination, `zel pub` needs no provider or project argument.
Previews are the default; `--prod` is explicit. See [setup](/cli/deploy#vercel).
These forms are newer than the published rc.1 binary.

## GitHub Pages shortcut

Current source provides `zel ghp` and `zel github-pages` for `zel deploy github-pages`.
For example, `zel ghp --site acme/manual --prod`; with a saved destination, use
`zel ghp --prod`. Dry-run plans also require `--prod`: Pages branch publishing has
no draft mode. See [setup and limits](/cli/deploy#github-pages).

## S3 shortcut

Current source provides `zel s3` for `zel deploy s3`. Use
`zel s3 --site acme-docs/manual --prod`, or `zel s3 --prod` with a saved destination.
Dry-run plans also require `--prod`: S3 uploads have no draft mode.
See [setup and upload behavior](/cli/deploy#aws-s3).
