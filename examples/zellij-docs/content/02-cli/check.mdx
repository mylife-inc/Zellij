<Callout type="tip" title="Available">
Portable Markdown checks run natively without Node, Docker, or network access.
Hosted YAML/MDX checks use the engine in a container with the content mounted read-only.
</Callout>

```bash title="terminal"
zel check
zel check ./docs --strict --json
zel check ./content --target static --deep --strict
```

## Choosing the checker

`check` uses the same automatic target selection as `build`: a `zel.yaml` entry
in the requested directory selects portable Markdown; otherwise recognized
structured content selects the hosted checker; otherwise the requested directory
is checked as portable Markdown. A malformed `zel.yaml` reports an error.

Use `--target portable` or `--target static` to choose explicitly. Here, `static`
means the hosted YAML/MDX checker; `image` is not a check target. With no directory
argument, the requested directory is `.`. Portable checks use that exact root.
Hosted discovery follows the rules described below.

## Native Markdown checks

```bash title="terminal"
zel check ./docs --target portable
zel check ./docs --strict
zel check ./docs --json > check-report.json
```

The native checker runs the portable build's compiler entirely in memory. It
reads optional [zel.yaml](/cli/config), discovers documents, parses Markdown and
front matter, resolves navigation and local references, and renders the site.
It checks image/download paths, heading and footnote fragments, and portable
output filename collisions. Hidden paths and `node_modules` cannot supply
published assets. Configured branding and navigation use the same checks as build.

No output directory or temporary files are created, and existing exports are
untouched. Shell redirection in the JSON example writes the report separately.
The checker does not test output ownership, permissions, available disk space,
browser behavior, or external URLs. A build can still fail to publish after a
successful content check.

Raw HTML produces a warning because it is displayed literally. `--strict`
makes warnings fail the command while retaining their warning severity.
Portable checks always validate local references: `--deep` is accepted for
shared CI commands but adds no extra coverage. MDX is unsupported in this target.

Errors are collected across documents during parsing, and across local
references when parsing succeeds. Configuration and discovery failures stop
dependent checks. Rendering and output-path failures also stop at their first
fatal error. Fix reported problems and run again; the report does not promise
to enumerate errors in phases that could not run.

### JSON reports

Portable `--json` writes exactly one report to stdout on validation success or
failure. Validation diagnostics go in the report, with no additional stderr
messages. Invalid CLI options and unsupported hosted JSON requests still use
normal CLI errors on stderr and exit 2 before running the checker.

```json
{
  "schema_version": 1,
  "target": "portable",
  "root": "/work/docs",
  "strict": false,
  "ok": false,
  "pages": null,
  "diagnostics": [
    {
      "severity": "error",
      "code": "reference",
      "file": "README.md",
      "message": "reference \"missing.md\": no matching document or local asset"
    }
  ]
}
```

`root` is canonical when it can be resolved, otherwise it retains the requested
path. `pages` is the generated HTML page count when compilation succeeds,
including a synthesized home; it is `null` when compilation fails. A strict
warning-only failure still has a page count. `file` is source-relative with
forward slashes when known, otherwise `null`. There are no structured line or
column fields. Consumers should tolerate additive fields.

Diagnostic codes are `source`, `configuration`, `markdown`, `reference`,
`output-path`, `rendering`, and `raw-html`. The last is a warning; the others
report errors. Human output sends a summary to stdout and diagnostics to stderr.

Exit status is 0 on success, 3 for invalid content or strict warnings, and 1
when the compiler returns an I/O failure. If multiple errors are collected,
the first fatal error determines the exit status.

## Hosted content checks

```bash title="terminal"
zel check ./content --target static
zel check ./content --deep
zel check ./content --deep --strict
```

Without a directory argument, `zel` looks in `./content`, then the current
directory, then `./docs` and `./documentation`. It recognizes `site.yaml`,
`pages.yaml`, `menu.yaml`, a `sections/` directory, or a guide directory with
`_sidebar.yaml`. A guide-only site does not need a `site.yaml` file. Hidden
directories and asset/example folders are not treated as guides.

A directory argument other than `.` selects that exact hosted folder, including
an empty folder when `--target static` is explicit; the engine reports its content
errors or warnings. `.` uses the discovery order above. Discovery never searches
parent directories. `dev`, hosted `build` and the image commands use this resolver.

### Shared engine schemas

Hosted checks run the engine's own schemas. The CLI mounts your folder read-only
and asks the engine to validate it, keeping the schemas shared with rendering.
A successful check is still followed by preparation and compilation, which can
detect additional errors.

### Hosted validation coverage

| | |
| --- | --- |
| Site configuration and referenced content | Against their schemas. Unknown values fail, naming what is accepted |
| Referenced sections and section examples | The type exists, required fields are present, values are in range |
| Navigation references | Menu/footer `page:` targets, navigation CTAs, announcements and footer URLs; literal menu `url:` entries are intentionally unchecked |
| Every sidebar entry | Names a page that exists in that guide |
| Route ownership | Physical pages, guide roots and home redirects cannot claim conflicting routes |
| The home page | `home:` names a page that exists |

#### Errors and warnings

An **unknown top-level key warns**. A content folder written for a newer Zellij
still builds on an older one, which is what lets a team upgrade the engine and
the content separately.

An **unknown value for a known key fails**, naming the key and listing what it
accepts. `theme: cupertno` is a typo, not forward compatibility, and treating it
as one would render the wrong theme silently.

<Callout type="tip" title="Unknown keys inside a section file are accepted silently">
Sections gain fields far more often than the top-level schema does, so a folder
written for a newer engine still builds. The cost is that a typo in a section
file is not reported — which is one more reason to read what `check` says about
files no page references.
</Callout>

### Hosted deep checks

`--deep` adds static analysis to the fast content-model check:

- Parse guide and `markdown-prose` MDX without executing JavaScript. Report malformed syntax.
- Check Markdown links and images, reference-style links, literal JSX `href`, `src`, `poster` and `id`, and `Screenshot` asset paths.
- Check section CTAs, card links, inline-Markdown links and schema-declared media, including nested items, logos and social images.
- Resolve relative links from the rendered page URL, including query strings and encoded paths. Check fragments against rendered heading IDs, explicit IDs and section anchors, following home/guide redirects.
- Check section examples, including missing or recursive `SectionPreview` references, and reject duplicate rendered IDs.
- Require referenced local media to exist as files inside the content's assets directory. Reject escaping paths and symlinks.

In YAML media and `<Screenshot>`, use `assets/image.png`. Ordinary Markdown/HTML
images use their actual public URL, such as `/_zellij/assets/image.png`; a relative
`assets/image.png` inside `/guide/setup` would request `/guide/assets/image.png`.
A Markdown document link is also a website URL, not a source filename: use
`/guide/install`, not `install.md`, unless a converter has rewritten it.

Errors name the content file and field or body location. MDX coordinates are
relative to the loaded body, after front matter and the leading title have been
removed. Section examples rendered inside a page use that page's link context.

### What still needs a hosted build

Deep checking parses MDX; it does not compile or execute it. Computed JSX props,
JavaScript expressions/imports, custom components and `srcSet` candidates produce
warnings because their generated links, assets or anchors cannot be established
statically. A missing anchor on a page with unevaluated MDX is also a warning.
`--strict` makes these warnings fail, rather than treating them as verified.

External URLs are not requested. Wrapper-owned public files outside the content
asset prefix, custom runtime output, and SVG-internal asset fragments are outside
this content-folder contract. Literal menu `url:` entries retain their intentional
unchecked behavior. Deep checking uses the optional math parser when installed;
a bare content-only engine image has no optional dependency installation. For a
math-enabled site, run the Node checker in its installed wrapper environment and
retain the full build with the selected features.

A valid parse does not prove that a component exists or accepts its props, that
an expression runs successfully, or that math/diagrams compile. Build and browser
acceptance are still required, especially after a conversion:

```bash title="terminal"
zel check ./content --deep --strict
zel build ./content
```

### Hosted workflows

**As a pre-commit hook.** It exits non-zero, takes a second, and catches the
class of mistake that is invisible in a diff — a renamed page that three
sidebars still point at.

**As the first job in a pipeline.** [`zel ci init`](/cli/ci) writes exactly that:
a check on every pull request, needing no credentials and no registry. A link to
a page somebody deleted gets caught before review rather than after deploy.

**Before a hosted build.** Hosted `zel build` and `zel dev` run the fast check.
Add an explicit `zel check --deep --strict` step for the stronger gate; they do not
automatically enable it. `zel deploy` remains planned.

### Container file sharing

```
error: my-docs is not shared with the container runtime
```

A bind mount of an unreachable path does not fail — it mounts an empty
directory, and the checker faithfully reports a site with no pages. True of what
it was shown, and a lie about what you asked.

Colima shares `$HOME` and not `/tmp`:

```bash title="terminal"
colima stop && colima start --mount '/tmp:w'
```

## Options

| Option | Portable Markdown | Hosted YAML/MDX |
| --- | --- | --- |
| `[dir]` | Exact Markdown root, default `.` | [Content discovery](/cli/#how-a-command-finds-your-content) |
| `--target` | `portable` | `static` |
| `--deep` | Accepted; local references are always checked | Adds MDX syntax and static-reference checks |
| `--strict` | Warnings fail the command | Warnings fail the command |
| `--json` | Structured report on success and validation failure | Rejected before execution |

`--strict` is off by default. Hosted strict mode includes unknown top-level
keys, unused sections and other existing warnings. Use `--deep --strict` to
include warnings about unverified dynamic MDX. The hosted Node command accepts
these two flags: `npx zellij check ./content --deep --strict`.

`--quiet` remains planned and is rejected with exit code 2. Hosted JSON reports
also remain planned. JSON is additionally available for `context`, `list`,
`explain` and `detect`.
