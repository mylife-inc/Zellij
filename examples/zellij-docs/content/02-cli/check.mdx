<Callout type="tip" title="Available">
Works today. Runs the engine in a container with your folder mounted read-only,
so it needs a container runtime and about a second.
</Callout>

```bash title="terminal"
zel check
zel check ./docs
zel check ./docs --deep
zel check ./docs --deep --strict
```

Without a directory argument, `zel` looks in `./content`, then the current
directory, then `./docs` and `./documentation`. It recognizes `site.yaml`,
`pages.yaml`, `menu.yaml`, a `sections/` directory, or a guide directory with
`_sidebar.yaml`. A guide-only site does not need a `site.yaml` file. Hidden
directories and asset/example folders are not treated as guides.

A directory argument other than `.` selects that exact folder, including an
empty folder; the engine reports its content errors or warnings. `.` uses the
discovery order above. Discovery never searches
parent directories. `dev`, `build` and the image commands use the same resolver.

```
✓ ./content
  site        Acme · theme cupertino
  pages       6
  guides      1 (5 pages) · /guide
  menu        Features · Pricing · Solutions · Resources
  home        /
  routes      11
```

And when something is wrong:

```
✗ ./content

  pages.yaml:14
    section "sections/home/pricing.yaml" does not exist

  01-guide/_sidebar.yaml:9
    "installation" is not a page in this guide
    did you mean "install"?

  site.yaml
    nav.cta: "Guide" → /missing-guide — no such route

3 problems
```

## The one thing worth understanding

**`check` runs the engine's own schemas, not a reimplementation of them.**

That is why it needs a container, and it is the reason to trust it. The
alternative — parsing YAML in Rust and checking it against rules written a
second time — would produce a validator that agrees with the build on the day it
is written and disagrees with it a month later. Every field added to a section
type would need adding twice, and the failure mode is the worst kind: `check`
passes, the build fails, and the two disagree about the same file.

So the CLI does not know what a `hero` is. It mounts your folder read-only,
starts the engine, and asks.

The cost is a container runtime. The benefit is that schema and content-model
checks use the same implementation as rendering. A successful check is still
followed by preparation and compilation, which can detect additional errors.

## What it validates

| | |
| --- | --- |
| Site configuration and referenced content | Against their schemas. Unknown values fail, naming what is accepted |
| Referenced sections and section examples | The type exists, required fields are present, values are in range |
| Navigation references | Menu/footer `page:` targets, navigation CTAs, announcements and footer URLs; literal menu `url:` entries are intentionally unchecked |
| Every sidebar entry | Names a page that exists in that guide |
| Route ownership | Physical pages, guide roots and home redirects cannot claim conflicting routes |
| The home page | `home:` names a page that exists |

### Errors against warnings

An **unknown top-level key warns**. A content folder written for a newer Zellij
still builds on an older one, which is what lets a team upgrade the engine and
the content separately.

An **unknown value for a known key fails**, naming the key and listing what it
accepts. `theme: cupertno` is a typo, not forward compatibility, and treating it
as one would render the wrong theme silently.

<Callout type="tip" title="Unknown keys inside a section file are accepted silently">
Sections gain fields far more often than the top-level schema does, so a folder
written for a newer engine still builds. The cost is that a typo in a section
file is not reported — which is one more reason to read what `check` says about
files no page references.
</Callout>

## Deep checks

`--deep` adds static analysis to the fast content-model check:

- Parse guide and `markdown-prose` MDX without executing JavaScript. Report malformed syntax.
- Check Markdown links and images, reference-style links, literal JSX `href`, `src`, `poster` and `id`, and `Screenshot` asset paths.
- Check section CTAs, card links, inline-Markdown links and schema-declared media, including nested items, logos and social images.
- Resolve relative links from the rendered page URL, including query strings and encoded paths. Check fragments against rendered heading IDs, explicit IDs and section anchors, following home/guide redirects.
- Check section examples, including missing or recursive `SectionPreview` references, and reject duplicate rendered IDs.
- Require referenced local media to exist as files inside the content's assets directory. Reject escaping paths and symlinks.

In YAML media and `<Screenshot>`, use `assets/image.png`. Ordinary Markdown/HTML
images use their actual public URL, such as `/_zellij/assets/image.png`; a relative
`assets/image.png` inside `/guide/setup` would request `/guide/assets/image.png`.
A Markdown document link is also a website URL, not a source filename: use
`/guide/install`, not `install.md`, unless a converter has rewritten it.

Errors name the content file and field or body location. MDX coordinates are
relative to the loaded body, after front matter and the leading title have been
removed. Section examples rendered inside a page use that page's link context.

## What still needs a build

Deep checking parses MDX; it does not compile or execute it. Computed JSX props,
JavaScript expressions/imports, custom components and `srcSet` candidates produce
warnings because their generated links, assets or anchors cannot be established
statically. A missing anchor on a page with unevaluated MDX is also a warning.
`--strict` makes these warnings fail, rather than treating them as verified.

External URLs are not requested. Wrapper-owned public files outside the content
asset prefix, custom runtime output, and SVG-internal asset fragments are outside
this content-folder contract. Literal menu `url:` entries retain their intentional
unchecked behavior. Deep checking uses the optional math parser when installed;
a bare content-only engine image has no optional dependency installation. For a
math-enabled site, run the Node checker in its installed wrapper environment and
retain the full build with the selected features.

A valid parse does not prove that a component exists or accepts its props, that
an expression runs successfully, or that math/diagrams compile. Build and browser
acceptance are still required, especially after a conversion:

```bash title="terminal"
zel check ./content --deep --strict
zel build ./content
```

## Where it belongs

**As a pre-commit hook.** It exits non-zero, takes a second, and catches the
class of mistake that is invisible in a diff — a renamed page that three
sidebars still point at.

**As the first job in a pipeline.** [`zel ci init`](/cli/ci) writes exactly that:
a check on every pull request, needing no credentials and no registry. A link to
a page somebody deleted gets caught before review rather than after deploy.

**Before a build.** `zel build` and `zel dev` run the fast check. Add an explicit
`zel check --deep --strict` step when you want the stronger gate; they do not
automatically enable it. `zel deploy` remains planned.

## When the folder is somewhere the runtime cannot see

```
error: my-docs is not shared with the container runtime
```

A bind mount of an unreachable path does not fail — it mounts an empty
directory, and the checker faithfully reports a site with no pages. True of what
it was shown, and a lie about what you asked.

Colima shares `$HOME` and not `/tmp`:

```bash title="terminal"
colima stop && colima start --mount '/tmp:w'
```

## Options

| | | |
| --- | --- | --- |
| `[dir]` | The content folder | [Resolved](/cli/#how-a-command-finds-your-content) |
| `--deep` | Parse MDX and validate static local references | Off by default |
| `--strict` | Exit nonzero if any warning is reported | Off by default |

`--strict` applies to either check mode: unknown top-level keys, unused sections
and other existing warnings fail too. Use `--deep --strict` to include warnings
about unverified dynamic MDX. The Node command accepts the same two flags:
`npx zellij check ./content --deep --strict`.

<Callout type="warning" title="Planned">
`--json` and `--quiet` are not implemented. Rust's global `--json` is currently
accepted and ignored; output remains the human report.
</Callout>

### The intended `--json`

```json
{
  "ok": false,
  "root": "./content",
  "problems": [
    {
      "file": "pages.yaml",
      "line": 14,
      "severity": "error",
      "message": "section \"sections/home/pricing.yaml\" does not exist"
    }
  ]
}
```

The intent is that every command supports `--json`, because a tool only a human
can read cannot be used by a pipeline. None of them do yet.
