`zel` is the interface to Zellij. Creating a content folder, converting one from
another tool, checking it, running it, building it and putting it online are all
subcommands of the same binary.

It is a native executable with **no Node dependency**. The commands that
describe the content model read a schema compiled into the binary. The commands
that scaffold, check, build and preview portable Markdown run natively too.
Hosted YAML/MDX builds run the engine in a container, so nothing on your machine
needs npm, a Node version, or a lockfile. Use `zel new portable` for a Markdown
starter that opens directly from disk after building.

<Callout type="info" title="Not the terminal multiplexer">
There is a well-known terminal multiplexer called Zellij whose binary is
`zellij`. This one is `zel`. Both can sit on the same PATH.
</Callout>

## Installing

Binaries are published on the repository's releases page — Linux and macOS,
x86-64 and arm64, each with a `.sha256` beside it. On Windows, install into WSL.

```bash title="terminal"
curl -fsSL https://raw.githubusercontent.com/mylife-inc/releases/main/zellij/install.sh | sh
```

Or download the archive for your platform, verify it against its `.sha256`, and
put `zel` on your PATH. See [the Quickstart](/guide/quickstart) for the detail.

## How a command finds your content

Every command that reads or writes content takes an optional directory:

```bash
zel check              # figure it out
zel check ./docs       # this one
```

For commands that discover structured content, the search order is `./content`,
the current directory, `./docs`, then `./documentation`. Marker files such as
`site.yaml`, `pages.yaml`, and `menu.yaml`, a `sections` directory, or guide
folders with `_sidebar.yaml` identify a candidate. Discovery does not walk up
the directory tree. An explicit content path is used as supplied.

CLI defaults from `zel.toml` are still planned. Portable projects can use
[zel.yaml](/cli/config). Both `zel build ./docs` and `zel check ./docs` choose
portable Markdown when that config is present or no structured content is
discovered. Portable commands use the exact requested root. See [build](/cli/build)
and [check](/cli/check) for explicit target selection and output rules.

## Where Docker comes in

Commands that only read the content model — `explain`, `list`, `context`,
`detect`, `convert`, `new` — are pure Rust and need nothing installed.

Structured-content `check`, `dev`, and hosted `build` commands run the Next.js
engine in a container from a public image. Portable `build` and `check` run
natively and need no external tools. `serve` and `view` use a native local
HTTP server; `view` can invoke the system browser launcher. Deployment commands
remain planned.

```bash title="terminal"
zel doctor
```

tells you whether a container runtime is present and which image it would use.
You never write a Dockerfile, and you never see one unless you ask for it with
[`zel image dockerfile`](/cli/image#zel-image-dockerfile).
