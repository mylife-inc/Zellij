---
title: zel
description: One binary. Everything you do to a Zellij site, you do with it.
---

`zel` is the interface to Zellij. Creating a content folder, converting one from
another tool, checking it, running it, building it and putting it online are all
subcommands of the same binary.

It is a native executable with **no Node dependency**. The commands that
describe the content model read a schema compiled into the binary. The commands
that scaffold, check, build and preview portable Markdown run natively too.
Hosted YAML/MDX builds run the engine in a container, so nothing on your machine
needs npm, a Node version, or a lockfile for those container commands.
`zel new app` can also create an editable local wrapper; running that wrapper
requires Node and npm. Use `zel new portable` for a Markdown
starter that opens directly from disk after building.

<Callout type="info" title="Not the terminal multiplexer">
There is a well-known terminal multiplexer called Zellij whose binary is
`zellij`. This one is `zel`. Both can sit on the same PATH.
</Callout>

## Installing

[Candidate 0.2.0-rc.5](https://github.com/mylife-inc/Zellij/releases/tag/v0.2.0-rc.5)
targets GNU/Linux, macOS and Windows on x64 and ARM64. Check the release page
for publication status, pinned installers, package checksums and release notes.
This reference covers candidate `0.2.0-rc.5`, including separate company branding,
preview upgrades, versioned templates and matching default engine versions. Pre-1.0 installation uses
explicit candidates; obsolete distributions are retired after their replacements
are verified.

### Homebrew on macOS and Linux

The owned [Homebrew tap](https://github.com/mylife-inc/homebrew-tap) publishes
the verified native formula for both x64 and ARM64:

```bash
brew install mylife-inc/tap/zel
brew upgrade mylife-inc/tap/zel
brew uninstall zel
```

The tap README identifies its currently published version. Until 1.0, the formula
clearly labels development previews. It installs Bash, Zsh and Fish completions
and verifies archive checksums. No Node or container runtime is installed for
portable documentation. Hosted commands require a supported container runtime.
Use Homebrew to update a Homebrew installation; `zel upgrade` detects its
ownership marker and prints the correct command without changing any files.

### Native archives and installers

The current source implements every registered command family. Imports cover
MkDocs, Docusaurus, VitePress, Jekyll, Hugo and Sphinx within their documented
declarative subsets. Deployment supports Netlify, Cloudflare Pages, Vercel,
GitHub Pages, S3, existing Fly web apps, Railway image services and image
registries. Workflow generation supports GitHub Actions, GitLab and CircleCI;
remote dispatch remains GitHub-only. Authoring includes interactive wizards and
scriptable section values.

The documented command surface is implemented. Live Fly/S3 and actual
GitLab/CircleCI runner verification are deferred until after this release;
Vercel live verification is also deferred. These are remaining acceptance tasks.
See the [completion ledger](https://github.com/mylife-inc/Zellij/blob/main/specs/zel-cli-completion-2026-11-11.md)
for current evidence. Command availability does not promise full source-tool
plugin/theme compatibility or support for an unlisted provider.

```bash title="terminal"
curl -fsSL https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.5/install.sh -o install.sh
ZEL_VERSION=v0.2.0-rc.5 ZEL_RELEASE_BASE_URL=https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.5 sh ./install.sh
```

Or download the archive for your platform, verify it against its `.sha256`, and
put `zel` on your PATH. See [the Quickstart](/guide/quickstart) for the detail.

For Windows, use the candidate release page's pinned PowerShell instructions.
They download its attached `install.ps1` and select version `v0.2.0-rc.5` and
that release's asset directory. The installer supports
Windows PowerShell 5.1 and PowerShell 7, selects x64 or ARM64, verifies the
checksum and executable version, and installs into
`%LOCALAPPDATA%\Programs\Zellij\bin`. `-InstallDir` selects another directory.
Add that directory to your user PATH and open a new terminal; the installer
does not change your environment settings. No administrator rights are needed
for the default user location.

Both candidate installers preserve an existing executable if validation
fails. The Windows installer requires a native Windows archive; a Linux archive
is used only inside WSL. Native portable `build`, `check`, `dev`, `serve` and `view`
need no container runtime.

The standalone installers require an explicit candidate version. Follow the candidate release
page's pinned instructions: they download the installer attached to that release
and select its asset directory. Unpinned stable installation does not select a
candidate. Standalone rc.4+ installations can discover the newest candidate with
`zel upgrade --preview`; `--check` reports it without replacing the executable.
The default hosted/container engine now matches the CLI version. To explicitly
select an engine for this session:

```bash
export ZELLIJ_IMAGE=ghcr.io/mylife-inc/zellij-base:0.2.0-rc.5
```

In PowerShell, use `$env:ZELLIJ_IMAGE = 'ghcr.io/mylife-inc/zellij-base:0.2.0-rc.5'`.
Image tags omit the version's leading `v`; candidates do not update `latest`.

## Output controls

All commands accept these options before or after the command, including shortcuts:

```bash
zel b --quiet
zel --verbose --config docs/manual/preview.yaml build
zel check --json --quiet > report.json
zel image static --no-color
```

- `--quiet` (`-q`) suppresses routine progress, success messages and subprocess
  progress. It still performs the complete command. Errors, native warnings,
  conversion limitations and requested reports remain visible.
- `--verbose` adds execution timing, site selection and container discovery
  details on stderr. It does not dump raw arguments, credentials or environment
  values. It conflicts with `--quiet`; there is no `-v` flag (`zel v` means view).
- `--no-color` removes terminal styling from help, errors, human reports and
  streamed tool output. A nonempty `NO_COLOR` environment variable does the same,
  including when a force-color variable is set. Child tools and containers also
  receive the color preference. Generated content is not rewritten.

Quiet mode preserves stdout data: JSON, context, section YAML, Dockerfiles,
completion scripts, inspection and doctor reports, dry-run plans, formatting
findings and page-registration snippets. Hosted validation retains its complete
report because the engine combines diagnostics and its summary. Portable checks
suppress the success summary but retain diagnostics; their JSON remains complete.
`context --json <file>` writes the file and suppresses its notice under `--quiet`.

Verbose JSON commands still write only the requested JSON on stdout; verbose
messages use stderr. Without `--verbose`, portable/hosted check and doctor JSON emit
one report with no stderr diagnostics for handled validation or preflight failures. Unsupported JSON
commands remain errors. Quiet/verbose never change strictness, overwrite rules,
publication intent, browser launching or watch behavior. Quiet previews suppress
their readiness URL; choose a known `--port` when using them interactively.

Ordinary text output keeps its existing stream placement for compatibility.
Successful external-tool logs are suppressed in quiet mode; if a tool fails,
its last 64 KiB per stream is replayed on stderr with a truncation notice when
needed. Quiet and color-filtered subprocesses spool logs to temporary files
until they exit, then remove them. This avoids pipe deadlocks and keeps failure
reporting bounded in memory; long-running verbose tools can use temporary disk
space. This does not turn third-party logs into structured diagnostics.

## How a command finds your content

Common workflows also have short forms: `zel init`, `zel c`, `zel b`, and
`zel v --watch`. See [the full shortcut table](/cli/shortcuts). Both forms accept
the same arguments; help and shell completion show the available names.

Publish, build/check/fmt/watch/view/serve/dev and image static/next/build/dockerfile accept a site directory.
Without one, they select `./zel.yaml`, then `./docs/zellij/zel.yaml`.

```bash
zel new portable                     # creates docs/zellij/zel.yaml and content/
zel check --strict                   # uses that site
zel build                            # writes docs/zellij/site/
zel build docs/manual                # a custom site name
zel build ./existing-markdown        # explicit legacy Markdown folder
zel --cwd ../my-product b            # use another repository as the working directory
zel b --site-root docs/manual        # explicit selector, also accepted before the command
zel b --config docs/manual/preview.yaml # select a named YAML config
```

A versioned `zel.yaml` declares `renderer: portable` or `renderer: hosted`;
both use `content/` and default to `site/` output. There is no parent or recursive
search. A missing default is an error with an explicit-path suggestion. Existing
flat portable configs and explicit raw content folders still work. See
[configuration](/cli/config) for settings, precedence and compatibility rules.

`--cwd` sets the base for CLI paths. `--site-root` selects an existing site;
`--config` selects a named YAML config. The selectors conflict with one another
and with another site argument. See [selection rules](/cli/config#working-directory-and-site-selection)
for the supported commands and error behavior.

Creation destinations, conversion sources, image tags and CI workflow options
keep their distinct meanings; they are not interchangeable site selectors.

## Where Docker comes in

Commands that only read the content model — `explain`, `list`, `context`,
`detect`, `convert`, `new`, `fmt` — are pure Rust and need nothing installed.

Hosted `check`, `watch`, `dev`, `view` and `build` commands run the Next.js
engine in a container from a public image. Portable `build`, `check`, `watch`, `dev` and `view` run
natively and need no external tools. `serve` and `view` use a native local
HTTP server; `view` can invoke the system browser launcher. Configured image
publication uses the container runtime. Netlify deployment is native for portable
content and uses a container export for hosted content.

Container-dependent operations stop with exit code 4 and setup guidance if no
usable runtime is available. Docker, Podman and nerdctl are supported discovery
candidates. No software is installed and no renderer is changed automatically.
[`zel doctor`](/cli/doctor) documents timeouts and explicit endpoint selection.
`image dockerfile` only prints a recipe and does not require a runtime.

```bash title="terminal"
zel doctor
```

tells you whether a container runtime is present and which image it would use.
You never write a Dockerfile, and you never see one unless you ask for it with
[`zel image dockerfile`](/cli/image#zel-image-dockerfile).
