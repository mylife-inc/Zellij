title: zel new
description: Create portable documentation, hosted content, an editable Next.js app, pages, guides or sections.
---

`portable`, `docs` and `project` start a project; `page`, `guide` and `section`
add to hosted content. `app` creates an editable Next.js wrapper.

| | Creates | Default location | |
| --- | --- | --- | --- |
| `zel new portable [dir]` | Markdown and `zel.yaml`, built natively | `./docs/zellij` | **Available in source** |
| `zel new docs [dir]` | Hosted YAML/MDX content | `./docs/zellij` | **Available** |
| `zel new section <type>` | One section file | `--out`, or stdout | **Available** |
| `zel new page <name>` | One page, and the section files it references | inside the content folder | **Available** |
| `zel new guide <name>` | A guide folder with a sidebar and an index | inside the content folder | **Available** |
| `zel new app [dir]` / `zel na [dir]` | An editable Next.js wrapper | `.` | **Available in source** |
| `zel new project <name>` | A repository with docs and product as siblings | `./<name>` | **Available** |

The available ones are pure Rust with the schema compiled in — **no container
runtime, no Node** for file generation. Running an app generated by `zel new app`
requires Node and npm.

Choose `portable` for ordinary Markdown documentation that also opens directly
from disk. Choose `docs` for the hosted engine's MDX and page sections. Its build
and development preview use a container. [Build targets](/cli/build) explain
the output differences; several deployment commands remain planned.

## What every one of them refuses to do

**Overwrite authored files without an explicit overwrite option.** `new docs`
requires an empty directory unless `--force` is supplied. `new portable` and
`new project` require an empty directory. `new page` and `new guide` add files inside an existing
content folder, but refuse collisions with existing files. Every generated
destination is checked before writing, so a later collision does not leave
earlier sections behind.

The empty-directory check ignores dotfiles, so `git init` followed by `zel new docs` works —
a directory containing only `.git` is empty as far as anyone is concerned.
Individual output paths are still checked, including hidden files and symbolic
links. A generated path cannot escape its content root or write Git metadata.

## `zel new portable [dir]`

Creates Markdown and native configuration, ready for strict checking, building
and previewing. This command is available in source; older released binaries
may not have it. Check `zel new --help` before using an installed release.

```bash title="terminal"
zel new portable --name "Acme documentation" --theme forest
zel check --strict
zel build                      # writes docs/zellij/site
zel view --watch          # builds, serves, opens a browser and reloads edits
```

Double-click `docs/zellij/site/index.html` to view the build without a server. Move or
share the whole output folder so its pages and support files stay together.
To serve an existing export, run `zel serve`.

```text
docs/zellij/
├── zel.yaml                        # version, renderer and portable settings
└── content/
    ├── index.md
    ├── guide/getting-started.md
    └── assets/workflow.svg
```

`--minimal` writes only `zel.yaml` and `content/index.md`. Both starters pass
`zel check --strict` as created. They need no Docker, Node or network connection.
An existing Markdown folder can be built directly; scaffolding is optional.

| Option | Meaning | Default |
| --- | --- | --- |
| `[dir]` | Site destination folder | `docs/zellij` |
| `--name <text>` | Site name and home title | Destination folder's name |
| `--theme <name>` | A theme from `zel list themes` | `cupertino` |
| `--minimal` | Omit the example guide and image | off |
| `--interactive` / `-i` | Choose missing settings in the site wizard | off |

Names must be nonempty text without control characters. Names and theme values
are validated before writing. Display names are quoted in metadata rather than
inserted into Markdown syntax. Existing dotfiles, including `.git`, are retained.
A nonempty folder or existing generated filename is refused; there is no
`--force` option for this starter. No command installs dependencies or launches
a server during creation.

Add ordinary Markdown pages and update `nav`, or remove `nav` to discover pages
automatically. See [portable configuration](/cli/config) and
[rendering limits](/cli/build). Hosted `new page`, `new guide` and `new section`
generate YAML/MDX and should not be used inside this Markdown starter.

## Site creation wizard

**Current source, newer than published rc.1**, supports interactive creation:

```bash
zel init -i                  # portable Markdown at docs/zellij
zel nd -i                    # hosted YAML/MDX at docs/zellij
zel nd docs/manual -i --name "Acme" --theme forest
```

The wizard asks for the site name, a theme, and a starter. Select a theme or
starter by name or by its displayed number. Portable sites offer `standard`
(home, guide and local image) or `minimal` (one Markdown page). Hosted sites
offer `standard`, `minimal`, or `full` (all section examples), then ask whether
to include a guide. The output folder is the command's positional argument,
or `docs/zellij` when omitted; it is not another question.

Enter keeps the displayed default: the destination's name, `cupertino` for
portable or `paper` for hosted, the standard starter, and no extra hosted guide.
Flags supply answers directly: `--name`, `--theme`, `--minimal`, `--full` and
`--guide` retain their normal meanings and skip the corresponding questions.
Unknown themes and empty names are rejected before writes. Interactive name
answers and all portable names must also exclude control characters; invalid
answers are requested again. Hosted `--name` values retain their literal text,
including newlines and tabs, through escaped YAML, with or without `-i`.

Prompts use stderr and remain visible with `--quiet`. Without `-i`, commands
never prompt and retain their previous defaults. Explicit `-i` accepts a
terminal or piped answers. `:q`, end of input, or Ctrl-C while answering cancels
without creating site files. Files are written only after all answers validate;
the destination root/configuration is checked before prompting and the complete
file plan is checked before writing. A hosted `--force` permits its usual
overwrites only after the questions are complete; cancelling still preserves
existing files. Portable creation has no overwrite option.

The wizard generates the same files as the equivalent flags and uses no Node,
container, network, dependency installer or server. It covers whole-site
creation. Page creation also has a wizard, described below; an app wizard remains
separate work.

## `zel new docs [dir]`

Creates a versioned hosted site: `zel.yaml` selects the hosted renderer and
`content/` holds the YAML/MDX files. No JavaScript project or installation is
created. The default destination is `docs/zellij`; any explicit name is allowed.

```bash title="terminal"
zel new docs
zel new docs ./product-docs
zel new docs --name "Acme" --theme cupertino --guide
zel nd --full                  # all section examples at docs/zellij
zel nd -i                      # choose site settings interactively
```

Display names and guide titles are written as quoted YAML strings, so names
such as `Acme: Docs` retain their punctuation. The starter includes a
“Read the guide” button only when `--guide` also creates its destination;
plain and minimal starters without a guide have no guide button.

### What it writes

The following files are inside `<destination>/content/`. Its sibling `zel.yaml`
contains `version: 1` and `renderer: hosted`.

```
content/
├── site.yaml            # name, theme, nav bar, footer
├── pages.yaml           # one landing page, built from two sections
├── menu.yaml            # the top bar
├── sections/
│   └── home/
│       ├── hero.yaml
│       └── features.yaml
├── 01-guide/            # only with --guide
│   ├── _sidebar.yaml
│   └── index.mdx
└── assets/
    └── .gitkeep
```

### All section examples with `--full`

**Current source, newer than published rc.1**, supports:

```bash
zel nd --full
zel nd docs/manual --full --guide --name "Acme" --theme cupertino
```

The full starter keeps the normal home page and adds an **Examples** menu item,
a catalogue at `/examples`, and one page per section type, such as
`/example-pricing-table`. All 23 section types have an editable YAML example
under `content/sections/examples/`. Active fields contain sample content;
optional fields remain commented examples. The catalogue links each example
and names its source file.

A local SVG and a tiny sample MP4 are included under `content/assets/`, so the
examples have no missing media or external media downloads. The video is only
a short gray clip; replace the sample media and copy before publishing.
`--guide` also adds the normal guide, its links and its menu item. This produces
25 routes, or 26 with the guide.

Creation is native and needs no Node, Docker or network. The generated site uses
the hosted renderer: `zel check --strict --deep`, `zel dev` and `zel build` use
their normal hosted runtime requirements. Use `new portable` for Markdown
output that opens directly from disk.

`--full` conflicts with `--minimal`. Existing-directory and `--force` rules are
the same as the ordinary starter; text and binary destinations are all checked
before writing. `--force` may replace generated example files and sample media,
so keep your edits before recreating a site.

### Why "a folder that already validates" was not an explanation

The folder is not a set of empty templates with `TODO` in them. It is a small
site that is complete and correct on the day it is created:

- `zel check` passes with no warnings.
- `zel dev` serves a landing page with a hero and a feature grid, with real
  placeholder copy.
- Every field written is a field the schema accepts, so the file is a working
  example of its own format.

That matters because the alternative — a skeleton with `TODO` in it — makes your
first experience of Zellij a validation error you did not cause. You start from
something that works and edit it into something you want, and at no point are
you debugging the thing that was supposed to get you started.

It is also why the generated `site.yaml` carries commented keys rather than a
minimal file. A key you can see and uncomment is discoverable; a key you have to
look up is not:

```yaml title="content/site.yaml"
theme: paper          # zel list themes — there are fourteen

# The absolute origin. Canonical URLs, Open Graph tags and the sitemap
# all need it, and without it the sitemap is generated empty.
# siteUrl: https://example.com
```

### Options

| | | |
| --- | --- | --- |
| `--name <name>` | The site name | The directory's name |
| `--theme <theme>` | One of the fourteen | `paper` |
| `--guide` | Also create a guide folder | off |
| `--minimal` | `site.yaml` and one page, nothing else | off |
| `--full` | Home, examples catalogue, all 23 section examples and local media; conflicts with `--minimal` | off |
| `--force` | Write into a directory that is not empty | off |

Without `--force`, a non-empty target is an error rather than a merge. Merging
into an existing folder is how a scaffold quietly overwrites something you
wrote.

## `zel new app [dir]`

Available in candidate `0.2.0-rc.1`; the public `zellij-v0.1.3` binary predates this
command. `zel na` is its shortcut. It creates editable Next.js files without
running Node, npm, Docker, a server or an installer.

The engine is not published to npm. Select a **built local engine package from
the matching Zellij checkout** with `--engine`. Build it once in that checkout:

```bash
npm ci
npm run build --workspace @shebka/zellij
```

Then, from your software repository:

```bash
zel na ./website --site-root docs/manual --engine /path/to/Zellij/engine/packages/zellij
cd website
npm install
npm run check -- --deep --strict
npm run dev
```

Omit `--site-root` to select `./zel.yaml`, then `./docs/zellij/zel.yaml`.
Alternatively, use `--config docs/manual/preview.yaml` to select an existing
hosted site by its YAML configuration. It conflicts with `--site-root` and
`--with-docs`; the wrapper's own `zellij.config.yaml` remains a separate format.
An explicit raw hosted content directory also works. The existing content is
referenced in place using an absolute path; it is not copied or modified.
Portable Markdown and the old `marketing/` layout are not supported by this
wrapper command. For portable Markdown inside a Next image, use
[`zel image next`](/cli/image), which includes the portable adapter.

<div id="--with-docs-and-both-together" className="zellij-legacy-anchor" />

### Start with documentation included

```bash
zel new app ./website --with-docs --name "Acme documentation" --engine /path/to/Zellij/engine/packages/zellij
```

```text
website/
├── package.json
├── next.config.js
├── postcss.config.mjs
├── tsconfig.json
├── zellij.config.yaml
├── .npmrc
├── src/app/
│   ├── layout.tsx
│   ├── [[...slug]]/page.tsx
│   ├── sitemap.ts
│   └── robots.ts
└── docs/zellij/
    ├── zel.yaml                # version: 1, renderer: hosted
    └── content/                # hosted starter with a landing page and guide
```

`zellij.config.yaml` is the wrapper's content selector. With `--with-docs`, it
contains:

```yaml
version: 1
content: docs/zellij/content
```

Checking, asset/search preparation, development and production rendering all
use this selector. Put presentation settings in the selected `content/site.yaml`;
`zel.yaml` continues to configure native CLI operations on that documentation
site. The wrapper and Next images share their core template.

### Options and prerequisites

| Option | Meaning | Default |
| --- | --- | --- |
| `[dir]` | New or empty wrapper destination | `.` |
| `--site-root <path>` | Existing configured site or raw hosted content | Current `zel.yaml`, then `docs/zellij/zel.yaml` |
| `--with-docs` | Create a hosted starter under the wrapper's `docs/zellij` | Off; conflicts with `--site-root` |
| `--engine <path>` | Built local engine package | `./engine/packages/zellij`, when present in the working directory |
| `--name <text>` | Display name for starter docs; normalized for npm's package name | Destination folder name |
| `--port <number>` | Development and production server port, 1–65535 | Selected site's `preview.port`, otherwise 3000 |
| `--features <list>` | Comma-separated `maths`, `diagrams`, or `all` | Neither feature enabled or required |

Scaffolding rejects incompatible/unbuilt engines and unsafe or nonempty
destinations. Existing noncolliding dotfiles such as a fresh `.git` directory
may remain; existing scaffold files are never overwritten. There is no `--force`
option. The output must not overlap its external content or engine package.

Running the generated app requires Node matching `package.json` and npm.
`npm install` copies the engine into the app and resolves its dependencies;
commit the resulting lockfile for reproducible installs. `npm run build` prepares
assets/search and builds Next.js; `npm start` serves that build. This hosted app
requires HTTP, while portable `zel build` output still opens directly from disk.

If the engine moves, update its `file:` dependency and reinstall. If external
content moves, update `zellij.config.yaml`. A deployment environment needs access
to both paths; the generated app does not upload or publish either one. Native
hosted `zel build` and `zel image next` remain available when you prefer the
container workflow without maintaining a local wrapper.

## `zel new section [type] [file]`

Writes a hosted section with required content and commented optional defaults.
The short form is `zel ns`. With a type and no customization, the original
engine-generated template is unchanged:

```bash title="terminal"
zel ns pricing-table --out content/sections/home/plans.yaml
zel ns hero content/sections/home/intro.yaml
zel ns faq                                      # YAML on stdout
```

The positional filename and `--out` are equivalent and cannot be combined.
An output file is never overwritten, including a dangling symlink. There is no
`--force`; choose another filename for an existing authored section.

### Interactive authoring

**Current source, newer than published rc.1**, adds a native section wizard:

```bash
zel ns                         # starts the wizard in a terminal
zel ns --interactive
zel ns pricing-table -i --out content/sections/home/plans.yaml
```

Choose a type by name or its displayed number. The wizard asks for list sizes
and the required content in the starter, including nested fields such as tier
names and prices. Pricing tables also ask which tier to highlight. Optional
fields stay discoverable as commented examples; the wizard does not ask you to
fill every possible field.

Press Enter to keep the displayed starter value. `:q`, Ctrl-C, or end of input
cancels before the section is written. Prompts use stderr, so stdout contains
only YAML when no output file is selected. `--quiet` still shows required
prompts. Without a type, automatic prompting requires terminal stdin and stderr;
pipelines fail with guidance instead of waiting. Explicit `--interactive` also
accepts piped answers, with the same validation and cancellation behavior.

If `--out` was omitted, the wizard asks for a filename at the end. Press Enter
to print YAML. Existing destinations are rejected before writing. A preset output
path is checked before prompting, and checked again when writing.

### Scriptable field values

Every answer can be supplied without prompts:

```bash
zel ns hero --set 'headline=Ship with confidence' --set 'badge=New'
zel ns pricing-table --tiers 3 \
  --set 'tiers.0.name=Free' --set 'tiers.0.price=$0' \
  --set 'tiers.1.name=Team' --set 'tiers.1.price=$20' \
  --set 'tiers.2.name=Business' --set 'tiers.2.price=Contact us' \
  --highlight Team --out content/sections/home/plans.yaml
zel ns faq --count items=2 --set 'items.0.question=Where do I start?' \
  --set 'items.0.answer=Read the guide.'
```

| Option | Meaning |
| --- | --- |
| `--set FIELD=VALUE` | Set a scalar field; repeat for multiple values |
| `--count FIELD=N` | Set an array size; repeat for different arrays |
| `--tiers N` | Pricing shortcut for `--count tiers=N` |
| `--highlight VALUE` | Pricing tier name, 1-based number, or `none` to clear highlighting |
| `--interactive` / `-i` | Prompt for values not supplied by flags |
| `--out FILE` or positional file | Write a new file; otherwise print YAML |

Field paths use dots and **zero-based** array indexes: `tiers.0.name`,
`cards.1.code.body`, `background.gradient.0`. `zel explain <type>` describes
available fields. Strings remain literal text, including `42`, `true`, quotes,
newlines and shell-like text. Boolean-only fields accept `true` or `false`;
numeric fields require JSON numbers. Quote shell arguments as appropriate.
`--set` does not evaluate YAML, JSON objects, JavaScript or shell expressions.

Counts are applied before field assignments. Existing entries are retained;
new entries receive starter values. Schema minimum/maximum counts apply; arrays
without a schema maximum are limited to 256 entries during authoring. Create
optional lists with `--count` before assigning indexes. Missing required parent
objects are filled with starter values. Repeated or conflicting assignments
are rejected. Values supplied by flags are skipped in the wizard, and a count
answer cannot discard those values.

A numeric highlight selects a **1-based** tier; other names must match exactly
one tier. Numeric tier names and a tier named `none` can be selected by position.
`--highlight` cannot be combined with explicit `tiers.N.highlighted` assignments.

The engine's cross-field rules still apply. Setting a media alternative switches
the exclusive choice in `hero-split`, `steps-panel` or `media-panel`; the previous
alternative remains as a commented example. For a matrix, `--count columns=N`
resizes every row's cells, and `--count rows=N` adds correctly sized rows. Cell
counts cannot be changed independently. Conflicting flags fail before writing.

Authoring needs neither Docker nor Node. The CLI validates field types, choices,
bounds and shared cross-field rules using embedded engine metadata. It does not
resolve links or check whether asset files exist. Review remaining `TODO` values
and placeholder media paths, add the section to your page, then run
`zel check --strict --deep` on the hosted site before publishing.

## `zel new page [name]`

Prints an entry to add to `pages.yaml` and creates the section files it references.
The default configured hosted site is selected as for `build`; `--dir` accepts a
custom site root or an explicit legacy content folder. Portable sites are rejected.

```bash title="terminal"
zel new page pricing --sections hero,pricing-table,faq
```

```
✓ sections/pricing/hero.yaml
✓ sections/pricing/pricing-table.yaml
✓ sections/pricing/faq.yaml

  Add this to pages.yaml:

    - name: pricing
      title: Pricing
      description: TODO
      sections:
        - pricing/hero
        - pricing/pricing-table
        - pricing/faq
```

Without `--sections` it creates the page with a single hero.

### Choose a page interactively

**Current source, newer than published rc.1**, supports the short form:

```bash
zel np -i                         # ask for a name and ordered sections
zel np pricing -i                  # name supplied; ask only for sections
zel np -i --sections hero,faq       # sections supplied; ask only for the name
zel np pricing --sections hero,faq # equivalent noninteractive command
```

`--interactive` / `-i` is opt-in. Without it, a name is required and commands
never prompt. The wizard lists the built-in section types and accepts a
comma-separated sequence of names or displayed numbers, in page order. Enter
chooses one hero. Unknown or repeated types are rejected: each selected type
creates one file under `sections/<name>/`. To use a type more than once, author
separately named sections with `zel ns` and add their references to your page.

The name identifies the page and its section subfolder; the printed title uses
the same initial capitalization as the ordinary command. Interactive names must
be nonempty and exclude control characters. Unsafe paths are refused. Supplied
values skip their questions; invalid answers are requested again. `--cwd`,
`--site-root`, `--config` and `--dir` retain their existing selection rules.

Prompts go to stderr, including with `--quiet`; the registration report remains
on stdout. Explicit `-i` accepts terminal or piped answers. `:q`, end of input,
or interruption while answering cancels without writing section files. All
destinations are checked before writing, so a collision later in the list does
not leave earlier files behind. Existing sections are never overwritten.

Generation needs no Node, Docker or network. The wizard uses the existing
templates, including their editable `TODO` values and placeholder media paths.
Add the printed entry to `pages.yaml`, edit the content and any menu links, then
run `zel check --strict --deep` on the hosted site. Creating section files alone
does not register a page or change `pages.yaml` or `menu.yaml`.

<Callout type="info" title="Why it does not edit pages.yaml for you">
Parsing that file and writing it back would lose the comments and the ordering
you chose. Four lines to paste is a better trade than a tool that silently
reformats a file you maintain.
</Callout>

## `zel new guide <name>`

Adds a guide folder — a numbered directory with a `_sidebar.yaml` and an
`index.mdx`. Site selection and `--dir` follow `new page`.

```bash title="terminal"
zel new guide api --title "API reference"
```

```
✓ 02-api/_sidebar.yaml
✓ 02-api/index.mdx
```

The number is one past the highest already in the folder, so guides keep the
order you created them in until you renumber them yourself. Two guides sharing
a prefix is a build error, and this is where it is prevented.

## `zel new project <name>`

A whole repository: documentation and a product as siblings, with a pipeline
that validates the first on every pull request and publishes it on every push.

```bash title="terminal"
zel new project acme --product-lang rust
```

```
✓ acme
  docs/zellij/             the configured hosted documentation
  product/                 yours
  .github/workflows/docs.yml validates on every pull request, image on main

  Write:  zel dev acme/docs/zellij
  Code:   cd acme/product && cargo init
```

| | | |
| --- | --- | --- |
| `--product-lang <lang>` | Which starting command to suggest | `none` |
| `--docs-dir <path>` | Configured site location within the repository | `docs/zellij` |
| `--product-dir <name>` | | `product` |

<Callout type="info" title="The product folder is empty on purpose">
An earlier draft of this page said `--product-lang` would write "a minimal,
buildable starting point" into `product/`. It does not, and it should not.

`cargo init`, `go mod init` and `npm init` exist, are better than anything a
documentation tool would write in their place, and are what you were going to
run anyway. Worse, the languages differ in how much opinion is required —
Rust needs two files, a JVM project needs a build system chosen for you — so
the useful cases would have been useful and the rest would have been wrong.

So `--product-lang` prints the command for your language, with your project's
name already in it, and writes nothing. `none` skips even that.
</Callout>

Notice what is absent: no `package.json`, no wrapper. The pipeline builds the
documentation inside a container from a public image, so the repository stays a
repository about your product.

The `docs/` half is exactly what [`zel new docs`](/cli/new#zel-new-docs-dir)
produces — the same scaffold, so the two cannot drift — and the pipeline is
exactly what [`zel ci init github --target image`](/cli/ci) writes.

[Lab 3](/guide/quickstart/new-project) walks this end to end.
