`zel deploy netlify`, also `zel netlify`, builds and uploads static HTML from

```bash title="terminal"
zel netlify --site-id YOUR_PROJECT_ID --dry-run
zel netlify --site-id YOUR_PROJECT_ID          # draft preview
zel netlify docs/manual --site-id YOUR_PROJECT_ID --prod
```

No path selects the current directory's `zel.yaml`, then
`docs/zellij/zel.yaml`. Pass an explicitly named site root or legacy content
folder when needed. See [site discovery](/cli/config#site-layout-and-discovery).

## Set up Netlify

Create a Netlify project using Netlify's dashboard. Copy its **Project ID** and
generate a personal access token with access to that project. Supply the token
as `NETLIFY_AUTH_TOKEN` through your shell environment or CI secret store. Supply
the project ID with `--site-id`, the compatible `--site` spelling,
`NETLIFY_SITE_ID`, or saved settings. A full site domain such as
`acme-docs.netlify.app` also works; a bare display name is not a domain.

`zel` uses Netlify's HTTPS API directly. It requires no Netlify CLI or Node.js,
and portable rendering requires no container runtime. Hosted content still
requires a usable [Docker, Podman or nerdctl runtime](/cli/doctor) for its build.
Nothing is installed or started automatically. `zel` does not create a provider
project, run login, read another CLI's stored login, or load `netlify.toml`.

Token values belong in the environment, not `zel.yaml`, command arguments or
committed files. Missing credentials fail before building; a read-only API
request checks access to the selected project before the build starts. Both
preview and production deployment need network access and valid credentials.

## Cloudflare Pages

Current source adds `zel deploy cloudflare`, `zel cloudflare`, and the short
alias `zel cf`. These commands are included in candidate `0.2.0-rc.3`.

```bash
zel cf --site manual --dry-run
zel cf --site manual             # preview
zel cf docs/manual --site manual --prod
```

Use an **existing Pages project**. Set `CLOUDFLARE_ACCOUNT_ID` to its account ID
and `CLOUDFLARE_API_TOKEN` to an API token with **Account → Cloudflare Pages → Edit**
access for that account. Tokens stay in your environment or CI secret store.
`--site` / `--site-id` takes the project name, such as `manual`, not a `pages.dev`
URL. It overrides `CLOUDFLARE_PAGES_PROJECT_NAME`, then saved `publish.site`.
Read [Cloudflare's Direct Upload setup](https://developers.cloudflare.com/pages/get-started/direct-upload/)
and [CI token setup](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/)
for account-side configuration. `zel` neither creates projects nor installs or
invokes Wrangler. It does not load Wrangler configuration or stored credentials.

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: cloudflare
  site: manual
```

`zel pub` and bare `zel deploy` then use this destination. An explicit provider
change never inherits another provider's saved destination or environment ID.
The account ID remains an environment setting; it is not saved in `zel.yaml`.

**Preview is the default.** The command selects branch `zel-preview`, regardless
of your local Git branch. Repeated previews update that branch alias and receive
individual deployment URLs. If the project's production branch is named
`zel-preview`, preview deployment fails before building; change that project
setting first. `--prod` selects the production branch returned by project
preflight. Skipped deployments are reported as failures. The command waits for the deployment stage to succeed and reports
its HTTPS `pages.dev` URL, with the hosted base path when configured. Project
settings, access restrictions and concurrent deployments still govern live access.

Both renderers build once into temporary output. Portable builds need no Docker
or Node.js; hosted builds retain their container requirement. Hosted URL/feature
flags below also work with Cloudflare. Source files and previous local output
remain intact, and `ship --provider cloudflare --site manual` saves the converted
site's destination for later `pub` calls. The `--prod` choice is never saved by ship.

This adapter uploads generated **static assets**, with a maximum of 20,000 files
and 25 MiB per file. It hashes assets, skips already uploaded content and batches
missing uploads. Worker code, Functions and root `_headers`, `_redirects` or
`_routes.json` are rejected; custom platform rules and server-side Next apps are
outside this adapter. Symlinks, junctions and non-regular files are rejected,
as are asset paths containing `#`, `?`, backslashes or control characters.
Unicode, spaces and literal percent signs retain their filenames.

Cloudflare applies its [HTML route rules](https://developers.cloudflare.com/pages/configuration/serving-pages/),
including redirects from `.html` URLs to clean routes. Downloaded portable output
still supports direct-file navigation. Current source adds a fallback `404.html`
to the temporary upload when the export has none, so missing URLs return HTTP
404 instead of Cloudflare’s home-page fallback. An existing generated 404 page
is preserved. This fix and support for Cloudflare’s success-only upload
acknowledgements are included in `0.2.0-rc.3`. No DNS or custom-domain changes are made.

Credentials and project access are checked before a build. API redirects are
refused, errors omit response bodies and tokens, and requests have bounded
connection/request/deployment timeouts. Failed requests are not retried
automatically. An uncertain create response may already have published; check
the Cloudflare dashboard before repeating a command. Tests cover the upload
protocol and generated exports. Current-source portable and hosted delivery
passed live account checks for pages, linked assets and missing-page responses on 2026-11-10. The temporary
test project was removed afterward.

## Vercel

Current source supports `zel deploy vercel`, `zel vercel`, and the short alias
`zel vc`. These commands are available in candidate `0.2.0-rc.3`.

```bash
zel vc --site prj_YOUR_PROJECT_ID --dry-run
zel vc --site prj_YOUR_PROJECT_ID           # preview
zel vc docs/manual --site prj_YOUR_PROJECT_ID --prod
```

Create a project in Vercel first. Set `VERCEL_TOKEN` to an access token scoped to
that project/account. For team projects, set `VERCEL_TEAM_ID` to the `team_…` ID.
Supply the project ID or project name through `--site` / `--site-id`,
`VERCEL_PROJECT_ID`, or saved `publish.site`, in that priority order. Use an ID
when possible; URLs are not accepted. Tokens belong in your shell environment
or CI secrets, never in `zel.yaml` or command arguments. See Vercel's
[access-token setup](https://vercel.com/docs/rest-api/reference/welcome#creating-an-access-token).

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: vercel
  site: prj_YOUR_PROJECT_ID
```

`zel pub` then uses this destination. An explicit provider change does not reuse
another provider's saved destination or environment variable. Team selection
remains an environment setting. `zel` does not install or invoke Vercel's CLI,
read its stored login, create projects, or change project configuration/DNS.

The command checks project access, builds once into temporary output, and uploads
static assets using Vercel's prebuilt deployment protocol. Portable rendering
needs no Node.js or container runtime; hosted rendering retains its container
requirement. Both preserve source files and previous local output. Hosted
base-path, site-URL and feature overrides below also apply to Vercel.

**Preview is the default**, independent of the local Git branch. `--prod` is
required for a production deployment, which can update the project's production
domains. The command waits for readiness and, for production, alias assignment,
then reports the deployment's HTTPS `vercel.app` URL with any hosted base path.
Project access restrictions and deployment protection still apply; `zel` does
not make a protected preview public.

The adapter packages [Build Output API](https://vercel.com/docs/build-output-api)
static files. Literal `.html` links remain available, with fallback rules for
clean hosted routes and directory indexes. This is a static export; Next server
functions, middleware and custom `vercel.json` / `.vercel` output are outside
this adapter. Those configuration paths are rejected. Symlinks, junctions,
non-regular files and paths containing `#`, `?`, backslashes or control characters
are also rejected. Unicode, spaces and literal percent filenames are preserved.

This initial adapter accepts at most **15,000 static files and 100 MiB total**;
Vercel account limits may be lower. Identical files share one SHA-1 upload.
Current source accepts Vercel's documented empty successful upload acknowledgements
as well as JSON objects; this compatibility fix is included in `v0.2.0-rc.3`.
Project and deployment responses still require valid identity/status JSON.
Requests use bounded timeouts, refuse redirects and omit provider response bodies
from diagnostics. Creation requests are never automatically retried. An uncertain
response or timeout may leave a deployment running remotely; check the dashboard
before repeating the command. Protocol and generated-export tests are automated;
live Vercel account acceptance is deferred.

## AWS S3

Current source supports `zel deploy s3` and the shortcut `zel s3`. This is available in candidate `0.2.0-rc.3`. The adapter uploads static HTML to an **existing
S3 website bucket**, optionally under a prefix. **There is no draft mode:
`--prod` is required**, including for a dry-run plan.

```bash
zel s3 --site acme-docs/manual --prod --dry-run
zel s3 --site acme-docs/manual --prod
zel s3 docs/manual --site acme-docs/manual --prod
```

Prepare the bucket in AWS first:

1. Use a general-purpose bucket in a supported commercial AWS region. Enable
   static website hosting with **index.html** as the index document. An error
   document is optional; redirect-all settings and routing rules are unsupported.
2. Configure website read access according to your intended audience. `zel`
   does not change bucket policies, public-access settings, ACLs or DNS.
3. Supply `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` through your shell
   environment or CI secret store. Temporary credentials also require
   `AWS_SESSION_TOKEN`. Set `AWS_REGION` to the bucket's region and
   `S3_EXPECTED_BUCKET_OWNER` to its owner's 12-digit AWS account ID.

The upload identity needs `s3:ListBucket` and `s3:GetBucketWebsite` on the bucket,
and `s3:GetObject` and `s3:PutObject` for the destination keys. It needs no delete,
ACL or bucket-configuration permissions. Bucket policy, encryption and other
account controls can impose additional requirements. See AWS's
[HeadBucket](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadBucket.html),
[GetBucketWebsite](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketWebsite.html),
[HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) and
[PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html) references.

`--site` / `--site-id` accepts `bucket` or `bucket/prefix`, not an `s3://` URI or
website URL. It overrides `S3_DESTINATION`, then same-provider `publish.site`:

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: s3
  site: acme-docs/manual
```

Then use `zel pub --prod` or bare `zel deploy --prod`. Prefix segments accept
ASCII letters, digits, dots, underscores and hyphens, with no empty/dot segments
or trailing slash. Prefix length is limited to 512 bytes. Credentials, region
and expected owner remain environment settings. They are never saved in this
publication block. An explicit provider change does not reuse another provider's
destination.

`zel` signs HTTPS requests directly. It neither requires nor invokes the AWS CLI
or reads AWS profiles, stored login, credential processes or instance metadata.
It does not assume roles or refresh temporary credentials; supply current values.
Custom `AWS_ENDPOINT_URL` / `AWS_ENDPOINT_URL_S3` settings are rejected.
S3-compatible services, China/GovCloud regions, access points and directory
buckets are outside this adapter.

Bucket region, expected owner and website configuration are checked before
building. Both renderers build once into temporary output and preserve source
files and previous local output. Portable output needs no Node.js or container
runtime; hosted output retains its container requirement. Portable keys receive
the destination prefix and their links remain relative.

For hosted output, the destination prefix becomes the invocation's default
`basePath`, and the S3 website origin becomes its default site URL. These
invocation defaults override authored URL settings without editing them.
Explicit `--base-path` must equal or sit below the destination prefix. Files
already contain that build prefix, so it is not prepended twice. The adapter
also uploads extensionless copies of non-index HTML pages: `/manual/guide`
and `/manual/guide.html` both resolve. A collision with another output file
fails before any upload. Explicit `--site-url` remains an SEO override; it does
not configure a domain or CDN. A website/CDN origin must serve the bucket root.

AWS website endpoints use **HTTP**, although the upload API uses HTTPS. Use
separately configured CloudFront or another suitable CDN for HTTPS delivery;
this command does not configure it or invalidate caches. See AWS's
[website endpoint behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteEndpoints.html).
The success message reports uploaded objects and the website URL, not a
verification that anonymous website access works.

**Uploads are not atomic.** All planned keys are inspected before the first
write; existing keys use their ETag as an `If-Match` condition and missing keys
use `If-None-Match: *`. Concurrent changes fail instead of being overwritten
silently. Assets upload first, then HTML, with the selected entry `index.html`
last. Requests carry SHA-256 checksums and `Cache-Control: no-cache`. Existing
keys with other names are retained, including removed pages and stale assets.
There is no prune, automatic retry, resume or rollback operation. A failed
upload can leave a partially updated website; inspect the bucket before retrying.

Limits: **5,000 objects, 25 MiB per file and 100 MiB total**, counting clean-route
copies. Keys are limited to 1,024 UTF-8 bytes. Links, junctions, non-regular files
and paths containing `#`, `?`, backslashes or control characters are rejected;
Unicode, spaces and literal percent filenames are preserved. The local output
marker is excluded. Requests refuse redirects, redact response bodies and
credentials, and use 60-second request / 15-second connect limits within a
15-minute upload budget. Website configuration is rechecked before writes and
after upload. Protocol and generated-export tests are automated; live AWS
account acceptance remains pending.

## GitHub Pages

Current source supports `zel deploy github-pages`, `zel github-pages`, and the
short alias `zel ghp`. These commands are available in candidate `0.2.0-rc.3`.
This adapter publishes static files to an existing GitHub.com repository's
`gh-pages` branch. **There is no draft mode: `--prod` is required**, including
when printing a dry-run plan.

```bash
zel ghp --site acme/manual --prod --dry-run
zel ghp --site acme/manual --prod
zel ghp docs/manual --site acme/manual --prod
```

Prepare the destination once in GitHub:

1. Use an existing repository with a dedicated `gh-pages` branch. Keep source
   code on a different default branch, such as `main`. Everything at the
   `gh-pages` root will be replaced by generated output; commit history remains.
2. In **Settings → Pages**, select **Deploy from a branch**, `gh-pages`, and
   **/ (root)**. Finish HTTPS/custom-domain setup there before deploying.
3. Create a dedicated fine-grained token restricted to this repository with
   **Contents: Read and write** and **Pages: Read and write**. Supply it as
   `GITHUB_PAGES_TOKEN` in your environment or CI secret store. Repository rules
   and organization token approval requirements still apply.

See GitHub's [publishing-source setup](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
and [Pages API permissions](https://docs.github.com/en/rest/pages/pages).
`zel` does not create repositories, branches or Pages sites, change repository
settings, read `gh` login credentials, or automatically use `GITHUB_TOKEN`.
Custom Actions-based Pages deployments, `/docs` publishing sources, other
publishing branches and GitHub Enterprise hosts are outside this adapter.

`--site` / `--site-id` takes `owner/repository`, not a URL or `.git` remote.
It overrides `GITHUB_PAGES_REPOSITORY`, then same-provider saved `publish.site`:

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: github-pages
  site: acme/manual
```

This enables `zel pub --prod` and bare `zel deploy --prod`. The production
choice and credentials are never saved in this publication block. An explicit
provider change does not reuse another provider's destination.

Repository, Pages configuration and branch access are checked before building.
Portable output needs no Node.js or container runtime. Hosted output retains
its container requirement. Both build once into temporary output and preserve
source files and previous local output.

For hosted output, the existing Pages URL determines the build's default
`basePath` and site origin. A project at `https://acme.github.io/manual/` builds
links under `/manual`, but uploads its files at the branch root. This avoids a
doubled `/manual/manual/` path. These invocation defaults override authored
URL settings without editing them. Explicit `--base-path` must equal or sit
below the Pages mount; `/manual/reference` publishes under `reference/` in the
branch. An explicit `--site-url` remains an SEO override. Portable links remain
relative and need no mount override. The reported URL includes the chosen path.

The adapter preserves a configured custom domain by generating `CNAME` from the
Pages settings, and includes `.nojekyll`. It refuses an exported `CNAME` that
conflicts with those settings. It creates Git blobs, a complete tree and a commit
with the old branch head as its parent, then rechecks the destination and updates
`gh-pages` **without force-pushing**. Concurrent branch/settings changes fail.
It requests a Pages build and waits for a successful build of that exact commit;
an older successful build is not accepted as success. No DNS changes are made.

The initial limits are **5,000 static files, 25 MiB per file and 100 MiB total**.
Small UTF-8 files are included directly in the tree; up to 200 distinct binary
or large-file uploads are supported per invocation. Tree requests are capped at
6 MiB. GitHub account limits may be lower. Git/workflow/Jekyll configuration,
symlinks, junctions, non-regular files and paths containing `#`, `?`, backslashes
or control characters are rejected. The local output marker is excluded.

Requests refuse redirects and omit provider response bodies and credentials
from errors. Upload/publication has a ten-minute budget, with a 60-second limit
per request and 15 seconds to connect. Mutations are paced and never retried
automatically. A failure may leave uploaded Git objects, or a published commit
whose Pages build is still running. Inspect **Settings → Pages** and the
repository's Actions/build history before retrying; automatic rollback and
resume are not implemented. Protocol and export tests are automated. Portable
and hosted live account acceptance passed on 2026-11-10; the temporary Pages site was removed afterward.

## Save the choice

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: netlify
  site: acme-docs.netlify.app
```

```bash title="terminal"
zel pub --dry-run
zel pub              # build once, then create a draft preview
zel pub --prod       # request production publication
zel deploy           # same saved plan and options as publish
```

`publish.site` is optional if you supply the destination elsewhere. Destination
precedence is `--site-id` / `--site`, then `NETLIFY_SITE_ID`, then `publish.site`.
The value must be a string containing an existing project ID or domain. Saved
settings never contain a token or automatically enable production publication.

Explicit `deploy netlify` supplies deployment intent even when there is no
saved publication, or when the saved plan describes an image push. `pub --to
netlify` also supplies explicit provider intent, but rejects a saved image-push
plan: it cannot silently replace a selected container artifact. `--tag` is
invalid for Netlify. Ordinary build/image commands never deploy.

## Preview and production

For Netlify, the default is a **draft preview** with its own deployment URL. Use `--prod` to
request an update to the live site. The command prints the deployment ID and
its HTTPS preview URL once Netlify reports `ready`; hosted basePath is appended
to that URL. Site locks or a newer concurrent deployment can affect which deploy
is current in production; the dashboard is authoritative for that status.

A dry run prints the site, renderer, destination and publication mode. It does
not read a token, contact a runtime or provider, validate content, build, or
write output. It is a plan, not a successful deployment check.

## Build and upload

The command validates and builds with the selected renderer exactly once into
a private temporary export. It leaves existing `site/`, configured `build.out`,
source and configuration intact. Portable output retains its direct-file
navigation. Hosted output is placed at the engine-resolved basePath, including
prefixes with hidden segments such as `/products/.docs`. Its temporary directory
is created beside the selected content, on the same project filesystem shared
with the runtime; that parent directory must be writable.

The upload manifest contains generated HTML and public assets, excluding the
local export ownership marker. It uses file digests, uploads only the bytes
Netlify requests, and waits for processing to finish. Files with identical
bytes need only one upload. This path publishes static files, without a remote
build, Next server, serverless functions, image push or browser launch.

Paths with `#`, `?`, backslashes or control characters are rejected before
creating a deployment, following Netlify's file-upload constraints. Spaces and
Unicode are URL-escaped. Symlinks and junctions in the export are rejected.

## Failures and retry

| Failure | Exit code |
| --- | --- |
| Invalid settings, incompatible options, missing token/site | `2` |
| Content/build failure or unsuccessful API deployment | `3` |
| Hosted runtime unavailable or unshared mount | `4` |
| Local filesystem/process error | `1` |

A failed build creates no deployment. Once a build succeeds, an upload or
processing failure reports that stage and keeps previous local output intact.
Temporary exports are removed on success or failure. Requests are bounded to
60 seconds (15 seconds to connect), and the create/upload/poll phase has a
five-minute budget. Failed requests are not automatically retried.

An interrupted request or timeout may already have created a deployment, and
Netlify may still finish it. Check the printed deployment ID or the Netlify
dashboard before rerunning. Rerunning builds a fresh export and creates a new
deployment; automatic resume, rollback and deletion are not implemented.
Provider errors report status and remediation without echoing response bodies
or credentials. Authentication redirects are refused.

## Temporary feature selection

```bash title="terminal"
zel netlify --site-id YOUR_PROJECT_ID --features all --dry-run
zel netlify --site-id YOUR_PROJECT_ID --features all
```

`--features` selects `maths`, `diagrams`, `maths,diagrams`, `all`, or `none` for
this deployment's build. It works for portable and hosted sites, including
saved `zel pub` deployment plans. The uploaded HTML uses that selection;
source, configuration and previous local output remain unchanged. A later
invocation without the flag uses saved/default features again. Explicit `none`
disables both optional renderers, even when they are enabled by default.

## Hosted URL and preflight overrides

The current source accepts the hosted [build overrides](/cli/build#hosted-url-and-validation-overrides)
with `netlify`, `deploy netlify`, and saved `publish`/`deploy` commands:

```bash
zel netlify docs/hosted --site-id YOUR_PROJECT_ID --base-path /manual --site-url https://docs.example.com --dry-run
zel netlify docs/hosted --site-id YOUR_PROJECT_ID --base-path /manual --site-url https://docs.example.com
```

The override controls uploaded paths, canonical URLs, sitemap and robots
metadata. The reported preview URL includes the actual exported prefix. Use
`--base-path /` to clear a saved prefix. The public origin is an SEO setting;
it does not create or move a Netlify domain or change which project receives
the deployment. Draft previews remain the default.

`--no-check` skips the separate content preflight. Netlify credentials and site
access are still checked before building; preparation and rendering still
validate content. A failed build creates no remote deployment and retains the
previous local output. Portable Netlify output rejects these three flags.
Authored configuration remains unchanged. These flags require a current CLI
and compatible engine; candidate `0.2.0-rc.3` includes them.

## Options

| Option | Meaning |
| --- | --- |
| `[provider]` | `netlify`, `cloudflare`, `vercel`, `github-pages`, `s3`, `fly` or `railway`; omit to execute saved publication settings |
| `[site]` | Site root, using normal discovery when omitted |
| `--site-id <destination>` | Netlify ID/domain, Cloudflare project name, Vercel project ID/name, GitHub owner/repository S3 bucket/prefix Fly app name or Railway service UUID; `--site` is equivalent |
| `--prod` | Request live publication; required for GitHub Pages, S3, Fly and Railway, which have no draft mode |
| `--kind <kind>` | Fly/Railway image kind; defaults to same-provider `publish.image`, then `static` |
| `--platform <platform>` | Fly/Railway accept only `linux/amd64`; saved `image.platform` is ignored for both |
| `--features <selection>` | Complete rendering selection for this build only; saved settings stay unchanged |
| `--base-path <path>` | Hosted deployment prefix; `/` clears it only when compatible with the provider mount |
| `--site-url <origin>` | Hosted public HTTP(S) origin for canonical URLs and SEO metadata |
| `--no-check` | Skip content preflight; retain preparation, rendering and credential checks |
| `--dry-run` | Resolve and print the plan only |
| `--to <provider>` | Explicit provider for saved static deployment |
| `--tag <reference>` | Image reference for saved registry publication or Railway deployment |

`--json`, `--target`, `--message`, and `--preview` are not supported. Preview is
the default for Netlify, Cloudflare and Vercel; GitHub Pages, S3, Fly and Railway require `--prod`.
Fly uses existing web Machines; Railway uses existing image services. See their setup below.

See [`zel publish`](/cli/publish) for image registry publication and
[`zel ci`](/cli/ci) for workflow generation from saved delivery settings.

## Fly

Current source implements `zel fly` and `zel deploy fly` for **existing Fly apps**.
It builds either the small static web-server image or the Next.js wrapper image,
pushes it to the app's Fly registry repository, and updates existing Machines
using the immutable image digest. This feature is available in candidate `0.2.0-rc.3`;
Live Fly account acceptance is still pending.

```bash
zel fly --site manual --prod --dry-run
zel fly --site manual --prod
zel fly --site manual --kind next --prod
```

The positional folder uses normal Zellij discovery; `--site` identifies the
remote app. Destination precedence is `--site` / `--site-id`, `FLY_APP`, then
same-provider `publish.site`. Image kind precedence is `--kind`, same-provider
`publish.image`, then `static`. For short repeated commands:

```yaml
publish:
  action: deploy
  provider: fly
  site: manual
  image: next
```

Use `zel pub --prod` or `zel fly --prod`. **Fly has no draft mode**, so `--prod`
is required even for a dry run. `publish.image` in a deployment is valid only
for Fly and Railway; registry push settings retain their existing meaning.

### Prepare an existing app

- Set `FLY_API_TOKEN` to one app-scoped deploy token, preferably with a limited
  lifetime. A raw token or one prefixed by `FlyV1 ` or `Bearer ` is accepted;
  comma-separated token sets, token files and stored Fly logins are not read.
- Set `FLY_ORG` to the expected organization slug. The API must return this
  organization and the selected app name before any build begins.
- Authenticate the **selected container runtime** to `registry.fly.io` before
  running the command. Docker users can use `fly auth docker` if they already
  use Fly's CLI. For a token-based Docker login on macOS/Linux:

  ```bash
  TOKEN="${FLY_API_TOKEN#FlyV1 }"
  TOKEN="${TOKEN#Bearer }"
  printf '%s' "$TOKEN" | docker login registry.fly.io --username x --password-stdin
  unset TOKEN
  ```

  Podman/nerdctl users must authenticate that client instead. Zel preserves the
  caller's runtime/context and does not install, start or log in a local runtime.
  Fly's CLI is not required by Zel's deployment adapter.
- The app must already have 1–10 started, reachable, uncordoned web Machines,
  each running one container with HTTP service handlers on internal TCP port
  **3000**, autostop disabled, and configured health checks that currently pass.
  The app must have no other process groups, mounts, injected files, additional
  containers or command/entrypoint/TTY overrides (default `tty: false` is accepted).
  `PORT` and `HOSTNAME` overrides
  must agree with `3000` and `0.0.0.0`.
- Configure public IPs, DNS/TLS, app secrets and the initial Machines separately.
  Zel does not apply `fly.toml`, create Machines, scale, allocate IPs, change
  service settings, execute release commands or create Fly release records.

See Fly's [registry authentication](https://docs.fly.io/blueprints/using-the-fly-docker-registry),
[scoped API tokens](https://docs.fly.io/security/tokens), and
[Machines API](https://docs.fly.io/machines/api/machines-resource) references.

### Build and rollout behavior

Both image kinds use **linux/amd64**. Explicit `--platform linux/amd64` is accepted;
`linux/arm64` and `all` fail before building. Saved `image.platform` and `image.name`
are not Fly defaults. On an ARM development machine, the selected builder must
already support amd64 builds. Zel does not configure emulation. CI uses an amd64
runner. Normal image feature selection and build arguments remain available;
portable static images still reject hosted-only URL/preflight overrides.

The image gets a unique `registry.fly.io/<app>:zel-…` tag. Zel builds once and
pushes, then requires the runtime's repository digest receipt. An absent or
ambiguous digest stops before any Machine update. Local and remote images are
retained on failure; `--tag` is not a Fly option.

Before updates, Zel rechecks app identity, Machine membership, versions and full
configuration. It acquires all Machine leases, then updates one Machine at a
time with an optimistic version guard. Only the image field changes. Each new
version must start with the requested digest and fresh passing results for all
previous health checks before the next Machine is updated. A final app and
Machine check precedes success. API bodies and credentials are omitted from
error diagnostics; requests reject redirects and bound response sizes.

**Updates are not atomic.** A timeout or failure can leave some Machines running
the new image. There is no automatic retry or rollback. Inspect the app before
retrying; a single-Machine app can have downtime during restart. Rollout has a
five-minute total budget; leases last ten minutes and are released on handled
success/failure paths. A killed process or failed cleanup may leave leases until
expiry. Success confirms Machine state and health checks, not external DNS/TLS
or public reachability. Source files and previous local site output are retained.


## Railway

Current source supports `zel railway` (alias `rw`) and `zel deploy railway`
for an **existing image service in an explicit Railway environment**. It builds
one static or Next.js image for `linux/amd64`, pushes it to your registry, changes
the service's image source to that immutable digest, and waits for the returned
deployment to reach `SUCCESS`. Static and Next image deployment plus public
HTTP acceptance passed on 2026-11-10; the temporary project was removed afterward.
Candidate `0.2.0-rc.3` includes the live-tested preflight/startup fixes
described below.

```yaml title="zel.yaml"
version: 1
renderer: portable
image:
  name: ghcr.io/acme/manual:v1
publish:
  action: deploy
  provider: railway
  site: 33333333-3333-4333-8333-333333333333
  image: static
```

```bash title="terminal"
zel rw --prod --dry-run
zel rw --prod
zel rw --kind next --tag ghcr.io/acme/manual:v2 --prod
zel pub --prod
```

Replace the example service UUID and registry reference. `--site` overrides
`RAILWAY_SERVICE_ID`, which overrides same-provider `publish.site`. `--kind`
overrides same-provider `publish.image`, defaulting to `static`. `--tag` overrides
`image.name` and is the exact build/push tag; existing contents of that tag can
be replaced. Choose a new tag to retain an older registry tag. Deployment uses
the repository digest, so later changes to the tag do not change the deployed
source. Explicit `--platform` accepts only `linux/amd64`; saved image platform
settings are ignored for Railway.

### Railway setup

1. Build and push an initial image using `zel image static --tag <reference>`
   (or `zel image next`) followed by `zel image push <reference>`. Create the
   Railway service from that image in the intended project/environment.
2. Set the service variable `PORT=3000`, configure an HTTP healthcheck path
   that returns a successful response (usually `/`), and wait for a successful
   initial deployment. Leave `HOSTNAME` unset or set it to `0.0.0.0`.
3. Create a **project token for that environment**, and supply it through
   `RAILWAY_TOKEN`. Set `RAILWAY_PROJECT_ID` and `RAILWAY_ENVIRONMENT_ID` to the
   expected UUIDs. Account/workspace tokens and stored Railway CLI logins are
   not used. The command verifies the project token's scope before building.
4. Authenticate the selected container runtime to your image registry.
   Railway must also be able to pull the image: use a public image, or configure
   private registry credentials on the service using a Railway plan that
   supports them. Local registry login does not grant Railway pull access.

Image references require an explicit registry, repository and tag. Supported
registries are `ghcr.io`, `docker.io`, `registry.gitlab.com`, `quay.io`, and
`mcr.microsoft.com`. Supply credentials through environment variables or the
registry client's login flow; never save tokens in `zel.yaml`.

### Railway limits and failure behavior

`--prod` explicitly authorizes an update to the selected environment, even if
that environment is named staging. There is no implicit preview environment.
The service must already use an image source, have a successful deployment,
and have no mounted volumes, custom start/pre-deploy/cron commands, repository
configuration file, or application sleeping. Resolve staged environment changes
and other deployments first. The adapter supports an environment with at most
100 volume instances so it can verify a complete inventory. Current source
checks the explicit staged patch without decrypting its variable values. This
fix is included in `0.2.0-rc.3`. The adapter also waits while a new deployment
has no running instances, requiring running instances when it reaches
`SUCCESS`.

Only the environment-scoped image source is patched. Other service settings,
variables, domains, registry credentials and resources are retained; no project,
environment, service, domain or volume is created. A Git-connected service is not
converted. The service and runtime variables are checked before building and
again before the update. These API calls are **not an atomic lock**: avoid
concurrent dashboard edits or deployments. The command detects observed changes
and checks the selected deployment and service source again before reporting
success.

The provider phase has a five-minute deadline, individual requests are bounded,
and API response bodies/GraphQL errors are omitted from diagnostics. A failure
after the image push retains the image; a failure after the source update can
leave the new source configured or a deployment still running. No automatic
retry, rollback or cleanup of published images occurs. Inspect Railway before
retrying. `SUCCESS` reflects Railway's deployment result and startup healthcheck;
it does not prove public DNS/TLS, external reachability, ongoing health, or
independently attest the running container's digest.

See Railway's [API authentication](https://docs.railway.com/integrations/api),
[service API](https://docs.railway.com/integrations/api/manage-services), and
[startup healthchecks](https://docs.railway.com/deployments/healthchecks).
