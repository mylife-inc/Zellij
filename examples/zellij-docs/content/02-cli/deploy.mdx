`zel deploy netlify`, also `zel netlify`, builds and uploads static HTML from
portable Markdown or hosted content. The downloaded `zellij-v0.1.3` binary
predates these commands. Cloudflare Pages is available in current source; rc.1 does not include it.

```bash title="terminal"
zel netlify --site-id YOUR_PROJECT_ID --dry-run
zel netlify --site-id YOUR_PROJECT_ID          # draft preview
zel netlify docs/manual --site-id YOUR_PROJECT_ID --prod
```

No path selects the current directory's `zel.yaml`, then
`docs/zellij/zel.yaml`. Pass an explicitly named site root or legacy content
folder when needed. See [site discovery](/cli/config#site-layout-and-discovery).

## Set up Netlify

Create a Netlify project using Netlify's dashboard. Copy its **Project ID** and
generate a personal access token with access to that project. Supply the token
as `NETLIFY_AUTH_TOKEN` through your shell environment or CI secret store. Supply
the project ID with `--site-id`, the compatible `--site` spelling,
`NETLIFY_SITE_ID`, or saved settings. A full site domain such as
`acme-docs.netlify.app` also works; a bare display name is not a domain.

`zel` uses Netlify's HTTPS API directly. It requires no Netlify CLI or Node.js,
and portable rendering requires no container runtime. Hosted content still
requires a usable [Docker, Podman or nerdctl runtime](/cli/doctor) for its build.
Nothing is installed or started automatically. `zel` does not create a provider
project, run login, read another CLI's stored login, or load `netlify.toml`.

Token values belong in the environment, not `zel.yaml`, command arguments or
committed files. Missing credentials fail before building; a read-only API
request checks access to the selected project before the build starts. Both
preview and production deployment need network access and valid credentials.

## Cloudflare Pages

Current source adds `zel deploy cloudflare`, `zel cloudflare`, and the short
alias `zel cf`. These commands are not in the published rc.1 binary.

```bash
zel cf --site manual --dry-run
zel cf --site manual             # preview
zel cf docs/manual --site manual --prod
```

Use an **existing Pages project**. Set `CLOUDFLARE_ACCOUNT_ID` to its account ID
and `CLOUDFLARE_API_TOKEN` to an API token with **Account → Cloudflare Pages → Edit**
access for that account. Tokens stay in your environment or CI secret store.
`--site` / `--site-id` takes the project name, such as `manual`, not a `pages.dev`
URL. It overrides `CLOUDFLARE_PAGES_PROJECT_NAME`, then saved `publish.site`.
Read [Cloudflare's Direct Upload setup](https://developers.cloudflare.com/pages/get-started/direct-upload/)
and [CI token setup](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/)
for account-side configuration. `zel` neither creates projects nor installs or
invokes Wrangler. It does not load Wrangler configuration or stored credentials.

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: cloudflare
  site: manual
```

`zel pub` and bare `zel deploy` then use this destination. An explicit provider
change never inherits another provider's saved destination or environment ID.
The account ID remains an environment setting; it is not saved in `zel.yaml`.

**Preview is the default.** The command selects branch `zel-preview`, regardless
of your local Git branch. Repeated previews update that branch alias and receive
individual deployment URLs. If the project's production branch is named
`zel-preview`, preview deployment fails before building; change that project
setting first. `--prod` selects the production branch returned by project
preflight. The command waits for the deployment stage to succeed and reports
its HTTPS `pages.dev` URL, with the hosted base path when configured. Project
settings, access restrictions and concurrent deployments still govern live access.

Both renderers build once into temporary output. Portable builds need no Docker
or Node.js; hosted builds retain their container requirement. Hosted URL/feature
flags below also work with Cloudflare. Source files and previous local output
remain intact, and `ship --provider cloudflare --site manual` saves the converted
site's destination for later `pub` calls. The `--prod` choice is never saved by ship.

This adapter uploads generated **static assets**, with a maximum of 20,000 files
and 25 MiB per file. It hashes assets, skips already uploaded content and batches
missing uploads. Worker code, Functions and root `_headers`, `_redirects` or
`_routes.json` are rejected; custom platform rules and server-side Next apps are
outside this adapter. Symlinks, junctions and non-regular files are rejected,
as are asset paths containing `#`, `?`, backslashes or control characters.
Unicode, spaces and literal percent signs retain their filenames.

Cloudflare applies its [HTML route rules](https://developers.cloudflare.com/pages/configuration/serving-pages/),
including redirects from `.html` URLs to clean routes. Downloaded portable output
still supports direct-file navigation. No DNS or custom-domain changes are made.

Credentials and project access are checked before a build. API redirects are
refused, errors omit response bodies and tokens, and requests have bounded
connection/request/deployment timeouts. Failed requests are not retried
automatically. An uncertain create response may already have published; check
the Cloudflare dashboard before repeating a command. Tests cover the upload
protocol and generated exports; live Cloudflare account acceptance remains pending.

## Save the choice

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
publish:
  action: deploy
  provider: netlify
  site: acme-docs.netlify.app
```

```bash title="terminal"
zel pub --dry-run
zel pub              # build once, then create a draft preview
zel pub --prod       # request production publication
zel deploy           # same saved plan and options as publish
```

`publish.site` is optional if you supply the destination elsewhere. Destination
precedence is `--site-id` / `--site`, then `NETLIFY_SITE_ID`, then `publish.site`.
The value must be a string containing an existing project ID or domain. Saved
settings never contain a token or automatically enable production publication.

Explicit `deploy netlify` supplies deployment intent even when there is no
saved publication, or when the saved plan describes an image push. `pub --to
netlify` also supplies explicit provider intent, but rejects a saved image-push
plan: it cannot silently replace a selected container artifact. `--tag` is
invalid for Netlify. Ordinary build/image commands never deploy.

## Preview and production

The default is a **draft preview** with its own deployment URL. Use `--prod` to
request an update to the live site. The command prints the deployment ID and
its HTTPS preview URL once Netlify reports `ready`; hosted basePath is appended
to that URL. Site locks or a newer concurrent deployment can affect which deploy
is current in production; the dashboard is authoritative for that status.

A dry run prints the site, renderer, destination and publication mode. It does
not read a token, contact a runtime or provider, validate content, build, or
write output. It is a plan, not a successful deployment check.

## Build and upload

The command validates and builds with the selected renderer exactly once into
a private temporary export. It leaves existing `site/`, configured `build.out`,
source and configuration intact. Portable output retains its direct-file
navigation. Hosted output is placed at the engine-resolved basePath, including
prefixes with hidden segments such as `/products/.docs`. Its temporary directory
is created beside the selected content, on the same project filesystem shared
with the runtime; that parent directory must be writable.

The upload manifest contains generated HTML and public assets, excluding the
local export ownership marker. It uses file digests, uploads only the bytes
Netlify requests, and waits for processing to finish. Files with identical
bytes need only one upload. This path publishes static files, without a remote
build, Next server, serverless functions, image push or browser launch.

Paths with `#`, `?`, backslashes or control characters are rejected before
creating a deployment, following Netlify's file-upload constraints. Spaces and
Unicode are URL-escaped. Symlinks and junctions in the export are rejected.

## Failures and retry

| Failure | Exit code |
| --- | --- |
| Invalid settings, incompatible options, missing token/site | `2` |
| Content/build failure or unsuccessful API deployment | `3` |
| Hosted runtime unavailable or unshared mount | `4` |
| Local filesystem/process error | `1` |

A failed build creates no deployment. Once a build succeeds, an upload or
processing failure reports that stage and keeps previous local output intact.
Temporary exports are removed on success or failure. Requests are bounded to
60 seconds (15 seconds to connect), and the create/upload/poll phase has a
five-minute budget. Failed requests are not automatically retried.

An interrupted request or timeout may already have created a deployment, and
Netlify may still finish it. Check the printed deployment ID or the Netlify
dashboard before rerunning. Rerunning builds a fresh export and creates a new
deployment; automatic resume, rollback and deletion are not implemented.
Provider errors report status and remediation without echoing response bodies
or credentials. Authentication redirects are refused.

## Temporary feature selection

```bash title="terminal"
zel netlify --site-id YOUR_PROJECT_ID --features all --dry-run
zel netlify --site-id YOUR_PROJECT_ID --features all
```

`--features` selects `maths`, `diagrams`, `maths,diagrams`, `all`, or `none` for
this deployment's build. It works for portable and hosted sites, including
saved `zel pub` deployment plans. The uploaded HTML uses that selection;
source, configuration and previous local output remain unchanged. A later
invocation without the flag uses saved/default features again. Explicit `none`
disables both optional renderers, even when they are enabled by default.

## Hosted URL and preflight overrides

The current source accepts the hosted [build overrides](/cli/build#hosted-url-and-validation-overrides)
with `netlify`, `deploy netlify`, and saved `publish`/`deploy` commands:

```bash
zel netlify docs/hosted --site-id YOUR_PROJECT_ID --base-path /manual --site-url https://docs.example.com --dry-run
zel netlify docs/hosted --site-id YOUR_PROJECT_ID --base-path /manual --site-url https://docs.example.com
```

The override controls uploaded paths, canonical URLs, sitemap and robots
metadata. The reported preview URL includes the actual exported prefix. Use
`--base-path /` to clear a saved prefix. The public origin is an SEO setting;
it does not create or move a Netlify domain or change which project receives
the deployment. Draft previews remain the default.

`--no-check` skips the separate content preflight. Netlify credentials and site
access are still checked before building; preparation and rendering still
validate content. A failed build creates no remote deployment and retains the
previous local output. Portable Netlify output rejects these three flags.
Authored configuration remains unchanged. These flags require a current CLI
and compatible engine; candidate `0.2.0-rc.1` does not include them.

## Options

| Option | Meaning |
| --- | --- |
| `[provider]` | `netlify` or `cloudflare`; omit to execute saved publication settings |
| `[site]` | Site root, using normal discovery when omitted |
| `--site-id <destination>` | Netlify ID/domain or Cloudflare project name; `--site` is equivalent |
| `--prod` | Request live publication instead of a draft preview |
| `--features <selection>` | Complete rendering selection for this build only; saved settings stay unchanged |
| `--base-path <path>` | Hosted deployment prefix for this invocation; `/` clears it |
| `--site-url <origin>` | Hosted public HTTP(S) origin for canonical URLs and SEO metadata |
| `--no-check` | Skip content preflight; retain preparation, rendering and credential checks |
| `--dry-run` | Resolve and print the plan only |
| `--to <provider>` | Explicit provider for saved static deployment |
| `--tag <reference>` | Only valid for saved image publication via bare `deploy` or `publish` |

`--json`, `--target`, `--message`, and `--preview` are not supported. Preview is
the default. Vercel, GitHub Pages, S3, Fly and Railway remain future
adapters; they are not aliases for Netlify.

See [`zel publish`](/cli/publish) for image registry publication and
[`zel ci`](/cli/ci) for workflow generation from saved delivery settings.

## Image build arguments

Current source accepts `--build-arg NAME=VALUE` only when bare `zel deploy` selects
saved image publication. `zel netlify`, `deploy netlify` and saved Netlify delivery
reject it before credentials, building or remote requests. See
[image build arguments](/cli/image#image-build-arguments).
