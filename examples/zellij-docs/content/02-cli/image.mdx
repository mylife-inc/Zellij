---
title: zel image
description: Build a static-site image or a Next.js image, then run or push it.
---

`zel image static` (shortcut `zel si`) builds HTML from portable Markdown or
hosted content and packages it with NGINX. `zel image build` retains the existing
Next.js application image for hosted content. The separate `image next` / `ni`
command and its plain-Markdown adapter are still planned.

These static-image commands are available in current source and require a new
binary release. Run `zel image --help` to check your installed version.

## `zel image static`

```bash title="From your software repository"
zel si
zel image run zellij-static:latest --port 8080
```

With no path, the command selects `./zel.yaml`, then
`./docs/zellij/zel.yaml`. An arbitrary site folder or an existing Markdown
folder can be supplied explicitly:

```bash
zel image static docs/manual --tag acme-docs:static
zel si ./markdown-files --tag acme-docs:static
zel ir acme-docs:static --port 8080
```

| Option | Meaning | Default |
| --- | --- | --- |
| `[site]` | Configured site root, or an explicit legacy content folder | Current site or `docs/zellij` |
| `--tag <reference>` | Image name and tag | `<site-name>-static:latest` |

The generated name uses the selected folder's name, lowercases ASCII letters,
and replaces runs of other characters with hyphens. A name with no ASCII
letters or digits uses `zellij-site`. Long names are shortened. The `-static`
suffix keeps this image separate from the existing Next image default. An
explicit `--tag` takes precedence.

For **portable Markdown**, Rust generates the same HTML, navigation, search,
theme, branding, and referenced assets as `zel build`. The temporary export is
removed after packaging, including on failure. Existing `site/` output and
`build.out` are untouched; run `zel build` separately if you also want an export
on disk. That export continues to work through `file://` without a server.

For **hosted YAML/MDX**, the Next.js builder validates content and produces a
static export inside the image build. Only the export reaches the final image.
The content's `basePath` is preserved: with `basePath: /products/docs`, open
`http://localhost:8080/products/docs/`. Hosted exports retain their HTTP
requirements and static-export limitations.

Both images use [NGINX's unprivileged Alpine image](https://github.com/nginx/docker-nginx-unprivileged),
listen on container port **3000**, and run as the `nginx` user. The HTTP server
serves direct HTML files, extensionless hosted routes, directory indexes, and
assets. Unknown routes return 404. A health check requests the exported index.
No push or deployment happens during a build.

Building requires a usable Docker, Podman, or nerdctl runtime, even when the
HTML itself is generated natively. A missing or unavailable runtime stops the
command with exit code **4**, before generating the export. The command does
not install or start a runtime or switch renderers. See [`zel doctor`](/cli/doctor).
Container image downloads and hosted dependency installation may require network
access. On macOS and Windows, the runtime must support Linux containers.

## `zel image build`

```bash
zel image build docs/hosted --tag acme-docs:next
# Equivalent compatibility spelling:
zel build docs/hosted --target image --tag acme-docs:next
```

These existing commands continue to accept hosted content and produce the
Next.js standalone application, with Node and its traced dependencies. They
retain the original `<site-name>:latest` default; they never select the new
static image implicitly. Portable sites need the planned Markdown-to-Next
adapter and are rejected by this path today.

The generated multi-stage recipe copies the selected content into the wrapper,
installs dependencies, checks content, builds Next, then copies the standalone
server, static chunks, and public assets into a Node 24 Alpine runtime. The
server runs without root on port 3000.

`--platform`, `--features`, and `--build-arg` are not implemented CLI options yet.

## `zel image run`

```bash
zel image run acme-docs:static --port 8080
zel ir acme-docs:next
```

Both image kinds work with this command. It publishes container port 3000 to
`--port` on your machine (default 3000), streams logs, and stops on Ctrl-C.

For compatibility, omitting the tag still derives the **legacy Next** default
from the selected hosted site. It does not remember the last image built or a
custom `--tag`, and it does not select the `-static` image. Pass the static tag
explicitly, as shown in the successful build's output.

## `zel image push`

```bash
zel image push acme-docs:static --registry ghcr.io/acme
zel ip acme-docs:next --registry ghcr.io/acme
```

This explicitly tags and pushes the image. Authentication belongs to your
container runtime and registry, such as `docker login`; `zel` does not store
registry credentials. No repository or cloud deployment is created.

## `zel image dockerfile`

`zel image dockerfile` / `zel idf` prints a recipe without runtime detection,
image downloads, or builds. `--kind static` selects the static recipe for the
site's renderer. `--kind next` and the omitted kind retain the Next recipe.
The static recipe's comment names its required build context.

For a portable site, **build the HTML first** and pass that export as the Docker
build context:

```bash
zel build docs/zellij
zel idf docs/zellij --kind static > Dockerfile.static
docker build -f Dockerfile.static -t acme-docs:static docs/zellij/site
```

If `build.out` changes the export location, use that location in the last
command. Do not pass the Markdown folder or site root to this recipe.

For hosted content, the recipe includes the HTML build. Pass **content/** as
its context:

```bash
zel idf docs/hosted --kind static > Dockerfile.static
docker build -f Dockerfile.static -t acme-docs:static docs/hosted/content

zel idf docs/hosted --kind next > Dockerfile.next
docker build -f Dockerfile.next -t acme-docs:next docs/hosted/content
```

For an explicit legacy hosted folder, use that folder directly as the context.
A saved Dockerfile no longer tracks future recipe changes; regenerate it when
upgrading the CLI.

## The base image

`ZELLIJ_IMAGE` overrides the hosted builder image (default
`ghcr.io/mylife-inc/zellij-base:latest`) for both Next and hosted-static builds.
It has no effect on portable compilation or the static NGINX runtime.

The hosted builder carries the Zellij engine at `/opt/zellij` and a generated
Next wrapper at `/app`. Dependencies install during the site build. The
static runtime currently uses `nginxinc/nginx-unprivileged:stable-alpine`;
custom runtime-base selection is not yet a CLI option. For a separately managed
Dockerfile, pin image digests when you need fixed base versions.
