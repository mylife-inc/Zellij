---
title: zel image
description: Build a static-site image or a Next.js image, then run or push it.
---

`zel image static` (shortcut `zel si`) builds HTML from portable Markdown or
hosted content and packages it with NGINX. `zel image next` (shortcut `zel ni`)
packages either renderer in a Next.js application image. `zel image build`
retains its existing hosted-content behavior and default tag.

These image commands are available in candidate `0.2.0-rc.1`. Select its matching
engine image as shown in [installation](/cli). Run `zel image --help` to check
your installed version.

## `zel image static`

```bash title="From your software repository"
zel si
zel image run zellij-static:latest --port 8080
```

With no path, the command selects `./zel.yaml`, then
`./docs/zellij/zel.yaml`. An arbitrary site folder or an existing Markdown
folder can be supplied explicitly:

```bash
zel image static docs/manual --tag acme-docs:static
zel si ./markdown-files --tag acme-docs:static
zel ir acme-docs:static --port 8080
```

| Option | Meaning | Default |
| --- | --- | --- |
| `[site]` | Configured site root, or an explicit legacy content folder | Current site or `docs/zellij` |
| `--tag <reference>` | Image name and tag | `image.name`, then `<site-name>-static:latest` |
| `--features <selection>` | Complete selection for this image build | Existing renderer defaults |
| `--platform <platform>` | `linux/amd64` or `linux/arm64` | `image.platform`, then runtime default |

The generated name uses the selected folder's name, lowercases ASCII letters,
and replaces runs of other characters with hyphens. A name with no ASCII
letters or digits uses `zellij-site`. Long names are shortened. The `-static`
suffix keeps this image separate from the existing Next image default. An
explicit `--tag` takes precedence over `image.name` in a versioned `zel.yaml`,
then the generated default. The configured name is shared by both image kinds;
use separate tags explicitly when keeping both. See [image settings](/cli/config#image-and-publication-settings).

For **portable Markdown**, Rust generates the same HTML, navigation, search,
theme, branding, and referenced assets as `zel build`. The temporary export is
removed after packaging, including on failure. Existing `site/` output and
`build.out` are untouched; run `zel build` separately if you also want an export
on disk. That export continues to work through `file://` without a server.

For **hosted YAML/MDX**, the Next.js builder validates content and produces a
static export inside the image build. Only the export reaches the final image.
The content's `basePath` is preserved: with `basePath: /products/docs`, open
`http://localhost:8080/products/docs/`. Hosted exports retain their HTTP
requirements and static-export limitations.

Both images use [NGINX's unprivileged Alpine image](https://github.com/nginx/docker-nginx-unprivileged),
listen on container port **3000**, and run as the `nginx` user. The HTTP server
serves direct HTML files, extensionless hosted routes, directory indexes, and
assets. Unknown routes return 404. A health check requests the exported index.
No push or deployment happens during a build.

Building requires a usable Docker, Podman, or nerdctl runtime, even when the
HTML itself is generated natively. A missing or unavailable runtime stops the
command with exit code **4**, before generating the export. The command does
not install or start a runtime or switch renderers. See [`zel doctor`](/cli/doctor).
Container image downloads and hosted dependency installation may require network
access. On macOS and Windows, the runtime must support Linux containers.

## `zel image next`

```bash
zel ni
zel ir zellij-next:latest --port 8080
zel image next docs/manual --tag acme-docs:next
```

Site selection and `--tag` work like `image static`, with a distinct
`<normalized-site-name>-next:latest` default when `image.name` is absent. The result is a Next.js standalone
server running as `nextjs` on container port 3000. It needs an HTTP server;
use `zel build` for a portable export you can open directly from disk.

For portable Markdown, the command validates and adapts the content in a
private temporary folder. It preserves all discovered pages, including pages
omitted from custom navigation; nested groups, separate navigation labels,
external navigation links, page titles and descriptions, theme, company logo
and destination, heading IDs, footnotes, tables, task lists, code, and referenced
images/downloads. Root `index.html` becomes `/`; other document paths keep their
`.html` suffix, including nested `index.html`, so distinct source files stay
distinct. Document links, queries and fragments are rewritten accordingly.

Raw HTML and JavaScript-looking prose remain literal text. The Next renderer
uses its own guide layout, syntax highlighting, maths and diagram presentation;
this is not a pixel-identical copy of the portable page. `markdown.math` and
`markdown.mermaid` still control those features, and required optional packages
are enabled during the image build. Unknown code languages remain readable
plain text. All pages enter search; headings retain their anchors and TOC links.

Adapted content is removed after success or failure. Original Markdown,
`zel.yaml`, existing `site/`, and configured `build.out` remain untouched. For
hosted YAML/MDX, the existing content goes directly into the Next builder.
Its `basePath` is preserved, including in the container health check.

Both image kinds require a working Linux container runtime before any temporary
build output is created; unavailable runtimes return exit code **4**. No runtime
is installed or started automatically, and no image is pushed implicitly.

## `zel image build`

```bash
zel image build docs/hosted --tag acme-docs:next
# Equivalent compatibility spelling:
zel build docs/hosted --target image --tag acme-docs:next
```

These existing commands continue to accept hosted content and produce the
Next.js standalone application, with Node and its traced dependencies. They
retain the original `<site-name>:latest` default; they never select the new
static image implicitly. These compatibility commands remain hosted-only;
use `zel ni` for portable Markdown. These compatibility paths do not read the
new `image.name` setting.

The generated multi-stage recipe copies the selected content into the wrapper,
installs dependencies, checks content, builds Next, then copies the standalone
server, static chunks, public assets, and the selected content needed for
server-side route resolution into a Node 24 Alpine runtime. The
server runs without root on port 3000. The final runtime excludes npm, Yarn and
Node development headers; they remain available in the builder. Required Alpine
libraries, certificates, licenses and the shell used by health checks are kept.
Static images use the smaller NGINX Alpine slim variant without optional dynamic
modules. Both recipes keep compilation tools and build caches out of the final
image; Next copies only its traced production dependencies.

## Select the image platform

All image build forms, including `si`, `ni`, `image build`, and
`build --target image`, accept one Linux target architecture:

```bash
zel si --platform linux/arm64
zel ni --platform linux/amd64
```

Save a default in the selected version-1 `zel.yaml` to keep commands short:

```yaml
image:
  platform: linux/arm64
  name: ghcr.io/acme/docs:latest
```

`image.name` is optional for local builds. Publication still requires an explicit
name or `--tag`. `--platform` overrides `image.platform`; omitting both uses the
container runtime's default. The legacy Next build forms read `image.platform`
while retaining their existing tag rules. Platform selection applies to every
Dockerfile stage, including its base images.

Local builds accept `linux/amd64` and `linux/arm64`. These describe the container,
not the OS running `zel`: native Windows and macOS CLIs also build Linux images.
Other operating systems and architecture abbreviations are rejected before a build.

Current source also supports `all` for registry publication (requires 0.2.0-rc.2
or later, still unpublished). With saved publication settings:

```bash
zel pub --platform all
zel ci --platform all
```

This publishes one tag containing both Linux architectures. A client pulls only
the architecture it needs, not both images. Save `image.platform: all` to make
`zel pub` use it by default. The explicit comma list `linux/amd64,linux/arm64`
(or reversed order) is equivalent. Local-only image commands reject this selection;
override it with one architecture when building an image to run locally.

Docker uses the selected Buildx builder with direct registry output; Podman
builds an isolated temporary manifest and pushes all its images; nerdctl uses its
BuildKit image exporter. Authenticate with the selected client first. The builder
must support both architectures and each base image must provide both. Zel does
not create a builder, install emulation, or change runtime connections.

Combined publication does not promise a local image tag. If it fails, uploaded
layers may already exist: inspect the registry, fix the reported problem, and
retry `zel pub`. Podman's temporary manifest is removed after the attempt.
[`zel ci`](/cli/ci) uses native AMD64 and ARM64 runners and combines their
published digests only after both builds succeed.

Foreign-architecture `RUN` steps require a builder with emulation or native
support, and every base image must provide the requested platform. A failed
build preserves the runtime's diagnostic and explains these prerequisites;
Zellij does not install emulators or start daemons. See the
[Docker platform guide](https://docs.docker.com/build/building/multi-platform/)
and [Podman platform option](https://docs.podman.io/en/latest/markdown/podman-build.1.html#platform-os-arch-variant).

Docker, Podman and nerdctl receive the same single-platform selection. Podman
uses its native progress output. A nerdctl push uploads all content in the local
image, preserving a selected architecture even when it differs from the host;
see the [nerdctl command reference](https://github.com/containerd/nerdctl/blob/main/docs/command-reference.md).

## Feature selection for one image

```bash
zel si --features maths
zel ni --features all
zel image build docs/hosted --features none
zel image dockerfile docs/hosted --kind static --features diagrams
```

All image build forms and their aliases accept the same complete
[`--features` selection as build](/cli/build#temporary-feature-selection).
Portable static images compile the selected features natively; portable Next
images adapt the selected Markdown and configure the hosted dependencies to
match. Hosted static and Next images apply the selection inside the builder
before installation. `none` explicitly disables both features even when the
chosen base image enables them. Omission preserves portable settings/inferred
requirements or the hosted base image's default.

Hosted Dockerfile generation also accepts the option without requiring a runtime.
A portable static Dockerfile packages already generated HTML, so it rejects this
flag: apply it with `zel build` or `zel si` instead. Source files are unchanged;
ordinary image builds never push automatically. Use `zel ip <tag>` to publish an
image you built with an override. Delivery and CI generation also accept
`--features`; see [publication](/cli/publish#temporary-feature-selection) and
[CI generation](/cli/ci). A generated workflow keeps that selection until regenerated.

## Image build arguments

Current source (after candidate `0.2.0-rc.1`) accepts repeatable `--build-arg
NAME=VALUE` flags on `si`, `ni`, `image static`, `image next`, legacy `image build`
and `build --target image`:

```bash
zel ni --build-arg NODE_OPTIONS=--max-old-space-size=4096
zel si docs/hosted --build-arg NPM_CONFIG_FETCH_RETRIES=5
zel pub --build-arg NODE_OPTIONS=--max-old-space-size=4096
```

Each argument needs an explicit `=`; `NAME=` passes an empty value. Names use
ASCII letters, digits and underscores, with no leading digit. Values may contain
spaces, Unicode, additional `=` signs and shell-looking text when quoted for your
shell, but not control characters. A repeated name uses its last value. Zellij
does not look up omitted values from your environment or save these settings to
`zel.yaml`. A subsequent command without the flags uses the normal defaults.

The CLI passes values directly to Docker, Podman or nerdctl. It declares names
in the generated builder stage so install/build scripts and a custom engine can
consume them. They have an effect only when a build tool or script reads them;
there is no automatic content-variable substitution. For portable static images,
arguments affect container packaging, not the preceding native Markdown build.
Hosted images do not declare them in their separate runtime stage, and Zellij
does not turn them into runtime `ENV` settings. Builders may still retain values
in image history, provenance or generated files: use these flags for non-secret
build configuration, not tokens or passwords. See
[Docker build-variable semantics](https://docs.docker.com/build/building/variables/).

Proxy arguments (`HTTP_PROXY`, `HTTPS_PROXY`, `FTP_PROXY`, `ALL_PROXY`, `NO_PROXY`,
including lowercase forms) and `BUILDKIT_*` controls are forwarded without extra
`ARG` declarations, preserving the builder's predefined behavior. Zellij-owned
`ZELLIJ_*` settings, the historical `FEATURES` name and automatic `BUILD*`/`TARGET*`
platform variables are reserved. Use the dedicated `--features`, URL/preflight
and `--platform` flags for those settings.

`idf` / `image dockerfile` also accepts build arguments, for either supported
recipe kind. Its output declares **names only**; it does not embed supplied values.
When building that recipe yourself, supply the values again with the container
client's `--build-arg` flags. Dockerfile generation requires no runtime.

Image publication (`pub`, `publish`, saved image `deploy`) and image `ship` carry
arguments through the single build before pushing. Dry runs list names while
omitting values. Failures do not attempt a push; a failed `ship` retains converted
content and explains that the arguments must be repeated. Static-folder builds,
Netlify delivery and Netlify `ship` reject the option before output or remote work.
Prebuilt `image push` / `image run` do not accept build arguments. For generated
workflows, see [CI build arguments](/cli/ci#freeze-image-build-arguments).

## Hosted URL and validation overrides

```bash
zel si docs/hosted --base-path /manual --site-url https://docs.example.com
zel ni docs/manual --base-path /manual --site-url https://docs.example.com
zel ni docs/hosted --base-path / --no-check
zel idf docs/hosted --kind next --base-path /manual
```

Hosted static images, Next.js images, legacy `image build` / `build --target image`,
and hosted Dockerfile generation support [`--base-path`, `--site-url` and
`--no-check`](/cli/build#hosted-url-and-validation-overrides). `si` and `ni` keep
their short syntax. A Next.js image built from portable Markdown supports these
options after conversion; a portable static image rejects them. A standalone
portable static Dockerfile packages already generated relative-link HTML and
rejects them too.

The chosen prefix governs routes, assets and the image's health check. Next.js
images retain the same settings at runtime, including when an unknown URL needs
content loading before returning 404. The public origin affects canonical links,
sitemap and robots metadata. Settings stay in the generated artifact; authored
files are unchanged. `/` explicitly clears a saved prefix, and `--no-check`
only skips the separate preflight, leaving preparation and rendering validation
enabled. These options require a current engine image. Ordinary builds remain
local to the runtime; use `zel ip <tag>` to push a completed image.

## `zel image run`

```bash
zel image run acme-docs:static --port 8080
zel ir acme-docs:next
```

Both image kinds work with this command. It publishes container port 3000 to
`--port` on your machine (default 3000), streams logs, and stops on Ctrl-C.

For compatibility, omitting the tag still derives the **legacy Next** default
from the selected hosted site. It does not remember the last image built or a
custom `--tag`, and it does not select the `-static` or `-next` suffix. Pass the
new image tag explicitly, as shown in the successful build's output.
Omitted-tag `image run` also retains its legacy behavior when `image.name` is set.
Use `--site-root docs/hosted` to select that hosted site explicitly; it conflicts
with an explicit image tag. `--cwd` sets the working directory for all image
commands, while image push accepts a tag and rejects `--site-root`.

## `zel image push`

```bash
zel image push acme-docs:static --registry ghcr.io/acme
zel ip acme-docs:next --registry ghcr.io/acme
```

This explicitly tags and pushes the image. Authentication belongs to your
container runtime and registry, such as `docker login`; `zel` does not store
registry credentials. No repository or cloud deployment is created.
For a fully qualified reference, use `zel ip ghcr.io/acme/manual:v1` without
`--registry`. [`zel pub`](/cli/publish) combines one image build and a push using
saved settings; ordinary image builds never publish implicitly.

## `zel image dockerfile`

`zel image dockerfile` / `zel idf` prints a recipe without runtime detection,
image downloads, or builds. `--kind static` selects the static recipe for the
site's renderer. `--kind next` and the omitted kind retain the Next recipe.
The static recipe's comment names its required build context.

For a portable site, **build the HTML first** and pass that export as the Docker
build context:

```bash
zel build docs/zellij
zel idf docs/zellij --kind static > Dockerfile.static
docker build -f Dockerfile.static -t acme-docs:static docs/zellij/site
```

If `build.out` changes the export location, use that location in the last
command. Do not pass the Markdown folder or site root to this recipe.

For hosted content, the recipe includes the HTML build. Pass **content/** as
its context:

```bash
zel idf docs/hosted --kind static > Dockerfile.static
docker build -f Dockerfile.static -t acme-docs:static docs/hosted/content

zel idf docs/hosted --kind next > Dockerfile.next
docker build -f Dockerfile.next -t acme-docs:next docs/hosted/content
```

For an explicit legacy hosted folder, use that folder directly as the context.
A saved Dockerfile no longer tracks future recipe changes; regenerate it when
upgrading the CLI. Next Dockerfile output requires hosted content. For portable
Markdown, use `zel ni`, which owns the temporary adaptation and image build.

## The base image

`ZELLIJ_IMAGE` overrides the hosted builder image (default
`ghcr.io/mylife-inc/zellij-base:latest`) for both Next and hosted-static builds.
It also supplies the Next wrapper for adapted portable Markdown. It has no
effect on native static compilation or the static NGINX runtime. Portable Next
images require a builder that supports the current CLI's generated documents;
use the current Zellij base image when upgrading the CLI.

The hosted builder carries the Zellij engine at `/opt/zellij` and a generated
Next wrapper at `/app`. Dependencies install during the site build. The
static runtime currently uses `nginxinc/nginx-unprivileged:stable-alpine-slim`;
custom runtime-base selection is not yet a CLI option. For a separately managed
Dockerfile, pin image digests when you need fixed base versions.
