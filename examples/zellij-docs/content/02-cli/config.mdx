<Callout type="tip" title="Available in source">
Versioned `zel.yaml` selects a portable or hosted site with separate `content/`
and `site/` folders. Native release packages may lag this source version.
</Callout>

## Site layout and discovery

```text
my-product/
  docs/
    specs/
    zellij/             # Any folder name is allowed
      zel.yaml
      content/          # Markdown/assets, or hosted YAML/MDX
      site/             # Generated output
```

With no directory argument, deploy/netlify/publish, build/check/view/serve/dev and image static/next/build/dockerfile
first look for `./zel.yaml`, then `./docs/zellij/zel.yaml`. They do not search
parents or recursively scan the repository. A custom folder is explicit:
`zel build docs/manual`. A missing default reports the expected config path.
From inside `content/`, change to its parent or pass that parent explicitly.

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
name: Acme documentation
build:
  out: site
preview:
  port: 3000
```

Only `version` and `renderer` are required. The integer version is `1`, source is
always `content/`, output defaults to `site/`, and preview port defaults to 3000.
Set the port to `0` to choose an available port. `--out` and `--port` override
configuration. CLI paths are relative to the working directory; `build.out` is
relative to `zel.yaml` (an absolute path is also accepted). Existing overlap and
output-ownership protections still apply.

Hosted sites use `renderer: hosted`. Their `zel.yaml` accepts only `version`,
`renderer`, `build`, `preview`, `image`, and `publish`; put name, theme, navigation and branding in
`content/site.yaml` and the hosted content files. Renderer mismatches fail with
an explanation. `dev` is currently hosted-only; `view` is currently portable-only.
For a hosted static preview, use `build` followed by `serve`.

An explicit raw Markdown or hosted content folder remains supported. Existing
flat portable configurations without `version` keep their original meaning:
Markdown and `zel.yaml` share one folder, and the default native output is its
sibling `<folder>-site`. Use an explicit `.` for an unconfigured current folder.
Existing files are never moved into the new layout automatically. For hosted
legacy roots, explicit `.` retains the old content-discovery order.

## Portable Markdown

Add the following presentation settings to a portable site’s `zel.yaml`.
Navigation and logo paths are relative to `content/`. The file sets
site identity, initial theme, a company logo/link, and documentation navigation.
It does not require Node, Docker, or an internet connection.

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
name: Acme documentation
theme: forest
brand:
  logo:
    src: assets/company.svg
    alt: Acme company
    href: https://example.com
nav:
  - page: README.md
    label: Overview
  - label: Getting started
    children:
      - page: guide/install.md
        label: Installation
      - page: guide/configuration.md
  - label: Company website
    href: https://example.com
```

```bash title="terminal"
zel build
zel view --watch
zel build --name "Release documentation" --theme cupertino
```

### Selecting settings

`--name` and `--theme` override their respective file settings. If a setting is
absent from both flags and the file, the site name defaults to the source folder
name and the theme to `cupertino`.
Run `zel list themes` for accepted theme names. The complete configuration must
be valid, even when flags override some settings.

The selected site's configuration controls rendering. A versioned hosted config
cannot be forced through the portable renderer by `--target portable`. For an
explicit legacy raw folder without a configuration, `--target` can still select
the renderer. The complete config must be valid even when flags override settings.

### Mathematics

Math is disabled by default so dollar-sign prose keeps its existing meaning.
Enable it with a YAML boolean:

```yaml title="docs/zel.yaml"
markdown:
  math: true
```

Use `$...$` for inline equations and `$$...$$` for display equations. The
[portable math contract](/cli/build#mathematics) describes syntax, offline
rendering, validation, and supported limits. This is independent of hosted
Zellij's `features.maths` setting. `view --watch` rereads it after config edits.

### Mermaid

Enable Mermaid independently with `markdown: {mermaid: true}`, or put both
`math: true` and `mermaid: true` under `markdown`. Mermaid is disabled by default.
Its [local browser renderer](/cli/build#mermaid-diagrams) works offline, retains
readable source, and reports diagram syntax errors in the browser. Native
`zel check` validates source limits rather than Mermaid grammar.

### Navigation

`nav` is an ordered list. Each entry contains exactly one of:

| Field | Meaning | Label |
| --- | --- | --- |
| `page` | Exact Markdown source path relative to the content source | Optional; defaults to the document title |
| `children` | Another list of entries forming a group | Required |
| `href` | An absolute `http://` or `https://` link | Required |

Groups can nest up to 16 levels and must not be empty. Page paths include their
`.md` or `.markdown` extension and use `/` separators. Write spaces and Unicode
characters as they appear in filenames; these fields are filesystem paths, not
percent-encoded URLs. Missing pages, repeated page entries, traversal, and an
entry containing both `page` and `href` are errors.

Sidebar links and previous/next links follow the configured page order, walking
groups in order and skipping external links. Labels affect navigation; the
page's authored heading, HTML title and search title remain unchanged.
Breadcrumbs continue to describe source folders. If there is no root index or
README, the generated home lists the configured navigation.

All discovered Markdown documents are still validated, built, and searchable.
Omitting a page from `nav` removes it from sidebar and previous/next navigation;
it does not exclude or protect its content. Such pages remain reachable through
ordinary links and search. `nav: []` intentionally removes navigation links.
Omitting `nav` retains the automatic ordering described in [build](/cli/build).

### Company branding

`brand.logo.src` names a local image inside the Markdown folder. The builder
copies it into the export, using relative links that still work after moving
or opening the site directly. Remote logo sources, hidden paths, `node_modules`,
the reserved `_zellij` directory,
symlinks and Windows junctions are refused. `alt` is required, nonempty text.
Use an image format supported by your target browsers, such as SVG, PNG or WebP.

The logo appears at the left of the sticky header. Its optional `href` opens the
company's absolute HTTP(S) website; without it, the logo links to the docs home.
The site name beside it always links home. Search and theme controls remain on
the right. No external request occurs merely from displaying the company link;
visiting an external website requires connectivity.

### Editing and validation

Unknown keys, duplicate YAML keys, incorrect value types, invalid theme names,
and invalid navigation or branding fail before replacing the previous export.
Names, labels, alt text and paths must be YAML strings; quote values such as
`"2026"` if they should be text. The config file is not automatically published.
Source and output ownership rules are the same as for an unconfigured build.

`view --watch` notices config creation, edits, deletion, and logo changes. Invalid
edits keep the last working site and show the preview error notice. Fixing the
file rebuilds and reloads. Deleting a versioned config or changing its layout or
renderer reports an error and retains the last good preview; restore the config
or restart the command. Deleting a legacy flat config restores its defaults.
CLI overrides stay in effect. Output and port are fixed when preview starts;
restart to apply changes to `build.out` or `preview.port`.

An explicit visitor theme/appearance choice takes precedence over the site's
initial theme and survives navigation. Merely loading a default no longer saves
it as a visitor choice, so config theme changes can appear on reload. Preferences
saved by older exports may reset once when switching to this explicit-choice
format.

Portable settings do not load MkDocs plugins, `mkdocs.yml`, hosted navigation,
or a TOML defaults file. Use [`zel check --strict`](/cli/check) to validate a
configured portable site without writing an export; add `--json` for a structured
report. Use [`zel new portable`](/cli/new) for a working starter.

## Image and publication settings

Both renderers accept these additional fields in a versioned `zel.yaml`:

```yaml
image:
  name: ghcr.io/acme/manual:v1
publish:
  action: push
  image: static
```

`image.name` is a taggable image reference: an optional registry and port,
lowercase repository path, and optional tag. URL schemes, credentials, digests,
whitespace and malformed names are rejected. `image.name` must be a YAML string.
It supplies the default for `image static` / `si` and `image next` / `ni`;
`--tag` takes precedence. Both kinds use the same configured name, so choose
separate tags explicitly when retaining both. Without this field, local builds
retain their separate `-static` and `-next` generated defaults.

For `publish.action: push`, `publish.image` must be `static`
or `next`. [`zel publish` / `zel pub`](/cli/publish) builds and pushes that image;
it requires `image.name` or an explicit `--tag` and never chooses a generated
local name as a remote destination. There are no new environment overrides for
these settings. `ZELLIJ_IMAGE` still selects the **builder engine image**, not the
image being produced or published.

Saved delivery has no effect on ordinary `build`, `si` or `ni`: those commands
never push. Legacy `image build`, `build --target image`, and omitted-tag
`image run` retain their original tag rules and do not read `image.name`.
Provider, site-ID and credential fields are rejected in this registry-only
configuration. Unknown keys and malformed blocks fail before runtime detection.
The complete config must remain valid even when `--tag` overrides its name.

For static deployment, use the alternative publication block:

```yaml
publish:
  action: deploy
  provider: netlify
  site: acme-docs.netlify.app
```

`netlify` is the only implemented provider. `site` is an optional string containing
an existing project ID or full domain. Explicit `--site-id` / `--site` wins over
`NETLIFY_SITE_ID`, then `publish.site`. `NETLIFY_AUTH_TOKEN` supplies credentials;
tokens, image kinds and production flags are rejected in this block. A draft
preview is the default; pass `--prod` explicitly for live publication. See
[deployment](/cli/deploy) for behavior and limits. Bare `zel deploy` uses the same
saved plan as `zel pub`. `--to netlify` cannot replace a saved image-push intent.

## Planned CLI defaults

The site layout, build/preview settings, `image.name`, and registry-only
publication above are implemented in source. Direct provider delivery and CI
settings, shared `--site-root` / `--config` / `--cwd` selectors, and remaining
delivery commands are planned and are not accepted as working capabilities.

[Shortcuts](/cli/shortcuts) for working commands and
[shell completions](/cli/completions) are implemented in source. They use the
same configuration and defaults as the full command names.

The [full CLI contract](https://github.com/mylife-inc/Zellij/blob/main/specs/zel-cli-contract-2026-10-18.md)
records the remaining proposals. Current CI generation is documented in
[`zel ci`](/cli/ci); runtime diagnostics are in [`zel doctor`](/cli/doctor).
