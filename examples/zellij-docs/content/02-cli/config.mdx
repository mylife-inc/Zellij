<Callout type="tip" title="Available in source">
Portable Markdown uses `zel.yaml`. Hosted YAML/MDX sites use `site.yaml` and the
existing content model. The agreed site-root layout and common defaults described
below are not implemented yet; they will extend `zel.yaml`.
Native release packages may lag the source version.
</Callout>

## Portable Markdown

Place an optional `zel.yaml` directly inside the Markdown folder supplied to
`zel build` or `zel view`. A plain folder still works without it. The file sets
site identity, initial theme, a company logo/link, and documentation navigation.
It does not require Node, Docker, or an internet connection.

```yaml title="docs/zel.yaml"
name: Acme documentation
theme: forest
brand:
  logo:
    src: assets/company.svg
    alt: Acme company
    href: https://example.com
nav:
  - page: README.md
    label: Overview
  - label: Getting started
    children:
      - page: guide/install.md
        label: Installation
      - page: guide/configuration.md
  - label: Company website
    href: https://example.com
```

```bash title="terminal"
zel build ./docs
zel view ./docs --watch
zel build ./docs --name "Release documentation" --theme cupertino
```

### Selecting settings

`--name` and `--theme` override their respective file settings. If a setting is
absent from both flags and the file, the site name defaults to the source folder
name and the theme to `cupertino`.
Run `zel list themes` for accepted theme names. The complete configuration must
be valid, even when flags override some settings.

The builder reads only `<input>/zel.yaml`; it does not search parent folders or
look for child `docs` directories. Its presence selects the portable target for
an otherwise automatic `zel build`, including a folder with hosted markers.
An explicit `--target static` or `--target image` still selects that target.
`view` always uses the portable target.

### Mathematics

Math is disabled by default so dollar-sign prose keeps its existing meaning.
Enable it with a YAML boolean:

```yaml title="docs/zel.yaml"
markdown:
  math: true
```

Use `$...$` for inline equations and `$$...$$` for display equations. The
[portable math contract](/cli/build#mathematics) describes syntax, offline
rendering, validation, and supported limits. This is independent of hosted
Zellij's `features.maths` setting. `view --watch` rereads it after config edits.

### Mermaid

Enable Mermaid independently with `markdown: {mermaid: true}`, or put both
`math: true` and `mermaid: true` under `markdown`. Mermaid is disabled by default.
Its [local browser renderer](/cli/build#mermaid-diagrams) works offline, retains
readable source, and reports diagram syntax errors in the browser. Native
`zel check` validates source limits rather than Mermaid grammar.

### Navigation

`nav` is an ordered list. Each entry contains exactly one of:

| Field | Meaning | Label |
| --- | --- | --- |
| `page` | Exact Markdown source path relative to this folder | Optional; defaults to the document title |
| `children` | Another list of entries forming a group | Required |
| `href` | An absolute `http://` or `https://` link | Required |

Groups can nest up to 16 levels and must not be empty. Page paths include their
`.md` or `.markdown` extension and use `/` separators. Write spaces and Unicode
characters as they appear in filenames; these fields are filesystem paths, not
percent-encoded URLs. Missing pages, repeated page entries, traversal, and an
entry containing both `page` and `href` are errors.

Sidebar links and previous/next links follow the configured page order, walking
groups in order and skipping external links. Labels affect navigation; the
page's authored heading, HTML title and search title remain unchanged.
Breadcrumbs continue to describe source folders. If there is no root index or
README, the generated home lists the configured navigation.

All discovered Markdown documents are still validated, built, and searchable.
Omitting a page from `nav` removes it from sidebar and previous/next navigation;
it does not exclude or protect its content. Such pages remain reachable through
ordinary links and search. `nav: []` intentionally removes navigation links.
Omitting `nav` retains the automatic ordering described in [build](/cli/build).

### Company branding

`brand.logo.src` names a local image inside the Markdown folder. The builder
copies it into the export, using relative links that still work after moving
or opening the site directly. Remote logo sources, hidden paths, `node_modules`,
the reserved `_zellij` directory,
symlinks and Windows junctions are refused. `alt` is required, nonempty text.
Use an image format supported by your target browsers, such as SVG, PNG or WebP.

The logo appears at the left of the sticky header. Its optional `href` opens the
company's absolute HTTP(S) website; without it, the logo links to the docs home.
The site name beside it always links home. Search and theme controls remain on
the right. No external request occurs merely from displaying the company link;
visiting an external website requires connectivity.

### Editing and validation

Unknown keys, duplicate YAML keys, incorrect value types, invalid theme names,
and invalid navigation or branding fail before replacing the previous export.
Names, labels, alt text and paths must be YAML strings; quote values such as
`"2026"` if they should be text. The config file is not automatically published.
Source and output ownership rules are the same as for an unconfigured build.

`view --watch` notices config creation, edits, deletion, and logo changes. Invalid
edits keep the last working site and show the preview error notice. Fixing the
file rebuilds and reloads; deleting it restores defaults. CLI overrides stay in
effect until restarting the command. Output paths and ports remain CLI options.

An explicit visitor theme/appearance choice takes precedence over the site's
initial theme and survives navigation. Merely loading a default no longer saves
it as a visitor choice, so config theme changes can appear on reload. Preferences
saved by older exports may reset once when switching to this explicit-choice
format.

`zel.yaml` is a portable-renderer format. It does not load MkDocs plugins,
`mkdocs.yml`, hosted `site.yaml`/`_sidebar.yaml`, or a TOML defaults file.
Use [`zel check ./docs --strict`](/cli/check) to validate configuration and
Markdown natively without writing an export; add `--json` for structured reports.
Use [`zel new portable`](/cli/new) for a working native starter.
The common configuration and layout below remain future work.

## Planned CLI defaults

<Callout type="warning" title="Agreed layout; implementation pending">
The earlier `zel.toml` proposal has been superseded. The common site configuration
will extend `zel.yaml` with a version marker and an explicit renderer. Current
binaries do not yet accept the new schema or perform this discovery.
</Callout>

The agreed layout keeps authored content separate from configuration and output:

```text
my-product/
  docs/
    specs/
    zellij/             # Any folder name is allowed
      zel.yaml
      content/          # Markdown, assets, or hosted YAML/MDX content
      site/             # Generated output
```

Once implemented, `zel build` from the software repository root will select
`docs/zellij/zel.yaml`. A differently named folder is explicit:
`zel build docs/manual`. From a site root containing `zel.yaml`, the proposed
resolver uses that site. It will not search ancestors or recursively guess which
site in a repository to use. The output default is that site's `site/` directory.

The proposed minimal configuration is:

```yaml title="docs/zellij/zel.yaml — proposed, not accepted yet"
version: 1
renderer: portable
name: Acme documentation
```

A hosted site will use `renderer: hosted`, with its existing presentation model
under `content/site.yaml`. Portable navigation and logo paths will be relative
to `content/`. Existing flat portable configs and explicitly supplied raw
content folders will keep compatibility paths; no files will be moved silently.

The common schema will also hold build output, preview, image, delivery and CI
defaults. Command-line values will override configured defaults. Paths from the
command line are relative to the working directory; configured paths are
relative to the configuration file. Credentials remain outside this file.

The [full CLI contract](https://github.com/mylife-inc/Zellij/blob/main/specs/zel-cli-contract-2026-10-18.md)
records the proposed fields and aliases. Its unimplemented examples must not be
copied into current pipelines. Current CI generation is documented in
[`zel ci`](/cli/ci); current runtime diagnostics are in
[`zel doctor`](/cli/doctor).
