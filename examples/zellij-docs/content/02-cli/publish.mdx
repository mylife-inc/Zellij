<Callout type="tip" title="Available in candidate 0.2.0-rc.6">
`zel publish`, also `zel pub`, builds and pushes a configured image. It supports
portable Markdown and hosted content, with an explicit choice of static-server
or Next.js image. These commands are available in candidate `0.2.0-rc.6`; stable `0.1.3` predates them.
Saved Netlify deployment is also available; see below. Current source also supports Cloudflare Pages, Vercel, GitHub Pages, S3, Fly and Railway; see [deployment](/cli/deploy#cloudflare-pages).
</Callout>

## Save the destination

Add image and publication settings to a versioned site configuration:

```yaml title="docs/zellij/zel.yaml"
version: 1
renderer: portable
name: Acme documentation
image:
  name: ghcr.io/acme/manual:v1
publish:
  action: push
  image: static
```

Use `image: next` under `publish` for a Next.js application image. This setting
chooses the artifact for publication; it does not change `renderer` or turn an
ordinary `zel build`, `zel si` or `zel ni` into a publication command.

`image.name` is the exact reference to build and push. It also supplies the
saved default for `si` and `ni`; both use that same name if explicitly configured.
Use distinct `--tag` values when retaining both kinds. Without a configured name,
local image builds still have separate generated defaults. Publication requires
an explicit destination in configuration or `--tag`; it never guesses one from
the site's folder name. An omitted tag suffix uses the container client's usual
`latest` tag. Include a registry hostname to avoid the client's default registry.

```bash title="terminal"
zel pub --dry-run
zel publish
zel pub docs/manual --tag ghcr.io/acme/manual:v2
```

No path means the current directory's `zel.yaml`, then `docs/zellij/zel.yaml`.
A custom site folder is explicit. Saved delivery settings require `version: 1`
and `content/`; explicit raw-content folders do not acquire a publication default.
The configuration is not modified by overrides or a successful push.

## Netlify publication

Use this alternative block to publish static HTML from either renderer:

```yaml
publish:
  action: deploy
  provider: netlify
  site: acme-docs.netlify.app
```

Set `NETLIFY_AUTH_TOKEN`, then run `zel pub` for a draft preview or `zel pub
--prod` to request live publication. `--site-id` (also `--site`) overrides
`NETLIFY_SITE_ID`, which overrides `publish.site`. The same shared flow is used
by `zel netlify`, `zel deploy netlify`, and bare `zel deploy` with saved settings.
See [deployment](/cli/deploy) for setup, prerequisites, failure behavior and limits.
Portable Netlify delivery uses native Rust; hosted delivery uses one container
export. Both build into temporary output and preserve the previous local site.

`pub --to netlify` can supply deployment intent without saved settings, but it
rejects a saved image-push plan. Use explicit `deploy netlify` to choose static
HTML in that case. `--tag` cannot accompany a Netlify deployment. Ordinary
build/image commands never deploy, regardless of saved settings.

## What runs for image publication

The command resolves the site, image kind and destination, then checks for a
usable container runtime. It validates and builds using the same operation as
[`image static` or `image next`](/cli/image). A successful build is pushed once
to the exact selected reference, without a second build or implicit retagging.

For portable sources, generated HTML or adapted Next content lives in a private
temporary directory, removed on success or failure. Existing `site/`, configured
`build.out`, Markdown, configuration and assets are preserved. Hosted image builds
use their existing validated recipes. The pushed image has the same server,
health check, navigation and deployment-prefix behavior as its local image kind.

A successful push publishes an image to a registry. It does not launch a cloud
service, create provider infrastructure, or open a browser. Use [`zel image run`](/cli/image#zel-image-run)
to run a built or pulled image.

### Credentials and prerequisites

Authenticate using the selected container client's normal registry login, such
as `docker login ghcr.io`. Credentials are managed by that client; put neither
passwords nor tokens in `zel.yaml` or the image reference. Registry authentication
and write permissions are checked by the push itself. Runtime preflight does
not prove registry access.

Docker, Podman and nerdctl follow the same [runtime selection](/cli/doctor) as
other image commands. No runtime is installed or started automatically. Network
access may be needed for image downloads, dependencies and the push.

### Failure and retry

Invalid shared settings or an invalid image reference stop with exit **2**.
Missing/unavailable runtime stops with **4**. Content/build failures and an
unsuccessful runtime push stop with **3**; process/IO failures use **1**.
A failed validation/build never attempts a push.

If building succeeds and pushing fails, the command names the completed build
and leaves the local image available. After correcting registry access, retry
only the push:

```bash
zel image push ghcr.io/acme/manual:v1
```

Do not add `--registry` to that command when the reference already contains the
registry: that option prefixes a new destination for the existing manual push
command. A failed push may have uploaded some layers; Zellij does not attempt
to delete registry state or roll back a previously published tag.

## Temporary feature selection

`zel pub --features all` enables math and Mermaid for this publication;
`zel pub --features none` disables both. The same flag works with `publish`,
`deploy`, and `netlify`, for either renderer and either image kind. Choose
`maths`, `diagrams`, `maths,diagrams`, `all`, or `none`; the value is a complete
selection. Mindmaps remain independent.

The selection appears in `--dry-run` plans and reaches the single build before
push/upload. It does not modify source or saved configuration. A later command
without the flag uses saved portable settings or the hosted engine image's
defaults again. Hosted builds require a compatible engine supporting feature
selection; an incompatible engine stops before publication. Content validation
and credential/runtime checks still apply.

## Hosted URL and preflight overrides

Candidate rc.6 supports `--base-path`, `--site-url` and `--no-check` for
hosted publication and portable Markdown adapted into a Next.js image:

```bash
zel pub docs/hosted --base-path /manual --site-url https://docs.example.com --dry-run
zel pub docs/hosted --base-path /manual --site-url https://docs.example.com
zel pub docs/hosted --base-path / --no-check
```

These flags follow the [build override rules](/cli/build#hosted-url-and-validation-overrides)
and appear in dry-run plans. They reach the single build before push/upload,
without changing source or saved settings. `/` clears the authored prefix.
Portable static images and portable Netlify exports reject them before runtime,
credential or remote checks. `--no-check` skips only content preflight;
preparation, rendering, runtime and credential checks still apply. Failed builds
never push an image or create a Netlify deployment. The flags require a current
CLI and compatible engine; they are included in candidate `0.2.0-rc.6`.

## Options

| Option | Meaning |
| --- | --- |
| `[site]` | Configured site root; otherwise use the standard discovery order |
| `--tag <reference>` | Override `image.name` for both build and push |
| `--platform <platform>` | Override `image.platform`; choose `linux/amd64`, `linux/arm64`, or `all` for one tag with both |
| `--kind <kind>` | Fly/Railway only: `static` or `next`; overrides `publish.image` |
| `--features <selection>` | Complete rendering selection for this build only; saved settings stay unchanged |
| `--base-path <path>` | Hosted deployment prefix; `/` clears it only when compatible with the provider mount |
| `--site-url <origin>` | Hosted public HTTP(S) origin for canonical URLs and SEO metadata |
| `--no-check` | Skip content preflight; retain preparation, rendering and credential checks |
| `--dry-run` | Print resolved settings and intended stages; perform no tool probes, content validation, build or registry requests |
| `--to <provider>` | Select `netlify`, `cloudflare`, `vercel`, `github-pages`, `s3`, `fly` or `railway`; rejected for a saved image-push plan |
| `--site-id <destination>` | Provider-specific project, repository or bucket/prefix override; `--site` is equivalent |
| `--prod` | Request live publication; required for GitHub Pages, S3, Fly and Railway, preview by default for other implemented providers |

`--json` is not supported and fails before work. A dry run checks shared settings
and site selection; it does not prove that the content builds, credentials work,
or the destination exists.

## Remaining delivery work

Live portable/hosted acceptance passed for Cloudflare Pages and GitHub Pages;
static/Next image acceptance passed for Railway. The Cloudflare and Railway
fixes are included in `0.2.0-rc.6`. Live Vercel, S3 and Fly account
acceptance is deferred. Fly supports existing configured web Machines;
Railway supports existing image services.
The [`ship`](/cli/ship) composition imports and delivers a configured site.
[Workflow generation](/cli/ci) now consumes saved publication settings through
`zel ci [site]`, with local-only generation and explicit credential provisioning.


Image plans include the effective platform in `--dry-run` output. Publication
builds once for a single architecture, then pushes the result. A failed single-
architecture build never starts a push. `zel pub --platform all` builds and
publishes both Linux architectures directly as one tag, with the same features,
URL settings and explicit build arguments. This mode needs a compatible builder
and does not promise a local image; inspect the registry before retrying a failed
attempt because layers may have uploaded. Saved image settings do not affect an explicit Netlify deployment;
passing `--platform` to Netlify is rejected. See
[platform prerequisites](/cli/image#select-the-image-platform).

## Image build arguments

Current source supports repeatable `--build-arg NAME=VALUE` on `publish`, `pub`
and bare saved image `deploy`. Arguments apply to the single build before push;
duplicate names use their last explicit value. Dry plans list names without
values, and the flags never change `zel.yaml`. Netlify publication rejects them
before credential checks or remote work. See
[image build arguments](/cli/image#image-build-arguments).

## Cloudflare Pages publication

Current source also accepts `publish.provider: cloudflare` with a Pages project
name in `publish.site`. `pub --to cloudflare` can override static deployment
intent; it still rejects a saved image-push plan. Supply Cloudflare credentials
in the environment. An override never reuses another provider's destination.
See [Cloudflare setup and limits](/cli/deploy#cloudflare-pages). This adapter is available in candidate `0.2.0-rc.6`.

## Vercel publication

Save `publish: {action: deploy, provider: vercel, site: prj_YOUR_PROJECT_ID}` to
use `zel pub`. `pub --to vercel --site prj_YOUR_PROJECT_ID` overrides static
publication intent, while saved image-push plans still reject `--to`.
Supply `VERCEL_TOKEN` and, for a team project, `VERCEL_TEAM_ID` in the environment.
Previews are the default; production requires `--prod`. See
[Vercel setup and limits](/cli/deploy#vercel). These forms are available in candidate `0.2.0-rc.6`.

## GitHub Pages publication

Save `publish: {action: deploy, provider: github-pages, site: acme/manual}` and
run `zel pub --prod`. `pub --to github-pages --site acme/manual --prod` overrides
a static destination without changing saved settings; saved image publication
cannot be replaced this way. Dry runs also require `--prod` because Pages has no
draft mode. This replaces the existing `gh-pages` root while retaining history,
and waits for the matching commit's Pages build. See
[setup, URL defaults and limits](/cli/deploy#github-pages). This provider is available in candidate `0.2.0-rc.6`.

## S3 publication

Save `publish: {action: deploy, provider: s3, site: acme-docs/manual}` and use
`zel pub --prod`. `pub --to s3 --site acme-docs/manual --prod` overrides a saved
deployment provider, while saved image-push plans keep their existing conflict
checks. S3 requires `--prod`, even for dry runs. Uploads replace matching keys
individually and retain other keys; they are not atomic. Both renderers preserve
local source and previous output. See [S3 setup and limits](/cli/deploy#aws-s3).
This provider is available in candidate `0.2.0-rc.6`.


## Fly publication

Save `publish: {action: deploy, provider: fly, site: manual, image: next}` and
run `zel pub --prod`. Omit `image` for static content or override it with
`--kind static|next`. Use `pub --to fly --site manual --prod` to change a saved
deployment provider. Destinations and image kinds from another provider are
not reused. Fly uses amd64 images regardless of saved `image.platform` and
creates its own registry tag; `--tag` is reserved for registry publication.
See [Fly setup, health checks and partial-rollout behavior](/cli/deploy#fly).


## Railway publication

Save `publish.provider: railway`, the service UUID in `publish.site`, the image
kind in `publish.image`, and a registry reference in `image.name`. Then run
`zel pub --prod`. `--kind` and `--tag` override the image kind and registry tag
for this invocation. `pub --to railway --site <service-uuid> --tag <reference>
--prod` can change a saved deployment provider; another provider's destination
and image kind are not reused. The expected project/environment and project
token come from the Railway environment variables. See
[Railway setup and failure behavior](/cli/deploy#railway).
