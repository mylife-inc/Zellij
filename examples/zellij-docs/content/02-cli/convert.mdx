The output goes in a **new folder**. The original is never touched, so a
conversion you dislike costs nothing but the folder you delete.

An existing empty folder is also accepted. The source and output must not
contain one another, including through a symbolic-link alias. These checks also
run with `--dry-run`. Imported document paths must stay inside their docs root;
parent paths, absolute paths, and symbolic links beneath that root are rejected.
Conflicting output filenames are reported before any files are created.

Run [`zel detect`](/cli/detect) first if you are not sure what the folder is, or
[`zel migrate`](/cli/migrate) to detect, convert and validate in one step.

## Choose the output layout

```bash title="terminal"
zel convert ./old-docs --out ./manual --layout site
# Identical shortcut and defaults:
zel cv ./old-docs --out ./manual --layout site
```

`--layout site` writes `manual/zel.yaml` with `version: 1` and `renderer: hosted`,
and puts the converted files and assets in `manual/content/`. Later commands
accept `manual` as the site root. Local builds default to `manual/site/`.
Conversion itself needs no container runtime; hosted checks/builds do.

**The default remains `--layout content`**, which writes the existing raw hosted
layout directly under the destination. Neither spelling silently inserts a
`content/` directory. This compatibility choice will change only at a documented
version boundary. The new layout option is implemented in source and is newer
than the public `zellij-v0.1.3` binary.

Current converters emit hosted sites whose HTML requires HTTP serving. They do
not produce the portable renderer's direct-file output.

## Take the plan first

```bash title="terminal"
zel convert ./docs --out ./content --dry-run
```

Prints exactly what it would write and what it could not carry over, and writes
nothing. Worth the ten seconds on any tree you did not author yourself: the list
of unmapped things is the real report, and reading it before there is a folder
to be attached to makes it easier to act on.

## Options

| | | |
| --- | --- | --- |
| `<source>` | Required. The folder to read | — |
| `--out <path>` | Required. Where to write | — |
| `--from <format>` | Force a format instead of detecting | detected |
| `--layout content\|site` | Raw hosted content or a configured site | content |
| `--assets copy\|link\|skip` | Copy files, link to a public base, or retain original URLs | copy |
| `--asset-base-url <url>` | Existing HTTP(S) asset directory; required only with `--assets link` | — |
| `--validate` | Validate the converted hosted content after writing | off |
| `--dry-run` | Report the plan, write nothing | off |

**`--out` can never be the source, and there is no flag to permit it.** A
conversion that overwrote the original would be unrecoverable — and the whole
reason a migration is safe to try is that failing costs you a folder you delete.

`--from` selects the parser explicitly. If multiple formats tie for the highest
detection confidence, conversion refuses to guess and asks for this option.
Forcing a format does not guarantee a faithful conversion; inspect warnings.

## Optional validation

```bash title="terminal"
zel cv ./old-docs --out ./manual --layout site --validate
```

`--validate` performs the same hosted content check as [`zel migrate`](/cli/migrate)
after writing either output layout. It requires a running Docker, Podman or
nerdctl runtime and a compatible engine image. Conversion without this flag
needs no runtime. `--dry-run` always skips validation, including runtime checks.

If validation fails, the command returns a nonzero exit status and retains the
converted files. A missing runtime returns exit 4; a content-check failure returns
exit 3. Correct the issue and run `zel check ./manual`; converting again into the
populated destination is refused. This checks the content model without compiling
the full site. Use `zel check ./manual --deep` for MDX and local references, and
`zel build ./manual` to compile. Successful validation does not guarantee complete
source-tool fidelity; review the conversion report.

`--validate` and `--assets` are available in candidate `0.2.0-rc.6`.

## What is recognised

```bash title="terminal"
zel list formats
```

| Format | Read from | |
| --- | --- | --- |
| MkDocs | `mkdocs.yml` | The `nav` tree, `site_name`, `site_description`, `docs_dir` |
| Docusaurus | `sidebars.js`, `.ts`, `.cjs` or `.json` | Categories, doc entries, links and nesting — when declarative |
| VitePress | `.vitepress/config.js`, `.ts`, `.mjs` or `.mts` | Literal config, `srcDir`, nested/multiple sidebars, Markdown links and referenced assets |
| Jekyll | `_config.yml`, `_config.yaml` or `_config.toml` | Markdown pages, output collections, scoped defaults, navigation data, source URLs and eligible assets |
| Hugo | `hugo.*` or legacy `config.*` in TOML, YAML or JSON | Markdown sections, page bundles, publication rules, source URLs and referenced resources |
| Sphinx | `conf.py` | Literal configuration, `.rst` pages, explicit toctrees, supported reStructuredText, references and eligible assets |

Converters are plugins compiled into the binary, so `zel list formats` prints
what your build can actually read.

## VitePress imports

```bash title="terminal"
zel cv ./vitepress-site --from vitepress --out ./manual --layout site --dry-run
zel cv ./vitepress-site --from vitepress --out ./manual --layout site
```

Pass the directory containing `.vitepress/`, even when `srcDir` moves the
Markdown elsewhere. Exactly one supported config file must exist. The importer
reads literal `export default {...}` and `module.exports = {...}` objects, plus
the standard wrapper below, as data. It does not execute JavaScript or install
VitePress:

```ts
import { defineConfig } from 'vitepress'
export default defineConfig({
  title: 'Product manual',
  description: 'How to use the product',
  srcDir: 'content',
  base: '/manual/',
  cleanUrls: true,
  themeConfig: {
    sidebar: [
      { text: 'Welcome', link: '/' },
      { text: 'Guides', items: [{ text: 'Install', link: '/guide/install' }] }
    ]
  }
})
```

This reads `content/index.md` and `content/guide/install.md`. `srcDir` defaults
to the config's parent site directory and must stay inside it. Sidebar links
resolve from that source root; item `base` values prefix descendant links.
Array order and nested labels are retained. A linked group places its page
first. Multiple sidebars are combined into one guide, grouped by route prefix
in lexical order, with a report explaining the change. Repeated pages are
written once. Styling fields and sidebar query/fragment suffixes are reported.

Without a sidebar, visible `.md` files supply navigation in filename order.
An explicitly empty or `false` sidebar stays empty. Files absent from a declared
sidebar are reported and skipped, even though VitePress's file-based routing
could publish them. Hidden/underscore trees, `node_modules` and `public` are
not scanned as documentation; `.mdx` files are reported and skipped.

Markdown file links and supported root-relative `.md`, extensionless, `.html`
and directory-index URLs become Zellij guide routes. Both authored root URLs
and URLs with the configured `base` are recognized. Relative website document
links use the source page's `cleanUrls`/index location. Queries and fragments
are preserved. VitePress provides no site-origin setting here, so absolute
HTTP(S) URLs remain external; nothing is fetched.

Referenced document-relative assets go to `assets/imported/docs/`. Root-relative
assets can also come from `public/` inside `srcDir`, and then go to
`assets/imported/public/`. If the same root URL names files in both places,
conversion fails before writes so you can resolve the ambiguity. `--assets skip`
still checks paths and ambiguity. Unreferenced public files are not copied.

Computed config, extra imports, functions, spreads and TypeScript type expressions
are rejected before output. Nonempty `rewrites`, `locales`, `srcExclude` and
`vite` settings, dynamic `[parameter]` Markdown paths, config inheritance/hooks,
and custom `outDir`/`cacheDir` also require simplification in a source copy first.
This prevents the importer from guessing routes, exclusions or generated trees.

Vue components, top navigation, home-page layout and custom Markdown features
such as containers, includes and code imports require manual migration. Source
text/metadata is retained, with conversion notes; these features are not turned
into equivalent Zellij components. Inspect the report and build the result.
This supported subset follows VitePress 1.x conventions and is available in candidate `0.2.0-rc.6`.

## Jekyll imports

```bash title="terminal"
zel cv ./jekyll-site --from jekyll --out ./manual --layout site --dry-run
zel cv ./jekyll-site --from jekyll --out ./manual --layout site
```

Pass the directory containing `_config.yml`, `_config.yaml` or `_config.toml`.
Exactly one configuration file is accepted. When several exist, consolidate
settings in a source copy before importing; the importer does not guess which
Jekyll configuration or override sequence you intended. YAML aliases/merge keys
and TOML tables/arrays are read as data; Ruby and Liquid are never executed.
The source stays untouched.

TOML configuration support is included in `0.2.0-rc.6`. It supports the same settings
and validation as YAML, with case-sensitive keys and typed booleans/numbers.
Date/time values are retained as text in inherited metadata; dated collection
pages still need manual migration. Page front matter remains YAML.
For example, the following configuration declares a documentation collection
and a default description for its pages:

```toml title="_config.toml"
title = "Product manual"
source = "pages"
baseurl = "/manual"

[collections.reference]
output = true
order = ["overview.md", "api.md"]

[[defaults]]
scope = { path = "", type = "reference" }
values = { description = "Product reference" }
```

TOML configuration nesting is limited to 64 levels. Invalid TOML, duplicate
keys, ambiguous config files and unsupported settings fail before output is
written, including in dry runs. See Jekyll's
[configuration reference](https://jekyllrb.com/docs/configuration/).

The importer reads `title`, `description`, a contained `source` directory,
`url`, `baseurl`, literal `exclude` paths and scoped front matter defaults.
Default scopes support literal path prefixes and optional types (`pages` or a
collection name). Longer paths take precedence, then type-specific scopes,
then later entries. Authored metadata takes precedence over defaults. Titles
and descriptions become active Zellij metadata; other fields and original front
matter remain in comments for review.

Only `.md` and `.markdown` files with YAML front matter become pages. An empty
front matter block is sufficient. Files without that block are reported as
static Markdown and skipped. `published: false` or null and `nav_exclude: true`
are excluded. Posts/drafts, hidden files, dependencies, generated output and
internal template directories are not imported as documentation.

### Documentation collections

```yaml
collections:
  reference:
    output: true
    order: [overview.md, api.md]
    permalink: /reference/:path/
```

This reads `_reference/overview.md`, `_reference/api.md` and other Markdown
pages in that collection. `output: true` is required. With derived navigation,
listed `order` entries come first, followed by remaining pages in filename
order. Entries without a published Markdown page are ignored and reported.
Collection groups follow ordinary pages and are sorted by name.
Collection URL patterns support `:collection`, `:path` and `:output_ext` only.
Dated collection files require manual migration; posts remain excluded even
when their collection declares output.

Candidate `0.2.0-rc.6` also supports collection `sort_by`, following
[Jekyll collection ordering](https://jekyllrb.com/docs/collections/#custom-sorting-of-documents).
For example, replace the `order` setting above with `sort_by: weight` and give
each page a numeric `weight` in its YAML front matter or scoped defaults:

```yaml
collections:
  reference:
    output: true
    sort_by: weight
```

Values sort ascending; absent/null values follow, and ties use source filename
order. Inherited defaults apply before sorting. A collection must use either
finite numbers or text for its sort field; mixing the two is rejected before
output. 64-bit integers retain their exact order; decimal/exponent values use
floating point. Text uses case-sensitive
lexical order, so text `'10'` comes before `'2'`. The key is literal and
case-sensitive: `lesson.name` addresses that exact key, not a nested mapping.
An explicit `order` array takes precedence over `sort_by`, including `order: []`
(which keeps filename order). Explicit navigation data takes precedence over
both collection ordering modes.

Generated `slug` and `ext` values use the source basename when absent. Generated
`title` sorting supports ASCII basenames; for non-ASCII names, supply an explicit
title in front matter or defaults. Boolean, array, mapping, nonfinite numeric,
generated `date`/`categories`/`tags`/`excerpt` and date/time-shaped sort values (including
quoted dates) require a numeric rank or explicit `order` list. The importer does
not guess timestamp types or timezone ordering. These sorting and stale-order
fixes are included in `0.2.0-rc.6`.

### Navigation data

The importer recognizes one `_data/navigation.yml`, `.yaml` or `.json` file,
using an array or an object containing only a `main` array. A contained
`data_dir` can change the data directory. Both `name`/`link` and `title`/`url`
entries are supported, with optional nested `children`:

```yaml
- name: Welcome
  link: /
- title: Reference
  children:
    - title: API
      url: /reference/api/
```

Local entries address source website URLs, including supported permalinks.
Array order is retained; a linked group places its page first. External links
are reported for migration to the Zellij menu. An explicit empty array stays
empty. Pages absent from declared navigation are reported and skipped. Without
this file, navigation is derived from eligible pages and enabled collections;
theme-specific ordering or hierarchy requires review.

### Links, assets and limits

Source `date`, `none` and `ordinal` permalink styles use HTML page URLs;
`pretty` uses directory URLs. Index pages, literal per-page permalinks and the
supported collection patterns are recognized. Markdown links, root-relative
and same-origin website URLs map to Zellij's filename-derived guide routes,
retaining queries and fragments. Relative website links use the original page
URL directory. Original permalinks do not become destination route overrides.

Referenced eligible static files are copied byte-for-byte to
`assets/imported/docs/`, preserving source-relative paths. Literal exclusions,
internal data/template directories and generated output remain excluded even
when linked. Files beginning with YAML front matter are treated as templates,
not copied as static assets. `--assets skip` retains asset URLs but still checks
unsafe paths. Missing or excluded assets are reported.

Liquid expressions, includes, layouts, plugins, theme-supplied configuration,
HTML pages and custom Markdown features need manual migration. Config
merging, glob exclusions or default scopes, forced `include` rules, custom
collection roots, unsupported permalink placeholders and localization settings
are rejected before output. Custom layout/include/plugin directory settings
also require a source copy using the documented defaults. This is a Jekyll 4.x
documentation subset, not a theme or blog migration. Read the report and build
the result before publishing. It is available in candidate `0.2.0-rc.6`.

## Hugo imports

```bash title="terminal"
zel cv ./hugo-site --from hugo --out ./manual --layout site --dry-run
zel cv ./hugo-site --from hugo --out ./manual --layout site
```

Pass the directory containing one `hugo.toml`, `hugo.yaml`, `hugo.yml`, or
`hugo.json` file. Legacy `config.*` names with the same extensions are accepted.
Configuration and front matter are read as data. Go templates, themes, modules
and shortcodes are not executed. The source files remain untouched.

The importer reads a contained `contentDir` (default `content`) and one
`staticDir` (default `static`). Content, static and generated `publishDir`
(default `public`) must not overlap. It reads the site title, description or
`params.description`, and `baseURL`. Only `.md` and `.markdown` pages are
converted. YAML, TOML and JSON front matter are supported; front matter is
optional. Metadata keys are case-insensitive, and conflicting keys are rejected.

### Sections and page bundles

```text
hugo.toml
content/
  _index.md
  guide/
    _index.md
    introduction.md
    install/
      index.md
      diagram.svg
static/
  logo.svg
```

`_index.md` supplies a home or section page and becomes `index.mdx` in Zellij.
Links authored against `_index.md` still work. A leaf bundle uses `index.md`;
other Markdown files inside it are page resources, not standalone pages, and
are reported rather than published. Root `index.md` and conflicting bundle
indexes require a source copy with an unambiguous `_index.md` home page.

Navigation is derived from sections and bundles. A section's own page comes
first within its group. Siblings sort by nonzero `weight` ascending, then date
descending, then case-folded `linkTitle`/title and source path. Zero or missing
weights come after weighted entries. Theme-specific ordering and locale-aware
collation need review. Declared menus require manual migration; they are not
silently treated as a complete documentation sidebar.

### Visibility, links and assets

Draft, future, expired, headless and unlisted/unrendered pages are excluded.
The explicit `buildDrafts`, `buildFuture` and `buildExpired` configuration flags
are honored. Supported page `build`/legacy `_build` rules read `list` and
`render`; conditional resource publication requires manual migration. Publication
dates and aliases such as `pubdate` are evaluated at conversion time. This does
not create ongoing publication scheduling in the converted site.

Dates accept ISO calendar dates, ISO local timestamps interpreted in UTC, and
RFC3339 timestamps with offsets. A configured time zone other than UTC or custom
front matter date rules requires normalization in a source copy.

Markdown-file links and supported source website URLs map to Zellij guide
routes, preserving queries and fragments. Directory URLs, `baseURL` prefixes,
regular-page `slug`/`url`, and `disablePathToLower` are recognized. Section and
bundle route overrides, custom permalink patterns and `uglyURLs` require manual
migration. Source route overrides do not become destination overrides. Redirect
aliases remain metadata for review; no redirect files are generated.

Referenced content resources and static files are copied to
`assets/imported/docs/` and `assets/imported/static/`. Hidden content, omitted
bundle resources and page resources cannot be copied through asset links.
Conflicting resource/static URLs and unsafe paths fail before output. Assets
use source-relative paths; template-generated or transformed asset URLs need
manual migration. `--assets skip` retains asset URLs while still checking paths.

Split/environment configuration, modules/mounts, multilingual or versioned
content, cascades, menus, content adapters, ignore patterns, alternate outputs,
and unsupported content formats are outside this subset. Shortcodes remain
literal text with a report. Read the report and build the result before
publishing. Hugo support is available in candidate `0.2.0-rc.6`.

## Sphinx imports

```bash title="terminal"
zel cv ./sphinx/source --from sphinx --out ./manual --layout site --dry-run
zel cv ./sphinx/source --from sphinx --out ./manual --layout site
```

Pass the **source directory containing `conf.py`**, not its parent build
project. Conversion needs neither Python nor Sphinx. Configuration is read as
literal data; Python imports, expressions, functions and extensions are never
executed. If the original configuration is dynamic, prepare a separate source
copy with a simplified `conf.py` before importing:

```python
project = 'Product manual'
extensions = []
root_doc = 'index'
source_suffix = {'.rst': 'restructuredtext'}
exclude_patterns = ['_build', 'private']
html_baseurl = 'https://old.example.test/manual/'
```

Accepted literals are single/double-quoted strings, integers, booleans, `None`,
lists, tuples and string-keyed dictionaries. Comments and multiline collections
are supported. Triple-quoted strings, string prefixes, computed values and
duplicate assignments are rejected. `master_doc` is the older name for
`root_doc`; when both exist they must agree. Only UTF-8 `.rst` input is
supported; `source_suffix` may be `'.rst'`, `['.rst']` or the dictionary above.
`exclude_patterns` accepts relative file/directory paths and glob patterns
(see below). `include_patterns` also accepts source-selection globs; its default
is `['**']`. Both glob settings are supported in `0.2.0-rc.6`. Unknown configuration that
could transform content is refused. Theme/presentation settings do not recreate
the original theme.

`language` must be absent, `None` or empty. Sphinx can select different image
files based on that setting, even for English; choose localized resources
explicitly in a source copy before importing. Local image/download names are
literal filenames: a filename containing `%20` remains distinct from one
containing a space. This differs from URL escaping in ordinary website links.

Navigation starts at `root_doc` (default `index`) and follows
`.. toctree::` entries in order. Relative document names resolve beside the
containing page; `/name` resolves from the source root. Explicit titles,
captions, nested document trees and `self` are supported. Hidden toctrees still
define navigation but produce no inline link list. `maxdepth` is reported as a
presentation difference; the full document hierarchy is imported. External
entries stay in visible inline lists and are reported for sidebar migration.
Missing/excluded targets, cycles and ambiguous destination routes fail before
writes. Unlisted pages are reported and not published; add them to the source
toctree if they should be imported. This differs from Sphinx's ability to build
unlisted/orphan documents.

Candidate `0.2.0-rc.6` also accepts `:glob:` and `:reversed:` on
toctrees. Both are flags without a value. For example:

```rst
.. toctree::
   :glob:
   :reversed:

   release-notes/*
```

Patterns match case-sensitive source document names **without `.rst`**.
Matches are sorted by name within each pattern, in the order the patterns
appear. `*` and `?` stay within one directory; `**` can cross directories.
`**/page` still requires a directory before `page`. Character classes such as
`[a-c]` and `[!a-c]` are supported. Relative patterns use the owning document's
directory, including when a toctree comes from an included fragment; `/` starts
at the source root. Earlier explicit entries and earlier pattern matches are
removed from later patterns in that same toctree. `:reversed:` then reverses
the whole resulting list, including explicit/external entries; it also works
without `:glob:`. Hidden trees use the same order in navigation.

Globs omit the owning page, excluded/hidden/internal sources and reserved
generated pages. A pattern with no remaining matches is reported and adds no
entries. Explicitly titled wildcard entries such as `Title <pages/*>` are not
expanded. A matched fragment still needs a page title; untitled fragments
belong in `include` directives. Existing path, cycle and destination checks
still apply. Patterns are limited to 4096 UTF-8 bytes after path resolution,
and an import accepts at most 10,000 expanded matches. Automatic section
numbering still requires manual migration.

### Excluding source files

`exclude_patterns` matches case-sensitive filenames relative to the selected
Sphinx source folder, including their extensions. Use `/` on every OS:

```python
exclude_patterns = ['draft*.rst', 'guide/private*', '**/archive', 'media/*.bak']
```

These patterns exclude root-level draft documents, matching files/directories
inside `guide`, nested `archive` directories and backup files in `media`.
A directory match excludes its entire subtree. `*` and `?` do not cross `/`;
`**` does, and bracket classes such as `[a-c]` and `[!a-c]` are supported.
As in Sphinx **source discovery**, `**/draft.rst` requires a subdirectory;
add `draft.rst` to exclude the root-level file too. Filenames are normalized to
Unicode NFC for matching; their original spelling is retained in the import.

Excluded documents are reported and never published, including through a
toctree glob. Exclusions also apply to referenced images/downloads and local
include, CSV and code resources, regardless of the asset policy. Explicit
toctree entries and include/CSV/code directives targeting excluded files fail
before output is written. Image/download references are reported for manual
repair and left unchanged, without copying the asset or linking it to a public
asset base URL. The importer
uses this one source-relative policy for resources; it does not reproduce the
HTML builder's separate copying of `html_static_path`/`html_extra_path` trees.
Hidden/internal source rules still apply, and exclusions cannot bypass the
existing rejection of symlinks or junctions beneath the source folder.

Use at most 1024 patterns, 4096 UTF-8 bytes per pattern and 128 KiB in total.
Absolute paths, drive prefixes, backslashes, control characters, parent/current
directory segments and empty path segments are rejected. Exclusion patterns
are matched as names, never opened as paths. Template/theme/static directory
settings still require explicit paths.

### Selecting source pages

Candidate `0.2.0-rc.6` also supports `include_patterns`:

```python
include_patterns = ['index.rst', 'guide/**', 'reference/*.rst']
exclude_patterns = ['guide/draft*']
```

When omitted, `include_patterns` defaults to `['**']`. An explicitly empty list
selects no pages and therefore fails because the root document is not selected.
Patterns match full source-relative filenames, including `.rst`, with the same
case, Unicode NFC, separator and size rules as exclusions. Exclusions take
precedence. Inclusion patterns match files only: use `guide/**` to select its
subtree; `guide` alone does not select the directory's documents. A leading
`**/` still requires a subdirectory, so include `index.rst` explicitly when needed.

The root document and every explicit toctree target must be selected; otherwise
conversion fails before writing output. Toctree globs see only selected pages.
Unselected pages are reported without parsing or publishing their content.

Page selection does not filter referenced images, downloads, CSV/code files or
parsed include fragments. A selected page can still use these resources from
elsewhere in the source folder. Fragments used by an `include` directive do not
become standalone pages or produce unselected-page reports. Explicit exclusions
and the existing containment, hidden/internal-source and asset-policy rules still
apply to all resources. Inclusion patterns are not a way to remove sensitive
resources from an import; use `exclude_patterns` for that purpose.

Supported reStructuredText includes underline/overline headings, paragraphs,
emphasis, strong text, inline literals, nested bullet/numbered lists, indented
literal blocks, `code`/`code-block`/`sourcecode`, standard admonitions, and
`image` with optional `:alt:`. Explicit section labels must occur directly before
a heading. `:doc:`, `:ref:` and `:download:` support automatic or explicit link
text. Inline explicit hyperlinks and named hyperlink definitions are supported.
Code, literal, command, file and keyboard roles become inline code; emphasis and
strong roles retain formatting. Source HTML is treated as literal text. Code
blocks remain literal, including directive-looking examples and backticks.
Separate directive options from content with a blank line; option-like text
inside a code block remains literal content.

### Reusing document fragments

Candidate `0.2.0-rc.6` supports local parsed `include` directives.
The included text joins the owning page: headings retain their hierarchy,
labels and substitutions work across the include boundary, and supported links,
images, lists, tables, admonitions and toctrees retain their normal behavior.
Fragments do not need their own title and are not published as separate pages
unless selected by a toctree. Only selected pages and their includes are parsed;
unlisted `.rst` sources are reported without reading their dependencies.

```rst
.. include:: fragments/install.rst
   :start-after: BEGIN INSTALL
   :end-before: END INSTALL
```

Paths, including nested `include` paths, resolve beside the **owning page**;
a leading `/` resolves from the selected source root. Images, downloads,
`literalinclude` and document roles keep that same page context. CSV `:file:`
paths instead resolve beside the file containing the directive, including a
fragment or another CSV file. File names are literal and case-sensitive.

The referenced file must be eligible under the same containment/exclusion rules
as `literalinclude` below. Keep fragments inside the source folder and outside
excluded, hidden, template and build trees; use `.inc`, `.txt` or unlisted `.rst`
files. Unlike Sphinx, explicitly excluded fragments cannot be included here.
Inclusion does not copy the original fragment as a downloadable asset.

Supported parsed-include options:

- `:encoding:` accepts `utf-8` or `utf-8-sig`; otherwise `source_encoding`
  applies. Line endings normalize to LF.
- `:start-line:` / `:end-line:` select a zero-based, end-exclusive slice.
  Negative indexes count from the end. Bounds clamp to the available lines;
  an empty or reversed slice inserts no text.
- `:start-after:` / `:end-before:` select text after/before the first exact
  marker in the remaining slice. Matching may occur within a line; it does
  not discard the whole marker line as `literalinclude` does. Markers must be
  nonempty and present. Line slicing precedes marker selection.
- `:tab-width:` expands tabs at column stops from 1 to 64 (default 8).

The directive requires one filename and no body. Repeated fragments are allowed;
cyclic includes and duplicate labels/headings fail before output. A chain is
limited to 32 active source files, with at most 10,000 include expansions per
conversion. Includes share the 8 MiB file and 32 MiB input/expanded-text budgets
with CSV tables and `literalinclude`. These checks also apply to dry runs and
all asset policies. Directive-looking examples inside code or comments are never
expanded. `:parser:`, `:literal:`, `:code:`, empty text markers, presentation options
and standard `<...>` include libraries are unsupported; use `literalinclude`
for code excerpts. No Python, parser plugin or network fetch is performed.
See the [Docutils include reference](https://docutils.sourceforge.io/docs/ref/rst/directives.html#including-an-external-document-fragment)
for the upstream syntax.

### Including code excerpts

`literalinclude` imports local UTF-8 code/text files as fenced code. Paths are
relative to the containing `.rst` file; a leading `/` means the selected Sphinx
source folder. Filenames remain literal, including spaces, Unicode, `#` and
`%20`. Match the filename's exact case, including on macOS and Windows. The file
must stay inside that folder and must not be hidden, excluded,
symlinked, a directory, or a template/theme/build resource. Included source code
is never executed or parsed as RST, and inclusion alone does not copy it as a
downloadable asset. This also works inside supported lists, admonitions and
table cells. Unlisted documents do not cause their referenced files to be read.

```rst
.. literalinclude:: examples/client.py
   :language: python
   :start-after: BEGIN EXAMPLE
   :end-before: END EXAMPLE
   :dedent: 4
```

Supported options:

- `:language:` selects the code language, otherwise `highlight_language` applies
  (or plain text when unset).
- `:encoding:` accepts `utf-8` or `utf-8-sig`, otherwise `source_encoding` applies
  (default `utf-8-sig`, which removes an initial BOM). LF, CRLF and CR line endings
  become LF. Unsupported control characters and invalid UTF-8 fail.
- `:tab-width:` expands tabs at column stops from 1 to 64; omitted tabs remain tabs.
- `:start-at:` / `:start-after:` retain/remove the first matching marker line.
  `:end-at:` / `:end-before:` retain/remove the first matching end line in the
  remaining excerpt. Use at most one start and one end option. `end-before`
  skips a match on the excerpt's first line, allowing the same opening/closing
  marker. Markers are literal substrings and must exist.
- `:lines:` selects one-based lines **after** marker filtering. Comma lists,
  inclusive ranges and open ranges work: `1,3-5,8-` or `-3`. Authored order and
  repeated lines are retained. Empty, zero, reversed and out-of-range selections
  fail instead of silently dropping lines.
- `:dedent: N` removes up to N leading spaces/tabs from each selected line;
  removing non-whitespace fails. Empty `:dedent:` removes the common whitespace
  prefix of nonblank lines. Dedenting happens after selection; tabs and spaces
  are distinct unless `tab-width` expands them first.

Each referenced file is limited to 8 MiB; unique input and total expanded text
are each limited to 32 MiB per conversion, shared with local CSV tables and parsed includes. Explicit line selections are limited
to 100,000 lines. Unsupported options such as `caption`, `name`, `linenos`,
`emphasize-lines`, `pyobject`, `diff`, `prepend` and `append` fail before output.
The directive requires a filename and has no content body. These checks also
apply to `--dry-run` and `--assets skip`. A `.rst` file used only as a snippet
does not need a title; pages selected by a toctree still require one.

Lists support `*`, `+`, `-`, `•`, `‣` and `⁃` bullets, plus decimal numbering
such as `1.`, `1)` and `(1)`. Alphabetic `a`–`z`/`A`–`Z` and canonical Roman
`i`–`mmmcmxcix`/`I`–`MMMCMXCIX` sequences support the same three punctuation
forms. The matching `#.`, `#)` or `(#)` continues the current sequence
automatically. Decimal numbering can start at 0–2147483647; alphabetic numbering
is limited to 1–26, and Roman numbering to 1–3999 so browsers retain Roman
markers. Automatic numbering must remain within that sequence's range.

An existing sequence resolves ambiguous letters: `H, I, J` is alphabetic and
`IV, V, VI` is Roman. At the start of a list, `i`/`I` means Roman one; other
single letters (including `v`/`V`) mean alphabetic. To include Roman five, begin with an
unambiguous value such as `iv` and then continue with `v` or `#`. A different case, sequence or punctuation style, a
nonconsecutive explicit number, or **any explicit marker after an automatic
marker** starts a separate list. Wrapped prose such as `A. Einstein was` followed
by an unindented prose line remains prose. Bullet glyphs and numbering
punctuation use the site's ordinary list presentation; letter/Roman case and
ordered-list start values are preserved.

Align continuation text and nested blocks with the first text after the marker.
Separate nested lists and paragraphs with blank lines. List items can contain
the supported paragraphs, code, admonitions, images, tables and references;
lists also work inside table cells. Empty items retain their position. Generated
MDX preserves semantic list nesting, ordered-list start values and alphabetic/
Roman styles through native HTML list attributes, and list text
remains searchable. Malformed indentation/separators and unsupported nested
constructs fail before output. Lists are limited to 10,000 items each and share
the table/admonition nesting limit of 16.

```rst
- Prepare the workspace.

  3. Open the guide.
  #. Follow the next step.

     * Keep this nested note.

- Finish.

Alphabetic sequence:

H. Eight.
I. Nine.
#. Ten.

Roman sequence:

(iv) Four.
(v) Five.
(#) Six.
```

**Substitutions** can reuse formatted text and inline images. Define them with
`replace` (one paragraph, optionally wrapped across lines) or `image` with
optional `:alt:` and `:target:`. References may appear before definitions, and
replacement text may use other substitutions, supported roles and named links.
Definitions belong to their document; they are not shared between pages.

```rst
|Product| is the |edition|. Visit |guide|_ or click |logo|.

.. |Product| replace:: **Zellij**
.. |edition| replace:: |Product| documentation engine
.. |guide| replace:: *Read* the guide
.. _guide: details.html
.. |logo| image:: media/logo.svg
   :alt: Company logo
   :target: guide_
```

Names normalize internal whitespace and prefer an exact-case match. If none
exists, a unique case-insensitive match is accepted; ambiguous matches fail.
`|name|_` uses a named hyperlink target. Image targets can be explicit URLs or
named targets ending in `_`. Referenced images/downloads follow the normal
asset policy, including containment checks in dry-run and asset-skip modes.
Images embedded in a paragraph stay inline; standalone figures keep their
block layout. Expanded text remains searchable.

`|version|` and `|release|` use literal strings from `conf.py` (empty when
unset); an authored definition overrides the corresponding default on that
page. Those configuration strings are not interpreted as markup. Inline code,
code blocks and escaped opening pipes remain literal. Use escaped spaces when
a substitution must touch a neighboring word, as in `prefix\ |name|\ suffix`.

Undefined references, cycles, duplicate definitions, nested hyperlinks and
unsupported substitution directives fail before output. All definitions in a
published document are validated, including unused ones. Limits are 1,000
authored definitions per document, 256-byte names and 64 KiB replacement text.
Each validation/rendering expansion pass allows at most 16 nested substitutions,
10,000 references and 4 MiB of processed expansion text. Headings and toctree
captions/titles still need plain text. Anonymous substitution links, `unicode`,
`date`/automatic `today`, trimming/presentation options and global
`rst_prolog`/`rst_epilog` transformations require manual migration.

Rectangular **grid and simple tables** are supported, including tables without
headers, multiple header rows, multiline cells and `.. table::` captions.
`list-table` and inline or local-file `csv-table` directives also support single-line captions,
`header-rows` and `stub-columns` (left-hand row headings). Both default to zero.
Keep at least one body row and one data column after those headings. List tables
require a uniform two-level bullet list; CSV tables pad short rows with empty
cells. `:widths: auto` is supported for all three table directives.
Cells reuse the supported reStructuredText subset above: paragraphs, lists,
admonitions, literal code, images and references keep their meaning. Generated
MDX uses semantic HTML tables with Markdown inside cells, so links and copied
assets still use the normal conversion pipeline and table text remains searchable.
Wide characters and combining marks are measured as display columns.

```rst
.. table:: Supported formats

   +----------+---------+
   | Format   | Native? |
   +==========+=========+
   | Markdown | Yes     |
   +----------+---------+
```

```rst
.. list-table:: Supported formats
   :header-rows: 1
   :stub-columns: 1

   * - Format
     - Status
   * - Markdown
     - **Supported**

.. csv-table:: Supported formats
   :header: "Format", "Status"

   "Markdown", "**Supported**"
   "Sphinx", "Supported subset"
```

CSV `:header:` adds header rows before any `:header-rows:` selected from the
body; indented continuation lines allow multiple supplemental header rows.
Quoted cells may contain commas and line breaks, and doubled quotes retain a
literal quote. CSV defaults to comma separators and double quotes, ignoring
ASCII spaces at the start of a field. `:delim:` and `:quote:` accept distinct
literal Unicode characters; `:delim: space` and `:delim: tab` are also supported. The flag
`:keepspace:` retains leading spaces, which then follow the ordinary
reStructuredText indentation rules inside the cell. Custom escape characters,
character-code notation and remote `:url:` data require manual migration.

To read CSV data from a local file, use `:file:` with no inline table body:

```rst
.. csv-table:: Supported formats
   :file: data/formats.csv
   :encoding: utf-8-sig
   :header-rows: 1
   :stub-columns: 1
```

Paths are relative to the document; a leading `/` means the Sphinx source root.
Names are literal (including `%20`) and must match exact case. Files must be
eligible, nonhidden, nonexcluded regular files inside that root, without symlinks.
`:encoding:` accepts `utf-8` or `utf-8-sig`; otherwise `source_encoding` applies
(default `utf-8-sig`, removing a leading BOM). LF, CRLF and CR are normalized.
Invalid UTF-8 and unsupported control characters fail before output.

Cells support the same markup, substitutions, images, links and nested tables as
inline CSV. A nested `csv-table :file:` in a data cell is relative to that CSV
file; nested directives in supplemental `:header:` cells retain the containing
directive's source directory. Sphinx document links, images, downloads and
`literalinclude` paths keep the original RST document's context. Quoted cells
may retain tabs; the delimiter itself can be selected with `:delim: tab`.

CSV files are read only for published documents and are not copied as downloads
unless explicitly linked. Copy, skip and dry-run modes enforce the same checks.
CSV and literal includes share the 8 MiB per-file, 32 MiB unique-input and
32 MiB expanded-text limits. Nested cells retain the shared depth limit below;
recursive inclusions fail. No Python, Docutils, source code or remote URL is run
or fetched. Local-file CSV support is available in candidate `0.2.0-rc.6`.

Simple-table continuation lines have an empty first column; use an empty comment
(`..`) in that column to start a new row whose first cell is empty. The final
column may extend beyond the border. Keep table borders aligned and separate a
table from surrounding text with blank lines. The importer rejects row/column
spans, malformed geometry, other table options (including numeric column widths,
alignment, classes and named table targets), and headings/section labels/toctrees
inside cells before creating output. It does
not flatten merged cells or silently reinterpret them. Tables are limited to
128 columns, 10,000 rows, 100,000 cells and a 16,384-column border; table/admonition/list
nesting shares a limit of 16. See the upstream
[table syntax](https://docutils.sourceforge.io/docs/ref/rst/restructuredtext.html#tables)
and the [table](https://docutils.sourceforge.io/docs/ref/rst/directives.html#table),
[list-table](https://docutils.sourceforge.io/docs/ref/rst/directives.html#list-table)
and [csv-table](https://docutils.sourceforge.io/docs/ref/rst/directives.html#csv-table)
directives.

Section labels and supported implicit section IDs become explicit anchors used
by links, TOC and search. Non-decomposing Unicode heading identifiers need an
explicit ASCII label. Duplicate heading IDs/implicit names are rejected. Review
old bookmark URLs: Sphinx can emit additional aliases for a labelled heading,
and those alternate IDs are not generated. Page titles come from their document
heading; navigation titles remain separate.

Source `.rst` links and ordinary HTML-builder `.html` links map to Zellij guide
routes. `html_baseurl` supplies the old site's origin/prefix for same-origin
links; it does not set the destination deployment URL. Referenced contained
images/downloads are copied byte-for-byte; root-relative resource paths resolve
from the source directory independently of `html_baseurl`. Excluded files, templates, source
documents, configuration and script files are ineligible as downloads.
`_build`, `_templates`, hidden directories and `node_modules` are omitted.
`html_static_path` and `html_extra_path` are not copied wholesale; use source
asset paths, not Sphinx-generated `_images` or `_downloads` URLs. Asset skip and
dry-run options retain their normal safety checks.

This is a **conservative reStructuredText subset**. Candidate `0.2.0-rc.6`
includes the parsed document includes and navigation/source-selection patterns above.
MyST, autodoc/domain roles, custom extensions, alternate include parsers, raw
directives, spanning tables, unsupported substitution forms, field lists (including `:orphan:`), footnotes,
definition/quote blocks, numbered toctrees, extra directive
options and custom/dirhtml builders require manual migration. Unsupported parsed
constructs fail with the source filename before output is created. No source
build or dependency installation is attempted. See the upstream
[configuration rules](https://www.sphinx-doc.org/en/master/usage/configuration.html),
[toctrees](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html#table-of-contents),
[reStructuredText primer](https://www.sphinx-doc.org/en/master/usage/restructuredtext/basics.html)
and [cross-references](https://www.sphinx-doc.org/en/master/usage/referencing.html).

## Page metadata and document IDs

The five Markdown importers preserve an authored `title` and `description` as active
page metadata. The title falls back to the first document-level H1, then the
navigation label, then the source filename without its extension. A navigation
label stays in the sidebar independently of the page title. Original front
matter remains in comments for reference, including fields that do not map to
Zellij. UTF-8 BOMs, CRLF line endings, multiline descriptions and YAML `...`
closing delimiters are supported. Malformed front matter or incompatible types
for supported fields fail with the source filename before writing output.

Docusaurus sidebar IDs resolve against document metadata. For example,
`docs/01-guide/install.mdx` with `id: setup` can be referenced as `guide/setup`.
A custom ID replaces the filename part only; it cannot contain path separators.
Default numeric prefixes are removed from directory and filename components
when determining IDs; date/version-like prefixes are retained.
`parse_number_prefixes: false` preserves those prefixes for that document.
An exact filename ID from older Zellij imports is still accepted when
unambiguous. Conflicting IDs, ambiguous `.md`/`.mdx` sources and missing sidebar
targets fail before output is written. Docusaurus `sidebar_label` takes
precedence over an explicit label in the sidebar file.

Documents marked `draft: true` or `unlisted: true` in Docusaurus are excluded
and reported, including when explicitly listed. A declarative sidebar does not
promote omitted documents into navigation; an empty sidebar stays empty.
Autogenerated branches expand only their selected folders. Partial documents
(files/folders starting with `_`) and hidden documents are excluded and
reported. When no sidebar exists, or a dynamic sidebar cannot be read, the
existing alphabetical folder fallback applies the same exclusions.

## Docusaurus URL slugs

Explicit document `slug` values become Zellij `route` overrides beneath `/guide`.
An absolute slug such as `/Reference/API` becomes `/guide/Reference/API`.
A relative slug resolves against the source document's parent directories, with
numeric prefixes removed unless that document sets `parse_number_prefixes: false`.
For example, `docs/01-Guides/02-Deep/page.mdx` with `slug: ../Start` becomes
`/guide/Guides/Start`. A slug of `/` selects the guide root.

Generated category indexes also accept `slug`. Both relative and absolute
category slugs resolve from the documentation root: `slug: Sections/Setup`
becomes `/guide/Sections/Setup`, regardless of the category's folder.

These overrides change URLs, not imported file locations. Sidebar entries still
identify the physical pages; converted file links, navigation and search use
their actual routes. Relative document and asset references continue to resolve
from the original source file's directory. Documents without an explicit slug
retain Zellij's existing filename-derived routes. Source `route` metadata stays
in comments; only the converter's validated override becomes active. MkDocs
`slug` fields remain unmapped.

Case is preserved. Percent-encoded Unicode and spaces are decoded once and
written as normalized Unicode routes; links encode the URL correctly. Trailing
slashes are removed. Duplicate routes, including case-only and canonically
equivalent Unicode differences, fail before output writes. Malformed encoding,
queries, fragments, hosts, encoded separators/dot segments, root escapes and
nonportable path segments are rejected. Generated default category routes yield
to explicit slugs, adding a numeric suffix when necessary without moving files.

Custom or versioned source routing, plugin routes and
custom JavaScript number-prefix parsers still require review. These import
improvements are included in candidate `0.2.0-rc.6`.

## Autogenerated Docusaurus sidebars

Declarative sidebar files can mix explicit entries with autogenerated blocks:

```js
module.exports = {
  docs: [
    'intro',
    {type: 'autogenerated', dirName: 'tutorials'},
    'reference',
  ],
};
```

`dirName` is a portable path relative to the source `docs/` directory. `.` selects
the whole directory. The selected directory contributes its contents; its own
name does not add a category. Nested folders become groups. Ordering applies
within each generated block and its nested groups, keeping explicit entries and
other blocks in their original array positions. Repeated references keep their
navigation entries but write the page file only once.

Documents use `sidebar_position`, then a filename's numeric prefix unless
`parse_number_prefixes: false` is set. Folders read one `_category_.json`,
`_category_.yml` or `_category_.yaml` file. Its `label` and `position` take
precedence over the linked index document's sidebar label/title and position,
then the folder's name and numeric prefix. Positions can be negative or
fractional finite numbers. Positioned items precede unpositioned items; filename
order breaks ties. Numeric-looking strings and nonfinite values are rejected.

The default category index conventions recognize `index`, `README`, or a file
with the folder's name, case-insensitively and without its Markdown extension.
A category metadata `link: {type: doc, id: intro}` selects an immediate child's
local document ID, then falls back to a full document ID. `link: null` disables
index detection. Zellij groups have unlinked headings, so a linked index is
placed first inside its group. A folder containing only its linked index becomes
a single page link. Page titles remain independent of category labels.

Category styling/collapse options are reported for review. Custom JavaScript
generators are not executed.
Duplicate category metadata files, malformed metadata, missing selected
directories and paths escaping the docs root fail before any output is written.
Use `--dry-run` to inspect the expanded plan first.

## Category links and generated pages

A manual category can link to an existing document using its full document ID:

```js
{
  type: 'category',
  label: 'Guides',
  link: {type: 'doc', id: 'guides/overview'},
  items: ['guides/install', 'guides/configure'],
}
```

The linked document is imported even when absent from `items`. It becomes the
first child link, with a duplicate direct reference removed. If it is the
category's only document, it becomes a single link using the category label.
Draft and unlisted documents remain excluded, including category links.

Manual categories and autogenerated folder metadata also support:

```yaml
link:
  type: generated-index
  title: Start here
  description: Learn how to install and configure this product.
```

This creates an ordinary editable MDX page with a title, description and nested
list of links to the category's imported documents. It appears first within the
category. The title defaults to the category label; authored titles remain
separate from navigation labels. Metadata text is treated as plain text, so
Markdown/JSX-looking descriptions do not execute code or introduce extra links.

Generated files live under `01-guide/category/<label>/index.mdx`, with normalized
labels and numeric suffixes to avoid existing routes and duplicate names. For
example, the label `Guides` produces `/guide/category/guides`; if that route is
occupied, the generated page uses a numbered alternative. Authored routes,
including excluded and orphan sources, are reserved. Repeated autogenerated
slices share one generated page for the same folder. Empty or fully excluded
categories do not create empty landing pages and are reported.

Source generated-index `image`, `keywords` and other unsupported link
fields are reported for review. Source deployment prefixes are not reused as destination settings;
inspect the new routes before publishing. The output is a plain link list, not Docusaurus
cards or an embedded `DocCardList` component. Foreign sidebar links keep their
existing report-only behavior. These category improvements are included in candidate `0.2.0-rc.6`.

## Document links and assets

Markdown links to converted documents become their Zellij routes. For example,
`02-Setup/APIReference.md#install` becomes
`/guide/setup/api-reference#install`. Nested paths, directory indexes, URL-encoded
filenames, query strings, images and reference-style links are supported. Code
examples are left alone. Extensionless file lookup requires one matching
converted document and must not conflict with a recognized source website URL.

Referenced local files are copied byte-for-byte into `assets/imported/docs/`,
keeping their source directory structure. Docusaurus also supports Markdown
references to its default `static/` folder using `/img/logo.svg` or
`@site/static/img/logo.svg`; those files go into `assets/imported/static/`.
Copied images and downloads use the published asset URL, including the site's
`basePath` (also configure the same prefix in the wrapper's Next config).
Download links open the copied file through ordinary browser navigation, without
requesting page data from the website router.
The dry-run plan lists asset files too.

### Link to existing public assets

Use `--assets link` when the referenced assets already exist on an HTTP(S)
server. Supply that directory with `--asset-base-url`:

```bash
zel cv ./old-docs --out ./manual --layout site \
  --assets link --asset-base-url https://cdn.example.com/manual/
```

For an eligible source asset `media/logo.svg`, this emits
`https://cdn.example.com/manual/media/logo.svg`. No asset file is copied or
symlinked. The imported site can move or deploy independently of the source
folder, while its images/downloads remain dependent on that public server.
Copying remains the default and keeps those files in the imported site.

The base is a directory prefix, with or without a trailing slash. It requires
an absolute HTTP(S) URL and rejects credentials, queries, fragments, whitespace,
backslashes, malformed escapes and dot segments. `--asset-base-url` is rejected
with `copy` or `skip`. A missing base with `link` is an error before writes.

Paths are relative to the asset root selected by the importer:

| Source | Asset root |
| --- | --- |
| MkDocs | Configured Markdown documentation directory |
| Docusaurus | Documentation directory for colocated files; `static/` for public files |
| VitePress | Selected source directory for colocated files; its `public/` directory for public files |
| Jekyll | Selected source directory, including eligible collection assets |
| Hugo | Content directory for bundle resources; static directory for public files |
| Sphinx | Selected source directory, respecting exclusions |

The copy-only `imported/docs/`, `imported/static/` and `imported/public/`
prefixes are not added. Two different files mapping to the same public URL
cause an error before output is written. This mapping expects the existing
server to retain these relative paths; it does not reproduce source-tool asset
hashes, theme transforms or custom CDN layouts. For example, a Hugo bundle
resource keeps its content-relative filename rather than adopting a page's
custom permalink.

Filenames are URL-encoded once, preserving literal percent signs and Unicode.
Each reference retains its query and fragment. The site's deployment prefix
(`basePath`) does not change these absolute asset URLs. Links between converted
documents still become Zellij routes, and unrelated external links remain intact.

The local target must still exist as an eligible regular file. Containment,
exclusion and symlink checks apply in both normal and dry-run modes; missing or
unpublished targets are reported rather than given invented public URLs. Link
mode checks local paths without reading the asset bytes. Content inputs such as
Sphinx CSV tables, parsed includes and `literalinclude` files are still read to build the pages.
HTML/JSX attributes and other unsupported source syntax still need manual work.

The conversion report lists each linked asset and its public URL, including in
`--dry-run`. Conversion does not fetch the URLs or verify their availability;
ensure the listed files exist on your asset server before publishing. These
options also work with `migrate`/`mig` and `ship`. The absolute URLs are saved
in the converted content, so subsequent `build` or `publish` commands need no
asset-base flag. This feature is available in candidate `0.2.0-rc.6`.

### Original website URLs

Current source also rewrites root-relative Markdown URLs and absolute HTTP(S)
URLs matching the configured source origin. It reads local files only; it never
downloads a URL. Queries and fragments stay intact, and original deployment
prefixes are removed when mapping to the new Zellij routes. For example:

```text
MkDocs site_url: https://old.example/manual/
/manual/install/?lang=en#linux -> /guide/install?lang=en#linux
https://old.example/manual/install/ -> /guide/install
```

MkDocs uses `site_url` for the origin/prefix and `use_directory_urls` for its
directory or `.html` URL style. `index.md` and `README.md` use the original
index convention; directory-style sites also recognize their `index.html`
addresses. An omitted/null `site_url` assumes the root and does not claim any
absolute origin. An empty `site_url` selects the source's `.html` style.

Docusaurus uses `url`, `baseUrl`, and the docs plugin's `routeBasePath` (default
`docs`). Routing settings must be a direct literal `module.exports = {...}` or
`export default {...}` object. A single classic preset or docs plugin can supply
literal options. URL lookup follows document IDs, numeric-prefix settings,
explicit slugs, and index/README/folder-name conventions. Explicit generated
category slugs are recognized too. The target is the actual emitted Zellij
route, which may differ from the original filename or public URL.

Relative website links also resolve from the original page's URL directory.
For example, from a MkDocs page at `/manual/nested/topic/`, the link
`../../index.html#welcome` becomes `/guide#welcome`. With
`use_directory_urls: false`, that page is at `/manual/nested/topic.html`, so
the equivalent link is `../index.html#welcome`.

Docusaurus relative document URLs follow the original slug and literal
`trailingSlash: true` or `false` setting. When that setting is absent, a URL
must identify the same imported document with both possible slash policies;
otherwise the converter reports it and leaves it unchanged. Make the intended
destination explicit with a Markdown file link or a root-relative website URL.
This also applies when website lookup and extensionless file lookup disagree.
Existing imports that relied on a guessed extensionless target may now require
that correction.

Explicit Markdown file links retain file-relative semantics, including links to
missing or omitted documents. Existing local asset files, including `.html`
downloads, retain their usual copying policy. Relative website lookup only maps
known document URLs; it does not introduce a new asset search directory.

Referenced assets under the original deployment prefix use the usual contained
docs/static roots and copying policy. Docusaurus's existing `/img/...` and
`@site/static/...` asset references continue to work. Other origins, ports or
schemes and protocol-relative URLs (`//host/path`) remain unchanged. URL path
case is preserved, Unicode is normalized, and percent encoding is decoded once.

Known omitted documents and ambiguous source URLs are reported and left
unchanged. Malformed supported configuration and unsafe local paths fail before
output is written. Computed JavaScript, custom presets/plugins, multiple docs
instances, custom docs/static directories, localization, versioned sites and
generated-category URLs without explicit slugs still need review. HTML/JSX
attributes, relative website assets without a corresponding local file, and
custom routing plugins are not newly interpreted. These improvements are available in candidate `0.2.0-rc.6`.

Source behavior follows the upstream [MkDocs URL settings](https://www.mkdocs.org/user-guide/configuration/#use_directory_urls)
and [Docusaurus document URLs](https://docusaurus.io/docs/create-doc#doc-urls),
[Markdown links](https://docusaurus.io/docs/markdown-features/links), and
[trailing slashes](https://docusaurus.io/docs/api/docusaurus-config#trailingSlash).

Copying is the default (`--assets copy`). To import only documents and generated
configuration, use:

```bash title="terminal"
zel cv ./old-docs --out ./manual --layout site --assets skip
```

`--assets skip` leaves local asset URLs unchanged, copies no referenced asset
files, and reports each omitted reference. Links between converted documents
still become Zellij routes. The skipped asset URLs may not work from their new
locations: supply the files and update their references before publishing.
This policy also applies to `migrate`/`mig` and `ship`; it does not bypass path
safety checks. Dry runs report the same omissions. For assets already hosted
on an HTTP(S) server, use the public link policy below.

Relative `..` segments in links may traverse within the docs root. A reference
that escapes the allowed root, uses a symlink, or targets Git metadata is
rejected before output is written. Duplicate output filenames and public page
routes are rejected too. Unlisted documents are reported, never copied as assets.

Explicit IDs on document-level headings are retained. These source forms work:

```md
# Getting started {#start}
## Installation {#install}
## Docusaurus MDX comment {/* #mdx-install */}
## Docusaurus HTML comment <!-- #html-install -->

Setext heading {#setext}
--------------
```

The converter writes literal MDX headings with those IDs. Links such as
`setup.md#install` and `#install` continue to target them; heading entries in
search and the table of contents use the same IDs. A leading title's explicit
ID becomes an anchor below the page title, so the title appears only once.
Formatting and links inside headings are preserved. Fenced examples remain
literal, including examples that contain shorter code fences.

IDs must be unique within a document and use letters, numbers, `_`, `-`, `.` or
`:`. Unsupported IDs and explicitly identified headings inside lists or
blockquotes or footnotes fail before output is written. Heading classes and other source
attributes are not carried over. After conversion, use `zel check --deep
--strict` to catch collisions with automatically generated or other authored
anchors too.

Missing and ambiguous targets, unmapped root-relative URLs, and HTML/JSX
`href`/`src` attributes appear in the conversion report. They need manual work.
JavaScript imports, custom static directories, source route overrides, and
plugin-generated URLs are not interpreted. Automatically generated heading IDs
can differ between tools, and links to a leading H1 without an explicit ID still
need review. Add an explicit ID in the source before converting when a stable
target is needed. Always build
and inspect the converted site before publishing it.

## What does not come across

**A landing page.** Every one of these tools describes a documentation tree.
Zellij has that *and* marketing pages built from typed sections with no
equivalent anywhere in the source — there is no MkDocs concept that becomes a
pricing table. So a conversion writes a faithful guide folder, a `site.yaml`
carrying whatever identity it found, and a `pages.yaml` with one hero to build
on, and says so every time.

That is not a gap in the converter. It is the part Zellij has that the source
did not, and the part you get to write.

**Links out of the sidebar.** A sidebar holds pages; an external link belongs in
[`menu.yaml`](/guide/menu). Reported rather than dropped, because silently
losing a link to your blog is the kind of thing nobody notices for months.

**Pages the navigation never mentioned.** A file on disk that no `nav` entry
points at may have been hidden deliberately — a draft, a scratch page, something
withdrawn. Publishing it because it happened to be in the folder would be a
worse mistake than leaving it out, so it is listed and skipped.

```
2 thing(s) could not be carried over:
  https://blog.acme.dev: "Blog" is an external link; sidebars hold pages. Add it to menu.yaml.
  draft.md: on disk but absent from the navigation; not converted
```

## When Docusaurus computes its sidebar

`sidebars.js` is a JavaScript module, not a data file. Most are data wearing
JavaScript's clothes and read fine. Some are not:

```js
module.exports = require('./generated').map((item) => ({ ...item }));
```

That is not read at all. The converter falls back to the folder and names the
construct that stopped it:

> `sidebars.js` contains a require() call, so it was not read: this converter
> parses declarative sidebars and will not guess at ones that compute their
> exports. The pages below came from the folder instead, and their order is
> alphabetical rather than yours.

Declining is the point. A sidebar half-read from a file the converter did not
understand would look finished and be wrong.

## Markdown that is not MDX

Zellij compiles guide pages as MDX, which is Markdown plus JSX. That addition is
not free: `{` opens an expression and `<` opens a tag. Prose written for MkDocs
has never had to care.

| In the source | Becomes | |
| --- | --- | --- |
| `{timeout}` | `\{timeout\}` | In prose only |
| `a < b` | `a &lt; b` | `<` is the syntax; `>` is just a character |
| `<n>`, `<your-token>` | `&lt;n>`, `&lt;your-token>` | Nothing closes them |
| `use <div> for layout` | `use &lt;div> for layout` | Naming a tag, not opening one |
| `<br>` | `&lt;br>` | Valid HTML, invalid MDX |
| `<div>…</div>`, `<br/>` | unchanged | Closed, so it is markup |
| `<https://x.com>` | `[https://x.com](https://x.com)` | MDX has no autolinks |
| ` ```sh {x} < y ``` ` | unchanged | Code is quoted by definition |

**The test is whether the tag is closed, not what it is called.** MDX is JSX:
every tag needs a closing tag or a slash, including the ones HTML lets you
leave open. A tag that is genuinely markup is balanced, because whoever wrote
it wanted it to render; a tag that is prose is not, because they were writing
about it.

Two earlier rules were both wrong, and both were caught by converting a real
MkDocs tree and compiling the result — never by reading the code. "Looks like a
tag name" accepted `<n>`. "Is a real HTML element" accepted the `<span>` in
*use `<div>` and `<span>` for layout*.

<Callout type="warning" title="check does not compile MDX">
[`zel check`](/cli/check) validates the content model — links, section types,
sidebar entries. It does not compile your Markdown. A converted folder can pass
`check` and still fail to build, so build it once with
[`zel build`](/cli/build) before you throw the original away.
</Callout>
