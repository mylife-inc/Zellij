<Callout type="tip" title="Available in source">
Portable `dev` builds, serves and watches natively. Hosted `dev` runs the Next.js
development engine in a container. Add `--open` to open the ready site in your
default browser, or `--browser <executable>` to choose a browser.
Native release packages may lag the source version.
</Callout>

```bash title="terminal"
zel dev                         # ./zel.yaml, then ./docs/zellij/zel.yaml
zel dev docs/manual             # a custom configured site or raw content folder
zel dev --port 4000
zel dev --features maths
zel dev --open
zel dev --host localhost --browser firefox
zel dev --host 0.0.0.0           # allow access through your machine's LAN address
```

The selected site's renderer determines the editing workflow. A configured site
reads `content/`; the folder containing `zel.yaml` can have any name.
`--port` overrides `preview.port`, which defaults to 3000.

## Portable Markdown

Portable `dev` is the same editing loop as [`zel view --watch --no-open`](/cli/view):
it validates and builds the documents, prints an HTTP URL, and watches
for content and configuration edits. It binds to loopback by default. Add
`--open` to open the URL after the initial build succeeds and the server is ready.

No Docker, Node or other runtime is needed. Use `--port 0` to choose an available
port automatically. The initial build must succeed before serving; later failures
show a preview notice and keep the last successful site available. Correct the
source to rebuild and reload open browser pages.

Output defaults to `build.out` or `site/` beside `zel.yaml`. A raw Markdown folder
uses the sibling `<folder>-site`. Ctrl-C stops the preview and watcher, retaining
the generated site. You can still open its `index.html` directly without a server.
The port and output location stay fixed for the session; restart to change them.
See [editing documents](/cli/view#editing-documents) for watching and recovery limits.

## Hosted YAML and MDX

For a hosted site, `dev` mounts the content into the container engine, validates
it, installs the wrapper's dependencies into a reusable named volume, and runs
Next.js development mode. It leaves no static export behind. The first run may
need to download the engine image and dependencies; later runs reuse them.
A usable Docker, Podman or nerdctl runtime is required. Missing prerequisites
produce setup guidance and exit code 4; `zel` does not install or start them.

Hosted `dev` needs a port between 1 and 65535. For a hosted static preview with
an automatically selected port, use `zel view --watch --port 0` instead.

The engine watches content edits, additions and deletions, including images and
guide routes. After a short debounce it refreshes public assets, fingerprints and
the search index, then open browser tabs reload their current URL automatically.
Image-only edits also reload the page with updated image fingerprints. This is a
full page reload, so transient UI such as an open search dialog is reset.

Invalid edits are reported in the terminal without triggering an automatic
reload; the open document stays visible. Correcting the content resumes
preparation and browser reloads. Initial preparation must succeed before startup.
Development polling uses a preparation signal created by the watcher; production
pages do not poll. Use a current engine image or updated editable wrapper package for
this behavior. Restart after changing
`basePath`, wrapper configuration or installed features. Ctrl-C stops development
and removes that session's container, retaining its reusable dependency cache.
Use a current engine image if an older image only prepares assets at startup.

### Looking at it on a phone

Hosted `dev` binds to `0.0.0.0` by default and can be reached from another device
using your machine's LAN address. Portable `dev` defaults to `127.0.0.1`; use
`--host 0.0.0.0` to allow LAN access. Both accept `--host localhost`, a specific
IPv4 address, or an IPv6 address such as `--host ::1`. Use `--host ::` for an IPv6
wildcard binding. IPv6 container publishing depends on your runtime's networking.
Pass only the address, without a URL scheme, brackets or port.

With wildcard bindings, the printed browser URL uses loopback; another device
uses your machine's LAN address instead. The `serve` and `view` commands retain
their loopback-only behavior.

If the runtime cannot see the content mount, `zel` reports that the folder is
not shared. Configure file sharing in your runtime, or move the content into an
already shared directory. `zel doctor` helps diagnose runtime availability.

## Options

| Option | Meaning | Default |
| --- | --- | --- |
| `[dir]` | Configured site or explicit raw content folder | `./zel.yaml`, then `./docs/zellij/zel.yaml` |
| `--port <n>` | Preview port; 0 is supported for portable sites | `preview.port`, otherwise 3000 |
| `--host <address>` | Bind to `localhost`, an IPv4 address or an IPv6 address | Portable: `127.0.0.1`; hosted: `0.0.0.0` |
| `--open` | Open the ready site in the default browser | Off |
| `--browser <executable>` | Launch this executable with the site URL; implies `--open` | System default when `--open` is used |
| `--features <selection>` | Complete rendering selection for this session | Portable configuration or hosted engine image |

The browser opens once per session. For a hosted site, `zel` waits for successful
preparation and an HTTP response from that session, then includes the site's
`basePath` in the URL. The first page may still need to compile. An occupied port
or failed initial build does not open an unrelated server. A custom browser is
an executable name or path, not a shell command with arguments; quote paths
containing spaces. Browser-launch failure prints the URL and keeps serving.

Automatic hosted opening requires a current engine image and a published port
reachable from the machine running `zel`. With an older image or a remote runtime,
the development server can continue running, but `zel` warns after five minutes
if it cannot confirm the URL. Open the runtime's reachable address and your site's
`basePath` manually in that case. Use `view --out` for an explicit static export
destination.

## Temporary feature selection

`--features` accepts `maths`, `diagrams`, `maths,diagrams` (either order), `all`,
or `none`. It selects the complete set: `maths` also disables Mermaid.
Mindmaps remain independent. The override lasts for the entire session,
including content edits and portable configuration reloads, without rewriting
authored files. Restart with another selection to change it. Omitting the flag
on a later command restores the usual saved settings.

Hosted development applies the selection to its disposable wrapper before
installing dependencies. Explicit selections use separate dependency caches,
so another build with different features cannot uninstall a live session's
packages. A current engine with explicit feature-selection support is required;
an older engine fails with upgrade guidance. Dependency or startup failures are
reported separately from invalid content.

## Editable wrapper apps

An app created by [`zel new app`](/cli/new) already has a `package.json` and can
use `npm run dev` after installing dependencies. Current wrappers use
`zellij dev -- --port <port>` to own the Next.js process and content watcher.
Older wrappers using `next dev` should switch to that script or run
`zellij prepare --watch` alongside their server.
