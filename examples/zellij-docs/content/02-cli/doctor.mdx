Site-aware diagnostics and JSON reports are included in candidate `0.2.0-rc.4`. Deployment credentials and

```bash title="terminal"
zel doctor
zel doctor docs/manual
zel doctor --config docs/manual/preview.yaml
zel doctor --cwd ../my-product --site-root docs/manual --json
```

The report includes the binary version and platform, selected site root,
configuration file, renderer, content and default output paths, layout, and
preview port. Hosted sites also report the selected container client, connection
and local engine image status.

## Site selection

Without a path, doctor looks for `zel.yaml` in the working directory, then in
`docs/zellij`. An invalid discovered configuration is an error, not a reason to
skip to another folder. `--site-root` selects a folder; `--config` selects one
configuration file and uses its parent as the site root. These share the
[global selection rules](/cli/config). Explicit paths also support legacy hosted
content, legacy flat portable configurations, and raw Markdown folders.

A **portable** site does not need a container runtime: doctor skips every runtime
probe, even when container endpoint variables are set. For a **hosted** site it
checks the runtime as described below. Without a configuration or explicit path,
legacy hosted content can still be discovered. If no site is found, doctor
retains its runtime-only diagnostic behavior; a product README alone does not
select a portable site. Pass `.` explicitly to diagnose a raw Markdown folder.

Doctor parses site settings and portable presentation settings. It does not scan
pages, check navigation targets or assets, validate content, test output ownership
or writability, reserve the preview port, or contact deployment providers. The
output path and port describe defaults; they are not readiness guarantees.
Use [`zel check`](/cli/check) to validate the selected site's content. Doctor does
not write configuration, generate output, pull images or start services.

## Which commands need a runtime?

| Operation | Container runtime required? |
| --- | --- |
| Portable `build`, `check`, `view` and static-file `serve` | No |
| Implemented scaffolding, `explain`, `list`, `context`, `detect`, `convert` | No |
| `publish --dry-run` | No; resolves a saved plan without validation or credential checks |
| `publish` / `pub` with image push | Yes; builds and pushes the configured image |
| `netlify` / `deploy netlify` / saved Netlify publication | Portable: no. Hosted: yes, for the static export. Requires Netlify credentials/network |
| `image dockerfile` | No; prints the recipe without building it |
| Hosted `check`, `dev`, static/image builds; `image static` / `si` and `image next` / `ni`, `image build`, `run`, `push` | Yes |
| `migrate` | Its conversion is native; its final hosted check needs a runtime |
| `ci [site]` / `ci init github\|gitlab\|circle` | Git required; no local runtime; a generated job may need one on its runner |

A container command that cannot find a usable runtime stops with **exit code
4**, before starting its container operation. Portable commands remain usable.
`zel` does not install software, start a daemon, change renderer, or send the
work to a remote service as a fallback.

## Runtime selection

Without explicit endpoint environment variables, `zel` tries **Docker, Podman,
then nerdctl**, using each client's configured connection. If none succeeds,
it tries existing local Docker-compatible sockets for Colima, Docker Desktop,
Rancher Desktop, rootless Podman, and `/var/run/docker.sock`. These socket
overrides are used only with the Docker client; Podman has its own connection
settings. Windows uses the clients' configured connections, including Docker's
named-pipe connection, rather than probing Unix sockets.

An endpoint variable selects its associated runtime:

| Runtime | Variables |
| --- | --- |
| Docker | `DOCKER_CONTEXT`, `DOCKER_HOST` |
| Podman | `CONTAINER_CONNECTION`, `CONTAINER_HOST` |
| nerdctl | `CONTAINERD_ADDRESS`, `CONTAINERD_NAMESPACE` |

When one of these is nonempty, `zel` uses that runtime and does not substitute
another runtime or socket if the connection fails. Variables selecting multiple
runtimes are rejected; unset the ones you do not intend to use. Within one
runtime, the client applies its own precedence. For example, Docker's
`DOCKER_CONTEXT` overrides `DOCKER_HOST`.

Explicit endpoint values and failed probe output are hidden from diagnostics
because they can contain credentials. A discovered local socket is shown by
path. These conventions follow the clients' own settings:
[Docker](https://docs.docker.com/reference/cli/docker/),
[Podman](https://docs.podman.io/en/latest/markdown/podman.1.html), and
[nerdctl](https://github.com/containerd/nerdctl/blob/main/docs/config.md).

Automatic discovery allows three seconds per `info` probe within a shared
twelve-second budget. When endpoint environment variables explicitly select one
runtime, its probe can use the full twelve seconds: there are no fallback clients
to reserve time for. This accommodates slower startup and client plugin checks.
Version and image inspection each have a two-second timeout. These
limits cover preflight probes; builds, downloads and foreground servers can take
longer. A working runtime with unavailable version or image metadata is still
usable; doctor reports that metadata as unavailable or unknown.

## When a runtime is missing or unavailable

The error distinguishes an executable that cannot be found, a client that cannot
be executed, an unsuccessful `info` command, and a timeout. Run `docker info`,
`podman info`, or `nerdctl info` directly for that client's detailed error.

| Platform | Next step |
| --- | --- |
| macOS | Start Docker Desktop or an existing Colima/Podman machine. Install a runtime first if needed; Colima also needs the Docker CLI. |
| Windows | Start Docker Desktop in Linux-container mode or an existing Podman machine. Install Docker Desktop or Podman first if needed. |
| Linux | Check the Docker/containerd service or rootless Podman, socket permissions and connection settings. Install a runtime first if needed. |

These are setup instructions for the user; `zel` does not run them automatically.
A responding client is a prerequisite, not proof that every image, network,
registry credential or mounted directory will work.

## The engine image

For hosted sites and runtime-only diagnostics, the report shows the configured
image and whether inspection found it locally.
A failed inspection is reported as not pulled; a timeout or an unavailable
inspection is reported as unknown. This check never pulls an image.

The default tag matches the CLI version: `ghcr.io/mylife-inc/zellij-base:0.2.0-rc.4`
for this release. Override it when your
organisation mirrors the image internally:

```bash title="terminal"
ZELLIJ_IMAGE=registry.internal/zellij-base:0.2.0-rc.4 zel doctor
```

The first container operation may download an absent image. Hosted builds also
install app dependencies, so a local base image alone does not guarantee an
offline build.

## JSON and exit codes

`zel doctor --json` writes one report to stdout with `schema_version: 1`, binary
`version` and `target`, `ok`, `exit_code`, `site`, `runtime`, `image` and `error`.
`site` is null when no site could be resolved; otherwise it contains `root`,
`config` (null for inferred settings), `layout` (`versioned` or `legacy`),
`renderer`, `content`, `output`, and `preview_port`.

Runtime status is `not_required` for portable sites, `not_checked` when site
configuration fails first, `available`, or `unavailable`. An available runtime
includes `program`, `version` and a redacted `endpoint`. Image inspection reports
`reference` and status `local`, `not_pulled`, or `unknown`; `image` is null when
not inspected. `error` is null on success, otherwise an object with `kind`
(`configuration` or `runtime`) and `message`.

| Exit code | Meaning |
| --- | --- |
| `0` | Site settings passed preflight and any required runtime responded, or runtime-only diagnostics succeeded |
| `2` | Invalid site selection or configuration |
| `4` | Required runtime discovery failed or endpoint settings were ambiguous |
| `1` | Filesystem or other unexpected I/O error |

An absent local image or unavailable version/image metadata does not fail doctor.
Handled configuration/runtime errors appear in the JSON report without duplicate
stderr diagnostics. `--verbose` can add tracing to stderr; `--quiet` preserves the
report. Argument parsing errors and an invalid `--cwd` occur before the doctor
report starts and keep the CLI's ordinary stderr diagnostics.

## Housekeeping

These commands are available in candidate `0.2.0-rc.4`. Stable `0.1.3` predates
them; use the candidate's [pinned installation instructions](/cli).

| Command | Purpose |
| --- | --- |
| [`zel version`](/cli/version) | Binary, selected image and embedded engine/schema details, without Docker |
| [`zel pull`](/cli/pull) | Pull or update the selected engine image ahead of time |
| [`zel upgrade`](/cli/upgrade) | Verify and replace this binary with a newer release |

[`zel completions <shell>`](/cli/completions), also `zel comp`, is available in
current source for Bash, Zsh, Fish, PowerShell, and Elvish.

Use `zel upgrade --check` to inspect the available stable native version without
replacing the executable. `zel --version` retains its compact binary version.
