A Zellij site is a Next.js app that statically generates every page. Deploy it
wherever you deploy Next.js.

```bash title="terminal"
npm run build     # runs `zellij prepare`, then `next build`
npm run start
```

## Where the content folder lives

The wrapper decides. It is the one thing about the site that is not inside the
content root, because it is not about the site — it is about the checkout.

```tsx title="src/app/[[...slug]]/page.tsx"
const zellij = createZellijPages({
  contentDir: '../../docs/external',
});
```

Give preparation the same path in both `predev` and `prebuild`:

```bash
zellij prepare --content ../../docs/external
```

Use the same runtime options for the wrapper's page, root layout and metadata
factories. Preparation does not infer options from your TypeScript files.

That is what lets a product repository keep its content beside the product:

```
payos/
├── apps/
│   ├── product/           # the application
│   └── external/          # the Zellij wrapper — no content of its own
└── docs/
    ├── external/          # the content root
    └── internal/          # not Zellij's business
```

## Under a path prefix

To serve at `example.com/products/acme/docs`, set the prefix once in content:

```yaml title="site.yaml"
basePath: /products/acme/docs
```

The generated wrapper uses `withZellij()`, which reads that value for Next's
build and passes the same prefix to Zellij's runtime. Rebuild after changing it;
Next embeds the prefix in browser bundles.

If the wrapper owns deployment settings, omit `basePath` from content and set it
in Next instead:

```js title="next.config.js"
import { withZellij } from '@shebka/zellij/next-config';

export default withZellij({ basePath: '/products/acme/docs' });
```

For a custom content root, give `withZellij` the same path as preparation and
all runtime factories:

```js
export default withZellij({}, { contentDir: '../../docs/external' });
```

The second argument also accepts `appRoot` and `configFile` for a legacy config.
Matching repeated prefix settings are allowed. Conflicting explicit settings,
including an explicit empty string, fail with a diagnostic. Remove the content
setting when the wrapper owns it. The internal `ZELLIJ_BASE_PATH` build value is
reserved; configure the prefix through `site.yaml` or `withZellij`.

Next prefixes its links and resources. Zellij prefixes image sources, search
requests, social-card images and sitemap URLs. CI checks a production build with
home/guide redirects, nested links, optimized and ordinary images, fonts/scripts,
search navigation and metadata under a nonempty prefix.

This is HTTP deployment support. Directly opening an exported `index.html` with
`file://` is a separate planned portable-output capability; today's export does
not promise that behavior.

## SEO

Set the canonical origin and a share image:

```yaml title="site.yaml"
siteUrl: https://acme.example.com
ogImage: assets/og.png
```

`siteUrl` is what turns relative URLs absolute, which Open Graph and canonical
tags require. With it set you get, per page:

- a `<title>` and meta description from the page's own fields
- Open Graph and Twitter card tags, with the share image
- a canonical URL
- an entry in `/sitemap.xml`, and a `/robots.txt`

Both `sitemap.ts` and `robots.ts` are one line each in the wrapper.

## Performance

The demo site scores 100 across the board on desktop Lighthouse. The things
that keep it there are structural, not tuning:

- every page is statically generated; no data fetching at request time
- syntax highlighting happens at build time, so no highlighter ships
- the search index and library load on first open of ⌘K, not before
- only the active theme's tokens are emitted, unless the runtime picker is on
- imagery goes through `next/image`, and only the hero is `priority`
- animation is `transform` and `opacity` only, so entrances cannot shift layout

## Upgrading

Bump the dependency. Nothing was generated into your repository, so there is
nothing to re-merge — all the rendering logic is in the package.

Unknown keys in `site.yaml` warn rather than fail, and unknown keys inside a
section file are accepted silently, so a content folder written against a newer
engine still builds on an older one. Downgrading is survivable; you lose
features, not the build.
