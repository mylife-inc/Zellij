---
title: Lab 4 — A repository you already have
description: Migrate the documentation already in your repo, and publish it on every push.
---

**You have:** code on GitHub, and documentation somewhere in it — a `docs/`
folder, a wiki you exported, a `README.md` that grew. **You will have:** that
documentation as a Zellij folder, in the same repository, published by CI.

**Needs:** `zel`, push access to the repository. A container runtime for the
local steps.

This is [Lab 3](/guide/quickstart/new-project) with an awkward first half: the
repository exists, so nothing can be scaffolded around you.

<Callout type="info" title="What runs today">
Every command in this lab runs.
</Callout>

<Steps>

<Step title="Work on a branch">

```bash title="terminal"
git switch -c docs/zellij
```

Everything below writes new files beside the old ones. Keep the original while
reviewing the conversion. A branch separates committed changes; untracked files
can remain across branch switches, so inspect `git status` before switching.

</Step>

<Step title="See what you have">

```bash title="terminal"
zel detect docs
```

If it names MkDocs, Docusaurus, VitePress, Jekyll, Hugo or Sphinx, [Lab 2, step 2](/guide/quickstart/existing-docs)
is your next move — convert, then come back here at step 4.

Point detection at the source tool's configuration directory. For example, if
`mkdocs.yml` is at the repository root, use `zel detect .` instead.

If it recognises nothing, plain Markdown can be built directly with `zel build docs`
or previewed with `zel view docs`. To migrate into hosted MDX and page sections,
[Lab 2, step 3](/guide/quickstart/existing-docs) describes the AI-assisted route.

Either way, write into a **new folder**:

```bash title="terminal"
zel migrate docs --out docs-site --layout site
```

Use that command only when detection identified a supported source format;
substitute its actual configuration directory for `docs`. The output is a
configured hosted site with `zel.yaml` and `content/`. It performs
`detect` → `convert` → `check`, stopping at the first failure. It does nothing
the three commands cannot; it exists because forgetting to validate after a
conversion is the mistake everybody makes once.

Read what the conversion could not carry over before going further — external
links belong in `menu.yaml`, and a page absent from the navigation was listed
rather than published.

</Step>

<Step title="Decide where it lives">

Three arrangements, and this is a decision worth making deliberately because
moving later means updating the pipeline and every relative link.

| Layout | When |
| --- | --- |
| `docs/zellij/` | Conventional site root, containing `zel.yaml` and `content/`; found by bare commands from the repository root. |
| `docs-site/` or `docs/external/` | Any name is valid; pass the site root explicitly. Other documentation and specs can remain separate. |
| `packages/*/docs/zellij/` | A monorepo where each package publishes its own site. Generate a separately named pipeline per site. |

This lab keeps the new site at `docs-site/` so the source at `docs/` remains
available for comparison. Inspect `git status --short` and the conversion
report. If you later move the complete site root, update the explicit paths and
regenerate its workflow. Do not replace the source folder before reviewing the
rendered content and preserving its history/assets.

</Step>

<Step title="Build it once, before you delete the original">

<Callout type="warning" title="check does not compile MDX">
`zel check` validates the content model. It does not compile your Markdown, and
MDX treats `{` and `<` as syntax. A converted folder can pass `check` and still
fail to build.
</Callout>

```bash title="terminal"
zel dev docs-site --open   # read the pages, then stop with Ctrl-C
zel build docs-site       # prove the imported MDX compiles
```

</Step>

<Step title="Add the pipeline">

```bash title="terminal"
zel ci docs-site --target image --zel-version 0.2.0-rc.5
```

<Callout type="tip" title="A separate workflow, not a step in yours">
It writes `.github/workflows/docs.yml` scoped to `docs-site/**` and that workflow file, and
leaves your existing pipelines alone — your test suite should not run because
somebody fixed a typo, and your documentation should not wait for it.

It refuses to overwrite a workflow that is already there, and prints whatever
you still have to do that a file cannot: the workflow permission, or the
secrets.
</Callout>

</Step>

<Step title="Add the check to pull requests">

The workflow checks and builds the Next image on pull requests without
publishing. Eligible `main` pushes and manual runs build once and push to GHCR.
Candidate `0.2.0-rc.5` and its matching engine image are published. Other selected
versions must exist before enabling the workflow; stable `0.1.3` is incompatible.
See [CI](/cli/ci).
A broken documentation link or build now fails before publication.

</Step>

<Step title="Open the pull request">

```bash title="terminal"
git add . && git commit -m "docs: migrate to Zellij"
git push -u origin docs/zellij
gh pr create --fill
```

The pipeline checks and builds the pull request. Review the rendered pages as
well: passing validation does not prove that every source-tool feature survived
migration.

</Step>

<Step title="Turn on package writing">

The image publication job requests `packages: write`. Ensure organization,
repository and GHCR package policy permit that repository to push. A 403 can
indicate package access or policy restrictions even when authentication succeeds.

</Step>

</Steps>

## Keeping the old site up during the switch

You probably have documentation published somewhere already, and taking it down
to try something is not a real option.

<Steps>
<Step title="Publish the new one somewhere temporary">

```bash title="terminal"
zel netlify docs-site --site your-existing-project-id
```

Create the destination site first and export `NETLIFY_AUTH_TOKEN`. The native
command builds and uploads once, creating a draft preview by default. It does
not create a Netlify account or site.

</Step>
<Step title="Circulate it">
Let people who read the documentation read this one for a week. They find the
things a validator cannot: a page that lost its ordering, a diagram that was an
image, a link that pointed somewhere clever.
</Step>
<Step title="Move the domain">
Repoint the CNAME at the new site — [Lab 1, step 6](/guide/quickstart/from-scratch)
has the whole DNS sequence — and delete the old deployment once traffic has
moved.
</Step>
</Steps>

## What this buys you

A build that fails when documentation is wrong. Before this, a stale link was
discovered by a reader; now it is discovered by the pull request that created
it.

That is the entire argument for documentation living in the repository, and it
only works if the check runs on pull requests. If you do one step from this lab,
do step 6.
