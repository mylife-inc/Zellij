---
title: Lab 3 — A new project, docs beside the code
description: One repository with a configured documentation site and a GitHub workflow.
---

Create a software repository with documentation in `docs/zellij/` and product
code in `product/`. The documentation folder contains `zel.yaml`, authored
`content/`, and generated `site/`. A different documentation folder name is
allowed with `--docs-dir`.

<Callout type="warning" title="Compatible release required for CI">
These commands describe current source. The generated workflow pins planned
`zellij-v0.2.0` and its matching engine image. Publish that compatible release
before enabling the workflow; public 0.1.3 cannot run the new configured-site
commands. Generation does not publish a release or provision credentials.
</Callout>

<Steps>
<Step title="Create the repository layout">

```bash
zel new project acme --product-lang rust
cd acme
```

This writes a hosted documentation starter, a product README, and
`.github/workflows/docs.yml`. `--product-lang` prints a language-specific hint;
it does not initialize a Rust project or install dependencies. Run your own
language tooling inside `product/` when ready.

```text
acme/
  docs/zellij/
    zel.yaml
    content/
  product/
    README.md
  .github/workflows/docs.yml
```

</Step>
<Step title="Preview the documentation">

```bash
zel check
zel dev
```

The default convention finds `docs/zellij/zel.yaml`. Hosted preview requires a
usable container runtime; open the printed localhost URL. Edit files inside
`docs/zellij/content/`. See [runtime diagnostics](/cli/doctor) if no runtime is
available. Generation never installs or starts one automatically.

</Step>
<Step title="Review the generated workflow">

The starter workflow validates with `--strict --deep` and builds a Next image
on pull requests. On eligible `main` pushes or manual runs it builds once and
pushes `ghcr.io/<lowercase-owner>/<lowercase-repo>/docs:<commit-sha>`. It watches
the configured documentation folder and its own workflow file.

The installer and engine image use the pinned compatible version. GHCR login
uses the job's `GITHUB_TOKEN` with `packages: write`; your organization and
package settings must allow that repository to publish. Pull requests never
publish and do not receive deployment credentials.

To regenerate this legacy image-publication preset after initializing Git:

```bash
zel ci --target image --zel-version 0.2.0 --force
```

For an explicit static or Next artifact and a fixed registry destination, add
saved `image` and `publish` settings as described in [publication](/cli/publish),
then use `zel ci --zel-version 0.2.0 --force`.

</Step>
<Step title="Commit and push after the release is available">

```bash
git init
git add .
git commit -m "Add product and documentation starter"
gh repo create acme --private --source=. --push
```

Private repository CI usage depends on your GitHub plan. Review the workflow
and release prerequisites before this push enables it.

</Step>
<Step title="Run the workflow manually">

```bash
zel ci run --workflow docs.yml --ref main
gh run watch
```

An empty commit may not match the documentation path filters; manual dispatch
is the way to rebuild without a documentation change. The workflow must exist
on the default branch before GitHub accepts dispatches. A successful image run
prints its registry destination; use that exact reference to pull/run it.

</Step>
</Steps>

## Choose Netlify instead

Add saved delivery and CI settings to `docs/zellij/zel.yaml`, retaining its
existing version and renderer:

```yaml
publish:
  action: deploy
  provider: netlify
  site: your-existing-site-id
ci:
  zel-version: 0.2.0
  production: false
```

Then regenerate and review the local workflow:

```bash
zel ci --force
```

Set the repository secret `NETLIFY_AUTH_TOKEN` before running it. Generation
uploads nothing by default; `--provision` explicitly copies an environment token
to repository secrets through the GitHub CLI. Native Netlify delivery builds and
uploads static HTML once, without Node or the Netlify CLI on the runner. Hosted
rendering still uses its container. Draft previews are default; choose
`ci.production: true` for production publication.

The [`zel ci` reference](/cli/ci) covers branch/tag/schedule settings, secret
handling, legacy options and release requirements. The [site configuration
reference](/cli/config) covers discovery and overrides; `zel.toml` is not used.
