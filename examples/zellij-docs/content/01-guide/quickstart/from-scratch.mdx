---
title: Lab 1 — Start from nothing
description: An empty folder to a published site, with the browser open the whole time.
---

**You have:** nothing. **You will have:** a site you wrote, running locally,
then published.

**Needs:** `zel`, and a container runtime from step 2 onward. Check with
`zel doctor`.

<Callout type="info" title="Use candidate 0.2.0-rc.5 or current source">
The complete loop is implemented: create a site, preview edits, validate, build
and deploy. This lab uses the hosted renderer and its container runtime. Native
[portable Markdown sites](/cli/build) also work without a server or container.
Provider access must be configured before the publication step.
</Callout>

<Steps>

<Step title="Create a content folder">

```bash title="terminal"
zel new docs my-docs --guide
```

```
✓ my-docs
  zel.yaml
  content/site.yaml
  content/pages.yaml
  content/sections/home/hero.yaml
  content/sections/home/features.yaml
  content/menu.yaml
  content/01-guide/_sidebar.yaml
  content/01-guide/index.mdx
  content/assets/.gitkeep

  Next: zel dev my-docs
```

**What just happened.** You have a small site that is complete and correct — not
a template with `TODO` in it. Every field written is a field the schema accepts,
so each file is a working example of its own format. `zel check my-docs` passes
right now.

No `package.json`, no `node_modules`, nothing to install. This folder is
**only** the words and the structure.

<Callout type="info" title="Nothing ran but a file writer">
`zel new docs` is native code. It wrote the configuration and content files and exited — **no container
started, no image pulled, no Docker needed**. If your `docker pull` is still
going, it did not wait for it.

That changes at the next step. `zel dev` is the first command that needs a
container: it starts one, mounts this folder into it, and runs the engine. The
two commands have nothing in common except the folder they both care about.

| | | |
| --- | --- | --- |
| `zel new docs` | Writes files | No container |
| `zel dev` | Serves them | Starts one |
| `zel check` | Validates them | Starts one |
| `zel build` | Compiles them | Starts one |
</Callout>

<Callout type="tip" title="What about the Next.js app?">
There isn't one, and you do not need one. The application that renders your site
lives inside the container image. It does not need to be part of your repository;
upgrading the engine image updates the rendering implementation.

If you *do* want it on disk — because you deploy to Vercel, or you want your own
React pages alongside — `zel eject my-docs --out my-site` extracts a wrapper and
engine while referencing the existing content. Install its dependencies and run
`npm run dev` there. [`zel new app`](/cli/new#zel-new-app-dir) is another option
when you already have a built local engine package to select with `--engine`.
</Callout>

</Step>

<Step title="Watch it while you write">

```bash title="terminal"
zel dev my-docs --open
```

<Callout type="info" title="Open after the server is ready">
`--open` launches your browser after startup succeeds. Omit it to open the
printed URL yourself. The default port is 3000; `--port` overrides it.
</Callout>

The terminal reports the selected image, mounted content and serving URL.
Edit files under `my-docs/content`; press Ctrl-C in the terminal to stop.

It validates first, installs what the site needs, then serves. The first run
may download the engine image and install dependencies into a named volume.
Later runs reuse the image and dependency cache; timing depends on the machine
and selected features.

<Callout type="info" title="Edits reload the browser">
The engine watches content files, assets and guide routes. A valid change
refreshes prepared content and reloads open pages. Invalid edits appear in the
terminal while the last rendered page stays visible; correcting them resumes
reloads. Restart after changing the deployment prefix or installed features.
</Callout>

**Leave this running.** Open `my-docs/content/sections/home/hero.yaml` in your editor:

```yaml title="my-docs/content/sections/home/hero.yaml"
type: hero
headline: Your product, explained
subhead: Change this line and watch the browser.
cta:
  - { label: Read the guide, href: /guide, style: primary }
```

Save. The browser updates before you get back to it.

Now break something on purpose — change `type: hero` to `type: heroo` — and
save. The terminal reports the invalid section; the browser keeps the last valid
page until you fix it. The diagnostic identifies the file and unknown type:

```
my-docs/content/sections/home/hero.yaml
  unknown section type "heroo"
```

That is the loop. You are never guessing whether a change was valid.

</Step>

<Step title="Add a page">

```bash title="terminal"
zel new page pricing --sections hero,pricing-table,faq --site-root my-docs
```

Three section files appear under `my-docs/content/sections/pricing`. The command
prints an entry to add to `my-docs/content/pages.yaml`; it does not edit that
authored file. Add the entry and replace its placeholder description:

```yaml
- name: pricing
  title: Pricing
  description: Choose a plan for your team.
  sections:
    - pricing/hero
    - pricing/pricing-table
    - pricing/faq
```

Once saved, the browser picks up `/pricing` without a restart.

Not sure what a section type takes?

```bash title="terminal"
zel list sections          # all 23 types
zel explain pricing-table  # one of them, in full
```

`explain` prints every field, which are required, the allowed values, and the
shape of anything nested. It is generated from the same schemas that validate
your content, so it describes exactly what will be accepted.

</Step>

<Step title="Add a guide">

A landing page is sections. Documentation is Markdown.

```bash title="terminal"
zel new guide docs --title "Documentation" --site-root my-docs
```

```
✓ 02-docs/_sidebar.yaml
✓ 02-docs/index.mdx
```

The starter already has `01-guide`, so this guide receives the next prefix.
Add pages by creating files under `my-docs/content/02-docs`. For example:

```mdx title="my-docs/content/02-docs/install.mdx"
---
title: Installing
description: Get it running in two minutes.
---

## Requirements

Anything that runs a container.

<Callout type="tip" title="On a Mac">
`brew install colima && colima start`
</Callout>
```

Then list it in the sidebar:

```yaml title="my-docs/content/02-docs/_sidebar.yaml"
title: Documentation
order: 1

nav:
  - index
  - install
```

It appears at `/docs/install`, in the sidebar, in the table of contents, and in
⌘K search.

</Step>

<Step title="Validate before you ship">

```bash title="terminal"
zel check my-docs --deep --strict
```

Every internal link is resolved, every section type checked, every sidebar entry
matched to a file that exists. It exits non-zero when something is wrong, so it
works as a pre-commit hook.

This runs the engine in a container with your folder mounted read-only, so it
needs a container runtime. Timing depends on the image and dependency cache.

<Callout type="warning" title="If your folder is outside your home directory">
Container runtimes only share part of your filesystem with the virtual machine
they run in. Colima shares `$HOME` and not `/tmp`. A bind mount of a path it
cannot reach does not fail — it mounts an empty directory.

`zel check` detects that and says so:

```
error: my-docs is not shared with the container runtime
```

Work under your home directory, or share the path:

```bash title="terminal"
colima stop && colima start --mount '/tmp:w'
```

On Docker Desktop it is Settings → Resources → File sharing.
</Callout>

</Step>

<Step title="Ship it">

<Callout type="info" title="Both delivery paths are available">
`zel netlify` builds and uploads static HTML to an existing project.
`zel image next` packages the site with a Next.js server; `zel image static`
packages static HTML with an HTTP server. Choose the artifact your host needs.
</Callout>

Choose one of these delivery paths.

## A · A static site on Netlify

Static hosting serves the generated files. Use a Netlify plan suitable for your
account and expected usage.

**Create a Netlify account and project.** Use its dashboard to create the project
and copy the Project ID. Zellij needs no Netlify CLI or Node.js for uploading.
If you prefer Netlify's own administration tool, the optional alternative is:

```bash title="terminal"
npm install -g netlify-cli
netlify login
```

A browser opens; authorise it.

**Optional CLI project creation.**

```bash title="terminal"
netlify sites:create --name my-docs
```

```
Site Created

Admin URL: https://app.netlify.com/projects/my-docs
URL:       https://my-docs.netlify.app
Project ID: 91774174-d4c2-41b5-aa4b-ac61eeadbf51
```

<Callout type="tip" title="Project ID is the site ID">
Netlify's UI calls it **Project ID** and its API calls it the site ID. Same
value.
</Callout>

**Build and upload with Zellij.** Set `NETLIFY_AUTH_TOKEN` in your environment
using a personal access token from the account that owns this project. Keep it
out of shell history, documentation and Git. Set the non-secret project ID, then
create a draft preview first:

```bash title="terminal"
export NETLIFY_SITE_ID=YOUR_PROJECT_ID
zel netlify my-docs
# After reviewing the returned draft URL:
zel netlify my-docs --prod
```

<Callout type="info" title="Native upload and optional Netlify CLI">
`zel` uses the supplied token and project ID; it does not read Netlify CLI's
stored login. If using that CLI instead, `zel build my-docs --out dist` followed
by `netlify deploy --prod --dir dist` remains a valid manual alternative and
uses the login created by `netlify login`. CI requires explicitly stored secrets.
</Callout>

### Getting the two values CI needs

**The site ID.** The dashboard or `sites:create` shows it as **Project ID**; Netlify's API calls
the same value the site ID. If you have lost it:

```bash title="terminal"
netlify sites:list --json | jq -r '.[] | select(.name=="my-docs") | .site_id'
```

**The auth token.** Prefer a separately revocable personal access token from
Netlify's user settings. If you already use Netlify CLI, its login configuration
can contain a token; this optional legacy recipe reads it without printing it:

```bash title="terminal"
# macOS
NETLIFY_CONFIG="$HOME/Library/Preferences/netlify/config.json"
# Linux
[ -f "$NETLIFY_CONFIG" ] || NETLIFY_CONFIG="$HOME/.config/netlify/config.json"

export NETLIFY_AUTH_TOKEN=$(jq -er '.users[.userId].auth.token | select(type == "string" and length > 0)' "$NETLIFY_CONFIG")
```

Check it worked without printing the token:

```bash title="terminal"
test -n "$NETLIFY_AUTH_TOKEN" && echo "Netlify token is set"
```

<Callout type="info" title="The CLI login file is outside the project">
Netlify CLI's [documented configuration locations](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/#configjson-location)
follow the operating system's application preferences:

| | |
| --- | --- |
| macOS | `~/Library/Preferences/netlify/config.json` |
| Linux | `~/.config/netlify/config.json` |
| Windows | `%APPDATA%\netlify\Config\config.json` |

And the token is nested at `users.<userId>.auth.token` — there is no top-level
`auth_token` key. Both of those are easy to get wrong in a way that produces an
empty string rather than an error, which then fails in CI as a 401 that looks
like a permissions problem.
</Callout>

**A personal access token is the preferred choice** for a shared
pipeline: **User settings → Applications → Personal access tokens → New access token**.
See [Netlify's user settings](https://docs.netlify.com/manage/accounts-and-billing/user-settings/).
It can be revoked
on its own without logging your laptop out, and it is not tied to your CLI
session.

Put both into the repository: **Settings → Secrets and variables → Actions →
New repository secret**, as `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID`. That is
what [Lab 3](/guide/quickstart/new-project) and
[Lab 4](/guide/quickstart/existing-repo) expect.

The long spelling of the native [deployment command](/cli/deploy) is:

```bash title="terminal"
zel deploy netlify my-docs --prod
```

### A custom domain

Say you own `example.com` and want the site at `docs.example.com`.

<Steps>
<Step title="Find who actually serves your DNS">

```bash title="terminal"
dig +short NS example.com
```

This is the step people skip, and it is the one that costs an afternoon. Where
you *bought* the domain is often not where its DNS is *served*. A record added
in the registrar's panel while the nameservers point elsewhere is inert — it
publishes nothing, and `dig` keeps returning nothing however long you wait.

Whatever that command prints is where the next step happens.

</Step>
<Step title="Add one CNAME, there">

| Field | Value |
| --- | --- |
| Type | `CNAME` |
| Name / Host | `docs` |
| Points to | `my-docs.netlify.app` |
| TTL | whatever it offers |

Use the exact `*.netlify.app` hostname from the dashboard or `sites:create`. A CNAME to a
hostname that does not exist fails silently.

<Callout type="warning" title="Do not repoint your nameservers">
Netlify offers to host your whole DNS zone. That means recreating **every**
record — including `mail`. For one subdomain, a CNAME touches nothing else.
</Callout>

</Step>
<Step title="Tell Netlify the name is yours">

**Project → Domain management → Add a domain** → `docs.example.com`.

Netlify verifies the CNAME it can already see, then issues a Let's Encrypt
certificate. Until you do this, the request arrives at Netlify and gets a 404 —
it has no way to know which project the hostname belongs to.

</Step>
<Step title="Confirm">

```bash title="terminal"
dig +short docs.example.com && curl -sI https://docs.example.com | head -1
```

```
my-docs.netlify.app.
13.52.188.95
HTTP/2 200
```

</Step>
</Steps>

## B · A container, running locally

Right when you need image optimisation, or when the site has to live wherever
your other services live.

```bash title="terminal"
zel image next my-docs --tag my-docs:dev
zel image run my-docs:dev
```

That is a Node runtime serving your site on port 3000 — the same artefact you
would push to Railway, Fly.io, Cloud Run or ECS.

```bash title="terminal"
zel image push my-docs:dev --registry ghcr.io/you
```

You never wrote a Dockerfile. If your organisation requires one in the
repository, [`zel image dockerfile`](/cli/image#zel-image-dockerfile) prints the
one `zel` would have used.

</Step>

</Steps>
