Four hands-on labs. Each starts where you are, ends with a site somebody else
can read, and says what every command does before you run it.

These labs include hosted development and deployment. For a rich double-click
website, only `zel` is needed: run `zel new docs my-docs`, then
`zel build my-docs`, and open `my-docs/site/index.html`. The first build downloads
a renderer once; later builds can reuse it offline. `zel check`, `zel watch`
and `zel view --watch` use the same cached renderer for validation and preview.
Portable Markdown also needs no container: use `zel new portable`, `zel build`
and `zel view`.
See the [CLI overview](/cli) for command availability and verification limits.

## Before you start

For rich double-click websites, skip container setup and go directly to
[installing `zel`](#install-zel). The first build needs a connection to download
its private renderer; subsequent builds can reuse it offline.

| | Needed for | |
| --- | --- | --- |
| **A container runtime** | Hosted `dev`, explicit static/container builds and image-backed deployments | Docker Desktop, Colima, Podman or Rancher Desktop |
| `curl` or `wget`, plus `tar` | Unix installer | macOS, GNU/Linux or WSL |
| PowerShell 5.1 or 7 | Native Windows installer | Windows x64 or ARM64 |

And what you do **not** need:

- **A separate Node.js/npm installation or project lockfile.** Rich file builds
  use the private runtime downloaded into the Zellij cache. Container-based
  commands run the engine inside their image.
- **`docker-compose`.** One container at a time; nothing to compose.
- **`gh`, the GitHub CLI**, for local documentation. GitHub workflow commands
  may use it when you explicitly invoke them.
- **A container runtime at all**, for rich double-click builds or portable
  web-only builds. `new`, `explain`, `list`, `context`, `detect` and `convert`
  also run natively with the content model compiled in.

### Installing a container runtime

This optional setup is for the container-based commands listed above.

<Tabs>
<Tab title="macOS">

**Colima** is the smaller of the two options and has no licence conditions. It
needs Homebrew, which is worth having anyway:

```bash title="terminal"
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install colima docker
```

Then start it — **with resources, not the defaults**:

```bash title="terminal"
colima start --cpu 8 --memory 24 --mount-type virtiofs --disk 80
```

<Callout type="warning" title="Change those numbers for your machine">
`colima start` on its own gives you 2 CPUs and 2 GB, and a site build on that is
painful.

| | |
| --- | --- |
| `--cpu` | Up to the cores you have — `sysctl -n hw.ncpu` says how many |
| `--memory` | GB for the virtual machine, not for your Mac. Half your RAM is a reasonable ceiling |
| `--disk` | GB, and it only grows as used. Raise it if you will run other containers |
| `--mount-type virtiofs` | Much faster file sharing than the default. Worth it every time |

The example suits a machine with 8 cores and 32 GB. On a 16 GB machine,
`--cpu 4 --memory 8 --disk 60` is closer.

These are fixed when the VM is created, so changing them later means
`colima stop` and starting again with the new values.
</Callout>

**Docker Desktop** works equally well if you have it already, or if your
organisation requires it. Nothing here needs one over the other.

</Tab>
<Tab title="Linux">

Docker Engine, from your distribution or Docker's own script:

```bash title="terminal"
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER"    # then log out and back in
```

Or **Podman**, which needs no daemon and no group membership:

```bash title="terminal"
sudo apt install podman    # or dnf, pacman, zypper
```

`zel` looks for `docker`, `podman` and `nerdctl`, in that order, so either works
with no configuration.

</Tab>
<Tab title="Windows">

**Docker Desktop with the WSL 2 backend.** Install WSL first if you have not:

```powershell title="PowerShell (as administrator)"
wsl --install
```

Then install Docker Desktop and enable WSL 2 integration in its settings.

<Callout type="tip" title="Work inside WSL, not on the Windows filesystem">
Put your content folder under `\\wsl$\Ubuntu\home\you\…` rather than `C:\`.
Bind-mounting across the Windows filesystem boundary is several times slower —
the difference between a build that takes one minute and four.
</Callout>

</Tab>
</Tabs>

### Start the image downloading now

The first container-based command waits for its engine image to download if it is missing.
You can pull the matching candidate image ahead of time:

```bash title="terminal"
export ZELLIJ_IMAGE=ghcr.io/mylife-inc/zellij-base:0.2.0-rc.17
docker pull "$ZELLIJ_IMAGE" &
```

It is a public image — no login, no account. By the time you have installed
`zel` and written a page, it will be there.

## Install `zel`

`zel` is the Zellij CLI: a single native binary, with no runtime of its own.
Use published [candidate 0.2.0-rc.17](https://github.com/mylife-inc/Zellij/releases/tag/v0.2.0-rc.17)
for this guide. Stable `0.1.3` predates these workflows. The candidate's six native
packages and both Linux image architectures passed
[public-artifact acceptance](https://github.com/mylife-inc/Zellij/actions/runs/44686349679).

If you already use a package manager, choose one of these installation methods:

```bash title="Homebrew — macOS and Linux"
brew install mylife-inc/tap/zel
```

```powershell title="Scoop — Windows"
scoop bucket add mylife-inc https://github.com/mylife-inc/scoop-bucket
scoop install mylife-inc/zel
```

Update managed installations with `brew upgrade mylife-inc/tap/zel` or
`scoop update; scoop update zel`. The standalone archive installers below are
another option. Use one installation method to avoid competing copies on PATH.

<Tabs>
<Tab title="macOS and Linux">

```bash title="terminal"
curl -fsSL https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17/install.sh -o install.sh
ZEL_VERSION=v0.2.0-rc.17 ZEL_RELEASE_BASE_URL=https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17 sh ./install.sh
```

Works on **Apple Silicon and Intel Macs**, and on Linux **x86-64 and arm64** —
the script reads `uname` and fetches the matching build. This candidate also
includes native Windows x64 and ARM64 archives.

To select another installation directory, reuse the downloaded installer:

```bash title="terminal"
ZEL_VERSION=v0.2.0-rc.17 \
ZEL_RELEASE_BASE_URL=https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17 \
ZEL_INSTALL_DIR="$HOME/.local/bin" sh ./install.sh
```

It installs to `$ZELLIJ_HOME/bin`, defaulting to `~/Dev/config/zellij/bin`,
and prints PATH guidance. `ZEL_INSTALL_DIR` takes precedence. For the default
resource home, add this line to your shell profile and open a new terminal:

```bash
export PATH="${ZELLIJ_HOME:-$HOME/Dev/config/zellij}/bin:$PATH"
```

The installer does not edit shell profiles. Homebrew keeps its own executable
location. Renderer and remote-template downloads share the
[Zellij resource home](/cli/config#zellij-home).

</Tab>
<Tab title="Windows">

Candidate 0.2.0-rc.17 supports native Windows x64 and ARM64. In PowerShell:

```powershell
Invoke-WebRequest https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17/install.ps1 -OutFile install.ps1
.\install.ps1 -Version v0.2.0-rc.17 -ReleaseBaseUrl https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17
$env:ZELLIJ_IMAGE = 'ghcr.io/mylife-inc/zellij-base:0.2.0-rc.17'
```

`-InstallDir` selects a directory and takes precedence over `ZELLIJ_HOME`.
The default is `$env:ZELLIJ_HOME\bin`, falling back to
`%USERPROFILE%\Dev\config\zellij\bin`. Add the resolved directory to your
user PATH and open a new terminal. The installer checks the archive checksum and
binary version before replacing a prior installation.

Native portable workflows need no WSL or Docker. Inside WSL, use the Linux
installation instructions instead. Hosted container workflows have separate
runtime requirements.

</Tab>
</Tabs>

<Callout type="info" title="What that script does">
Detects your platform, downloads the explicitly selected candidate archive,
**verifies it against its published SHA-256**, and installs one executable in the
selected directory. It preserves the existing executable if validation fails and
does not edit your PATH. The default user locations need no administrator rights.

You can read the attached
[install.sh](https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17/install.sh)
or [install.ps1](https://github.com/mylife-inc/Zellij/releases/download/v0.2.0-rc.17/install.ps1)
before running it.
</Callout>

## Check it

```bash title="terminal"
zel --version
zel doctor
```

`zel --version` should report `zel 0.2.0-rc.17`. For a rich site, `zel doctor`
reports the standalone renderer's cache path and readiness without downloading
it. Neither a rich file build nor a portable web-only build needs a successful
Docker check. Container-based operations have separate requirements; see
[`zel doctor`](/cli/doctor) for setup and endpoint diagnostics.

### Which one is yours

| If… | Go to |
| --- | --- |
| There is no documentation yet, and no repository to put it in | [Lab 1](/guide/quickstart/from-scratch) |
| There is documentation, in some other tool or none | [Lab 2](/guide/quickstart/existing-docs) |
| You are starting a codebase and want the docs to ship with it | [Lab 3](/guide/quickstart/new-project) |
| The codebase exists and the docs need to catch up | [Lab 4](/guide/quickstart/existing-repo) |

Labs 1 and 2 are about **writing**, and end with a published site. Labs 3 and 4
are about **shipping from a repository**, and assume you have content already —
from one of the first two, or the sample the scaffold writes.

## One optional tool, for publishing

Until [`zel deploy`](/cli/deploy) lands, uploading a built site to Netlify uses
Netlify's own tool. It is the only thing in these labs that needs npm:

```bash title="terminal"
npm install -g netlify-cli
netlify login
```

Labs 3 and 4 do not need it at all — they publish container images, which `zel`
does on its own.
