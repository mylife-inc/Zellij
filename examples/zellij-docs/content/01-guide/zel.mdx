---
title: The zel command
description: One binary for scaffolding, converting, validating, building and shipping a site.
---

`zel` is a native binary. It needs no Node on your machine: the commands that
describe Zellij's content model read a schema compiled into the binary, and the
ones that build run the engine in a container.

<Callout type="info" title="Not to be confused">
There is a well-known terminal multiplexer called Zellij whose binary is
`zellij`. This one is `zel`, so both can sit on the same PATH.
</Callout>

## Getting it

Binaries are published on the repository's releases page, one per platform.
`zellij prepare` and friends — the build-time commands a wrapper app runs — are
a separate thing that ships inside the npm package.

## Writing content

The commands that exist because nobody remembers nineteen section types.

```bash
zel explain bento-grid
```

Prints every field the type takes, which are required, their defaults, and the
fields of anything nested inside it — a bento tile's `title`, `span`, `icon`
and the rest. This is generated from the same schemas that validate content, so
it describes exactly what `zel check` will accept.

```bash
zel new section pricing-table --out sections/home/plans.yaml
```

Writes the file with its required fields filled in and the optional ones as
commented defaults. With no arguments and a terminal attached it asks; every
prompt has a flag, so the same thing scripts.

| Command | |
| --- | --- |
| `zel list sections` | All nineteen, with how many fields each takes. |
| `zel list themes` | All fourteen. |
| `zel explain <type>` | One type, in full. |
| `zel new docs [dir]` | A content folder that already validates. |
| `zel new app [dir]` | A Next.js wrapper around one. `--with-docs` adds a starter folder. |

## Converting from another tool

```bash
zel detect ./docs
zel convert ./docs --out ./content
```

`detect` says what a folder was written for and how sure it is. `convert`
writes a Zellij folder **beside** the original, never over it.

| Format | Read from |
| --- | --- |
| MkDocs | `mkdocs.yml`, including its `nav` tree |
| Docusaurus | `sidebars.js`, when it is declarative |

<Callout type="warning" title="What a conversion cannot do">
These tools describe a documentation tree. Zellij has that *and* marketing
pages built from section types with no equivalent in the source — so a
conversion produces a faithful guide folder and a landing page with one hero to
build on. It does not invent a landing page, and it says so every time.

A Docusaurus sidebar that computes its exports — `require`, a `map`, a template
literal — is not read at all. The converter falls back to the folder and names
the construct that stopped it, because a sidebar half-read from a file it did
not understand would look finished and be wrong.
</Callout>

Where nothing is recognised, there is no structure to convert from. The command
says so and points at `zel context`.

## Working with an AI agent

```bash
zel context zellij.md
```

Writes one self-contained description of the whole content model: the folder
layout, the naming and routing rules, every field of every config file, all
nineteen section types, the MDX components, and a worked example. Hand it to an
agent and ask for a content folder.

It is generated from the engine's schemas rather than written, and CI fails if
the copy compiled into the binary falls behind. A stale reference is worse than
none — an agent given one writes confident, invalid YAML, and because it looks
right the mistake surfaces as a failed build in your repository rather than as
an obviously outdated document.

## Building and shipping

| Command | |
| --- | --- |
| `zel check [dir]` | Validate. `--json` for a pipeline. |
| `zel dev [dir]` | Development server with hot reload. |
| `zel build [dir] --target <t>` | See below. |
| `zel deploy netlify\|vercel\|cloudflare\|ghpages\|s3` | Build and push. |

### What `--target` produces

| Target | Produces | Host |
| --- | --- | --- |
| `static` *(default)* | HTML, CSS and JS | Any CDN, free |
| `node` | A traced Node server | Any Node host |
| `image:static` | A container serving the static folder | Any registry |
| `image:node` | A container running the app | Any registry |

`static` is the default because documentation is read far more than it is
written, a CDN serves it better than a server would, and it is the only one that
costs nothing to host. The trade-off is that it loses `next/image`
optimisation — right for documentation, wrong for a marketing site heavy with
photography, which is what `image:node` is for.

## Doing several things at once

| Command | Runs |
| --- | --- |
| `zel migrate <src> --out <dir>` | detect → convert → check |
| `zel publish [dir]` | check → build → deploy |
| `zel ship <src>` | convert → check → image build → push |

Each is its primitives in order and does nothing they cannot. Converting a
folder and publishing it is one intention, and a tool that offered only the four
steps would make you assemble something it already knows how to assemble.

## When something is wrong

```bash
zel doctor
```

Reports the container runtime, the image, the versions, and what is missing.
The first thing to include in a bug report.
