Zellij uses a container for image packaging, image-backed deployment and
explicit `zel dev --dev-backend container`. Default `zel dev` uses verified
downloads and does not require a container. The container carries the engine
and its build environment, so those operations do not require a separate Node
installation on the user’s machine.

Rich double-click and HTTP websites use a downloaded, cached renderer:
`zel build` needs only `zel`, including `--target static`. Candidate rc.24 also
uses that cache for rich `check`, `watch`, `view --watch`, optional import
validation and static deployment builds.

```bash title="terminal"
zel dev --dev-backend container # explicitly serve through the container engine
zel image next     # the Next wrapper packaged as a container image
```

That is the whole of what most people need to know. You do not write a
Dockerfile, and there is not one in your repository.

Portable Markdown sites build and preview natively, without a container. These
instructions apply to the explicit container operations above.

## The base image

`ghcr.io/mylife-inc/zellij-base` is **public**. The source repository is also
public during current development. A site can be built without cloning the
engine's source.

It is a Next.js wrapper with the engine at `/opt/zellij` and **nothing
installed**. It carries a manifest describing what a site will
need, and the install happens when a site is built.

The image omits the wrapper's installed dependencies; a site build resolves its
own lockfile. Image size depends on the release and architecture. One image serves a site that wants
LaTeX, a site that wants diagrams, and a site that wants neither.

The wrapper inside it is generated by the same scaffold
[`zel new app`](/cli/new#zel-new-app-dir) uses, so it cannot drift from what you
would get locally.

## Optional features

Mathematics costs about fifty megabytes to install and diagrams about a
hundred, and most documentation wants neither. Both are optional: a site that
does not ask for them never fetches them, and the engine renders without them
rather than failing.

| Feature | Turns on | Costs |
| --- | --- | --- |
| `maths` | `$…$` and `$$…$$` | ~50 MB at build time, nothing at runtime |
| `diagrams` | ```mermaid fences | ~100 MB at build time, ~10 MB in the browser |
| `all` | both | |

`zel` detects which your content uses and installs accordingly. `--features`
overrides it when you want the dependency present before the content that needs
it.

<Callout type="info" title="Mindmaps need neither">
A `mindmap` fence is laid out during the build by the engine itself, so it works
everywhere and adds nothing. Maths is also build-time only — MathJax typesets to
SVG and never reaches the browser. Only Mermaid ships anything to a reader.
</Callout>

Four published variants exist — `:0.2.0-rc.24`, `:0.2.0-rc.24-maths`, `:0.2.0-rc.24-diagrams`
and `:0.2.0-rc.24-all` — for pipelines that would rather name an image than pass a
flag. Because nothing
is installed in the base image they are all the same size.

## Producing a container of your own site

Different thing, same word. The base image *builds* sites; you may also want the
site itself to *be* an image.

```bash title="terminal"
zel image build --tag acme-docs:v2
zel image run acme-docs:v2
zel image push acme-docs:v2 --registry ghcr.io/acme
```

That produces a Node runtime serving your site on port 3000, deployable to
Railway, Fly.io, Cloud Run, ECS or anywhere else that runs containers. See
[`zel image`](/cli/image) for the detail, and [`zel build`](/cli/build) for
choosing between that and a static site.

Static images contain the generated HTML and their HTTP server. Next images
contain the standalone Next runtime and the dependencies it needs. Authored
documentation and temporary build contexts are excluded from the runtime image.

## In a pipeline

Generate locally from a configured site:

```bash
zel ci --zel-version 0.2.0-rc.24
```

Save `publish.action: push`, choose `publish.image: static` or `next`, and set
`image.name` to the registry destination. PRs validate and build that artifact;
eligible publication events call the native build-once publication operation.
GHCR uses the job's scoped token; other registries use configured repository
secrets. Generation requires Git but no local container runtime.

The generated workflow pins a compatible binary release and engine image.
Candidate `0.2.0-rc.24` and its engine images are published; stable `0.1.3` is
incompatible. Other selected versions must also be published before use. [`zel ci`](/cli/ci) describes all settings and explicit
credential provisioning. The legacy GHCR Next-image preset remains available as
`zel ci --target image --zel-version 0.2.0-rc.24`.

## Requirements

`zel` tries Docker, Podman, then nerdctl. Colima is supported through its
Docker endpoint; it is not a separate runtime executable selected by `zel`.

```bash title="terminal"
zel doctor
```

reports which one it found and on which socket — the usual cause of "Docker is
not running" is a runtime that *is* running, on a socket the default context
does not look at.

The commands that only read the content model — `explain`, `list`, `context`,
`detect`, `convert`, `new` — need no runtime at all. They are pure Rust with the
schema compiled in.

## If you have to own the build

Some organisations require a Dockerfile in the repository, reviewed like any
other file. [`zel image dockerfile`](/cli/image#zel-image-dockerfile) prints the
one `zel` would have used, with your arguments resolved.

It becomes a normal file at that point, with the usual consequence: it stops
tracking changes to the base image, and updating it is yours.

## Getting the wrapper app out

If you want an editable Next.js app and its engine package, use [`zel eject`](/cli/eject):

```bash title="terminal"
zel eject --with-docs --out my-site
cd my-site
npm install
npm run dev
```

To keep an existing hosted site, use `zel eject docs/manual --out my-site`
instead. Candidate rc.24 downloads verified editable sources into the shared
`ZELLIJ_HOME` cache and copies its engine into `vendor/zellij`. Generation needs
only `zel`; `--offline` reuses prepared sources. Running the app needs Node/npm.

[`zel new app`](/cli/new#zel-new-app-dir) uses the same source cache by default
and accepts name, port and feature choices. Its explicit `--engine` option keeps
a dependency on your own built local engine. To extract a particular container
instead, pass `eject --image <image>` or set `ZELLIJ_IMAGE`; that path uses a
stopped container. Neither generation path installs dependencies. Copying
`/app` alone from an image omits `/opt/zellij` and is not a complete wrapper.
